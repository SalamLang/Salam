\chapter{Enums and Pattern Matching}%
\label{ch:enums-matching}

Many values in a program are not really numbers or text: they are a choice from
a small, fixed set of possibilities. A day is one of seven; a traffic light is
red, amber, or green; an order is pending, shipped, or delivered. An
\textbf{enum} (short for \emph{enumeration}) lets you name such a set and use those
names directly, instead of remembering that ``3 means Thursday.''

\section{Defining an enum}

An enum is declared with the \code{enum} keyword, a name, and a list of
\textbf{members} (the allowed values), closed with \code{end}. The members may
be written on one line, separated by commas, or one per line:

\begin{salamen}
enum Day: Mon, Tue, Wed, Thu, Fri, Sat, Sun end
\end{salamen}

This defines a new type, \code{Day}, whose only values are the seven named days.
A variable of type \code{Day} can hold exactly one of them and nothing else. That
is the whole point: the type makes invalid values \emph{unrepresentable}.

\section{Using enum values}

You refer to a member by qualifying it with the enum's name and a dot:
\code{Day.Mon}, \code{Day.Sat}. This makes it clear which enum the value belongs
to and avoids name clashes between enums that happen to share a member name.

\begin{salamen}
enum Day: Mon, Tue, Wed, Thu, Fri, Sat, Sun end

func main:
    today := Day.Sat
    if today == Day.Sat or today == Day.Sun:
        println "It's the weekend!"
    else:
        println "A working day."
    end
end
\end{salamen}

\begin{progout}
It's the weekend!
\end{progout}

You compare enum values with \code{==} and \code{!=}, exactly as you would
numbers. The variable \code{today} can only ever be one of the seven days, so the
compiler (and the next person to read your code) knows precisely what values
are in play.

\section{Enums have an underlying value}

Every enum member carries an underlying value of one of three kinds: an
\code{int} (the default), a \code{str}, or a \code{float}. All the members of
one enum share the same kind: you cannot mix an int-valued member with a
string-valued one in the same enum.

By default the values are integers, counting up from zero in order: in
\code{Day}, \code{Mon} is 0, \code{Tue} is 1, and so on to \code{Sun} at 6. You
can see a member's number by converting it to an integer with \code{as}:

\begin{salamen}
enum Day: Mon, Tue, Wed, Thu, Fri, Sat, Sun end

func main:
    println Day.Mon as int      // 0
    println Day.Sat as int      // 5
end
\end{salamen}

\begin{progout}
0
5
\end{progout}

\subsection{Choosing the numbers}

When the underlying numbers matter, because they correspond to codes, flags, or
external values, you can assign them explicitly. Any member you do not give a
number to continues counting up from the previous one:

\begin{salamen}
enum Color:
    Red            // 0
    Green = 5      // 5
    Blue           // 6 (continues from 5)
end

func main:
    println Color.Red as int, Color.Green as int, Color.Blue as int
end
\end{salamen}

\begin{progout}
0 5 6
\end{progout}

\code{Red} keeps the default 0, \code{Green} is pinned to 5, and \code{Blue}
follows on at 6. This is handy when an enum mirrors values defined elsewhere, such
as HTTP status codes or hardware register values.

\begin{warn}
The conversion goes one way freely: an enum value turns into its underlying
value with \code{as}. Going the other way, treating an arbitrary integer as an
enum, is something to do only with care, because a number might not correspond
to any member. Prefer to keep values in their enum form and convert only at the
edges of your program, where you must.
\end{warn}

\subsection{String- and float-valued enums}

When an enum's members stand for something that is naturally text or a
fractional number (a wire-format code, a currency symbol, a physical constant),
give every member an explicit \code{str} or \code{float} value instead of an
int. Unlike int members, a string- or float-valued member cannot be left to
auto-increment: every member needs its own explicit value.

\begin{salamen}
enum Currency:
    USD = "dollar"
    EUR = "euro"
    GBP = "pound"
end

enum Constant:
    Pi = 3.14159
    E = 2.71828
end

func main:
    println Currency.USD as str
    println Constant.Pi as f64
end
\end{salamen}

\begin{progout}
dollar
3.14159
\end{progout}

Convert a string-backed member with \code{as str}, and a float-backed one with
\code{as f64} (\code{as float} also works, but \code{float} is the 32-bit
\code{f32}, so it prints as \code{3.141590118408203}); \code{as int} only ever works on an
int-backed enum. Comparing two members of the same enum with \code{==} works
the same way regardless of which kind backs it.

\section{Names, and going from a name back to a value}

Every enum member's own name, a distinct thing from its underlying value, is
available too. Call \code{.name()} on a value to get that member's name as a
\code{str}, regardless of which kind backs the enum:

\begin{salamen}
enum Suit: Hearts, Diamonds, Clubs, Spades end

func main:
    s := Suit.Diamonds
    println s.name()
end
\end{salamen}

\begin{progout}
Diamonds
\end{progout}

The reverse direction, parsing a name string back into a member, is
\code{EnumName.FromString(name, ok)}. Like other fallible operations in Salam,
it reports success through an \code{ok} argument you pass in and it sets,
rather than by throwing: always check \code{ok} before trusting the result.

\begin{salamen}
enum Suit: Hearts, Diamonds, Clubs, Spades end

func main:
    mut ok := false
    s := Suit.FromString("Clubs", ok)
    if ok:
        println s.name()
    else:
        println "not a suit"
    end
end
\end{salamen}

\begin{progout}
Clubs
\end{progout}

Two more calls answer questions about the enum \emph{type} itself rather than
about one value: \code{EnumName.Count()} is the number of members, and
\code{EnumName.Names()} returns every member's name, in declaration order, as
a \code{Vector<str>}:

\begin{salamen}
enum Suit: Hearts, Diamonds, Clubs, Spades end

func main:
    println Suit.Count()
    names := Suit.Names()
    println names.get(0)
end
\end{salamen}

\begin{progout}
4
Hearts
\end{progout}

\section{Pattern matching with \texttt{match}}

To choose an action based on which enum value you have, Salam provides
\code{match}. A \code{match} looks at one value, the \emph{subject}, and picks the
first \textbf{arm} whose pattern fits it. Each arm is a pattern, a colon, the
result, and \code{end}. Because \code{match} is an \emph{expression}, the whole
thing produces a value that you can return, print, or store:

\begin{salamen}
enum Light: Red, Amber, Green end

func action(light: Light): str:
    ret match light:
        Red: "Stop" end
        Amber: "Slow down" end
        Green: "Go" end
    end
end

func main:
    println action(Light.Red)
    println action(Light.Amber)
    println action(Light.Green)
end
\end{salamen}

\begin{progout}
Stop
Slow down
Go
\end{progout}

Inside the arms you write the bare member names (\code{Red}, not
\code{Light.Red}); the compiler already knows the subject is a \code{Light}.

The most valuable property of \code{match} is that it is \textbf{exhaustive}: the
compiler checks that every member is handled. Leave out the \code{Green} arm and
the program does not build:

\begin{shell}
error[E080]: non-exhaustive match on enum 'Light': missing member Green
\end{shell}

If you later add a member to an enum, every \code{match} that forgot it becomes a
compile error that points you straight to the code you need to revisit. A
forgotten case is a classic source of bugs in other languages; here it cannot
slip through.

\subsection{Several members in one arm, and \texttt{else}}

An arm may list several patterns separated by commas, and a final \code{else}
arm catches everything not matched so far. An \code{else} also satisfies the
exhaustiveness check, so use it only when ``all the rest'' really means the same
thing:

\begin{salamen}
enum Day: Mon, Tue, Wed, Thu, Fri, Sat, Sun end

func kind(d: Day): str:
    ret match d:
        Sat, Sun: "weekend" end
        else: "weekday" end
    end
end

func main:
    println kind(Day.Sun), kind(Day.Tue)
end
\end{salamen}

\begin{progout}
weekend weekday
\end{progout}

\code{match} works on numbers and strings too (\code{match n \% 2: 0: "even"
end else: "odd" end end}), but there the \code{else} arm is required, because no
list of numbers can cover every possible \code{int}.

\begin{note}
Salam also has a \code{switch} statement. Unlike \code{match} it does not produce
a value, and its arms \emph{fall through} into the next one unless they end with
\code{break}, just as in C. Reach for \code{match} when you are choosing between
enum members; it is shorter and the compiler guards every case.
\end{note}

\section{Enums that carry data}

So far each member has been a bare name. A member can also carry
\textbf{values} of its own, declared like function parameters. The classic
example is a shape: a circle needs a radius, a rectangle needs a width and a
height, and an empty shape needs nothing:

\begin{salamen}
enum Shape:
    Circle(r: f64)
    Rect(w: f64, h: f64)
    Empty
end

func area(s: Shape): f64:
    ret match s:
        Circle(r): 3.14 * r * r end
        Rect(w, h): w * h end
        Empty: 0.0 end
    end
end

func main:
    shapes := [Shape.Circle(2.0), Shape.Rect(3.0, 4.0), Shape.Empty]
    each s in shapes:
        println s, area(s)
    end
end
\end{salamen}

\begin{progout}
Circle(r = 2) 12.56
Rect(w = 3, h = 4) 12
Empty 0
\end{progout}

You build a value with \code{Shape.Circle(2.0)}, much like calling a function.
In a \code{match} arm, the pattern \code{Rect(w, h)} both checks which member you
have \emph{and} gives names to the values inside it, so the arm's result can use
\code{w} and \code{h} directly. Write \code{\_} in place of a name to skip a value
you do not need. Printing such a value shows the member and its fields.

A value of type \code{Shape} is always exactly one of the three, and it is
impossible to read a radius out of a rectangle: the only way to get at the data
is through a pattern that names the right member. Chapter~\ref{ch:error-defer}
uses this same idea for results that are either a value or an error.

\section{Enums as state machines}

Enums shine when a value moves through a sequence of well-defined states. Consider
an order that progresses from \code{Pending} to \code{Shipped} to
\code{Delivered}. An enum names the states, and a function decides the next one:

\begin{salamen}
enum Status: Pending, Shipped, Delivered end

func next(s: Status): Status:
    ret match s:
        Pending: Status.Shipped end
        Shipped: Status.Delivered end
        Delivered: Status.Delivered end
    end
end

func label(s: Status): str:
    ret match s:
        Pending: "pending" end
        Shipped: "shipped" end
        Delivered: "delivered" end
    end
end

func main:
    mut s := Status.Pending
    println label(s)
    s = next(s)
    println label(s)
    s = next(s)
    println label(s)
end
\end{salamen}

\begin{progout}
pending
shipped
delivered
\end{progout}

The enum guarantees that \code{s} is always a valid status, and the \code{next}
function encodes the legal transitions in one place (\code{Delivered} is final,
so it stays put). This is a small example of a \textbf{state machine}, a powerful
and common way to model anything that moves through stages, from a game's
screens to a network connection's lifecycle.

\begin{deep}[In Depth: why an enum beats a bare integer]
You could represent a status with a plain \code{int} (0 for pending, 1 for
shipped, and so on), and many programs do. But then nothing stops you from
assigning \code{99}, or from adding a \code{Status} to a \code{Day} by accident,
or from forgetting which number meant what. An enum makes those mistakes
impossible: the type system knows the only valid values, the names document
themselves, and the compiler checks that you use them consistently. The cost is
nothing: a plain enum compiles down to exactly the integer you would have written by
hand, so you get the safety for free.
\end{deep}

\section{Chapter summary}

\begin{itemize}[leftmargin=1.4em]
  \item An \code{enum} names a fixed set of values; a variable of that type holds
        exactly one member.
  \item Refer to members as \code{EnumName.Member}; compare them with \code{==}
        and \code{!=}.
  \item Members have an underlying value: int by default, counting from 0,
        or an explicit \code{str} or \code{float}, one kind per enum. Convert
        with \code{as int}/\code{as str}/\code{as float} to match.
  \item \code{.name()} gets a value's member name as a \code{str};
        \code{EnumName.FromString(name, ok)} parses one back, reporting success
        through \code{ok}. \code{EnumName.Count()} and \code{EnumName.Names()}
        answer questions about the enum type itself.
  \item \code{match} picks the arm whose pattern fits the subject and produces
        a value; on an enum it must cover every member (or end with
        \code{else}), which the compiler checks.
  \item Members can carry data (\code{Circle(r: f64)}); a pattern such as
        \code{Rect(w, h)} checks the member and names its values.
  \item Enums are ideal for modelling states and transitions (state machines),
        and are safer than bare integers at no run-time cost.
\end{itemize}

\exercise Define \code{enum Suit: Hearts, Diamonds, Clubs, Spades end} and print
the integer value of each member.

\exercise Write a function \code{is\_red(s: Suit): bool} that returns \code{true} for
\code{Hearts} and \code{Diamonds}, and test it on all four suits.

\exercise Define \code{enum Direction: North, East, South, West end} and a function
\code{turn\_right(d: Direction): Direction}, using \code{match}, that rotates clockwise (North becomes
East, and so on, West wrapping back to North).

\exercise Model a traffic light that cycles \code{Green} $\to$ \code{Amber} $\to$
\code{Red} $\to$ \code{Green}. Write a \code{next} function and run it through two
full cycles.

\exercise Define \code{enum HttpStatus} with \code{Ok = 200},
\code{NotFound = 404}, and \code{ServerError = 500}, and print each member's
number.
