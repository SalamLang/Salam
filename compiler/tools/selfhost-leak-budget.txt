# Self-host leak budget.
#
# One line per canonical compiler invocation:
#
#   <case> <max_leaked_allocations>
#
# Enforced by compiler/tools/bash/leakcheck-selfhost.sh, which builds the
# self-hosted compiler with `--asan` and reads LeakSanitizer's own count of
# blocks still unreachable at exit. `<case>` names a fixed command in that
# script, not a test file, so the numbers are comparable run to run.
#
# Why a budget and not zero, when the C compiler is held to zero: the C
# compiler allocates from an arena it frees on the way out, so LSan sees
# nothing. Salam is manually memory-managed and has no arena behind its
# string temporaries, so every discarded `a + b` in compiler/*.salam is a
# live block until the process exits. Getting to zero means changing how the
# self-hosted compiler allocates, not adding a handful of frees - and until
# then a ratchet is what keeps the number from silently growing.
#
# This is a ratchet: the script FAILS when a case leaks more than its number
# and WARNS ("under budget - lower it") when it leaks less. Lower the number
# in the same change that improved it. The goal is every line at 0.
#
# Each number is the observed count plus ~2% headroom, and the script's
# "lower it" nag has a 5% deadband. Repeated runs of one binary on one machine
# are identical to the allocation, but the count drifts by a few dozen BETWEEN
# machines: the compiler allocates while walking absolute paths, and
# /home/runner/work/Salam/Salam is not the length of anyone's local checkout.
# An exact ratchet would have failed CI on a 28-allocation difference that
# said nothing about the compiler.
#
# Measured 2026-08-08 on Linux/x86-64, gcc 13, on both a local checkout and a
# GitHub ubuntu-latest runner (observed: version 6269, help 6257, format 6477,
# inspect 126078-126100, exec 130515-130528, build 230706-230734). The
# starting point was roughly twice these figures before three fixes landed
# together with this file:
#   - logger.New no longer reserves 512 diag-source slots (12 KB) for every
#     Logger ever default-constructed - one per Lx/Ps/Sema/Codegen
#   - langpack has_join_char stopped allocating a per-character Vector<str>
#     for every identifier the lexer scans
#   - io.ReadAll releases each 4 KB read buffer instead of dropping it, and
#     source.Free lets the schema/std-index scans release file text they are
#     done with
# `salam version` went from 4,349,628 bytes leaked to 148,810.
#
# Re-measured 2026-08-15 on Linux/x86-64, gcc 13 (observed: version 6179,
# help 6167, format 6372, inspect 118043, exec 122511, build 217275). Three
# fixes, the first two of which are what had pushed `inspect` and `exec` over
# the old numbers:
#   - sal_path PathJoin/PathDir build their answer into one StringBuilder
#     instead of composing PathToSlash(PathTrimSep(dir)) with `+`. The old
#     shape dropped three intermediate strings per join, and the std-package
#     scan joins paths thousands of times for a one-file compile.
#   - sema_definit releases the Di vectors and every di_snap flow snapshot;
#     one Di plus a snapshot per if/match/loop was leaked per checked function
#   - the lexer frees the '_'-stripped copy of each numeric literal, which
#     exists only to be handed to decode_number - the token keeps the literal
#     as written
#
# One caveat learned here, since the header above promises run-to-run
# reproducibility: that holds for one BINARY, not across a rebuild. These
# counts are LSan's unreachable-block count, and whether a block is reachable
# depends on stale pointers left in the stack and registers, so a change that
# only frees memory can still move an unrelated case by ~2%. Freeing the Di
# vectors alone moved `build` +5,116 with the lexing work provably identical
# (same 76 parses, same 73,728 tokens). Do not read a small move in one case
# as a leak in the code you just touched; diff the per-callsite profiles.

# Re-baselined 2026-08-18 on Linux/x86-64, gcc 13 (observed: version 6179,
# help 6167, format 6431, inspect 215492-215575, exec 219951, build 927314;
# the CI runner saw 215571 / 219943 / 927349). Only inspect/exec/build moved,
# and NOT because the compiler started leaking more per unit of work - the
# unit of work grew. These cases compile tests/en/basics/hello.salam, whose
# cost is dominated by the std/ packages the loader pulls in transitively, and
# 0.3.1 added a lot of stdlib (calendar, graph, matrix, json, image, dotenv,
# ...). Lexing the same hello.salam against the v0.3.0 std/ versus this one,
# with one and the same compiler binary:
#
#   case      v0.3.0 std/      this std/     growth
#   build     71,555 tokens    317,199       4.43x
#   inspect   40,168 tokens    162,293       4.04x
#
# against which the leak counts moved 217,275 -> 927,314 (4.27x) and
# 118,043 -> 215,535 (1.83x). Per token that is 3.04 -> 2.92 leaked
# allocations for build and 2.94 -> 1.33 for inspect: flat to better, in both
# cases, which is why this is a re-baseline and not a leak hunt. 88% of what
# remains is still the one known shape - the lex_slice() substring each token
# keeps as its lexeme, from scan_op/scan_number/scan_ident - unchanged since
# the numbers above it were measured.
#
# The ratchet only moves down for a FIXED workload; it cannot tell a real
# regression from std/ getting bigger. If these numbers need raising again,
# check the token counts first, the same way this entry did.

# Re-baselined 2026-08-21 on Linux/x86-64, gcc 13 (observed: version 6179,
# help 6167, format 6431, inspect 221689, exec 226231, build 937000; the CI
# runner saw 221855 / 226227). Only inspect and exec moved, and by 0.8% each -
# the same shape as the entry above, checked the same way rather than assumed.
#
# One ASan binary, two stdlib trees, nothing else different:
#
#   case      pre-merge std/   this std/    delta
#   inspect   219,939          221,772      +1,833
#   exec      224,481          226,231      +1,750
#
# The deltas are the whole overage (the budgets were 220,000 and 224,500, and
# the pre-merge numbers sit right on them), so the compiler is not leaking
# more per unit of work - there is more work. std/ gained five packages in
# 0.3.2 (aws, google, webpush, net/httpx, net/http/swagger), 599 -> 614
# package files, and the std index scan reads every one of their headers to
# build the import alias table. More files scanned, more allocations, flat
# per file.
#
# Raised by ~2%, the headroom this file has always carried.

version 6300

inspect 226500
exec 231000
