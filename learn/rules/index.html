What the compiler insists on

The Salam compiler catches a great many mistakes before the program ever runs. Every message says what is wrong, where, and usually how to fix it. This lesson goes through the rules behind the messages you will meet most.

Why so strict?

Every error the compiler catches is an error that never reaches a user. That is why Salam treats as errors several things that other languages only warn about: a variable nobody reads, a mut that never changes, a branch that can never run. Warnings tend to pile up and get ignored; an error is fixed on the spot, so a Salam program that compiles has no such leftovers in it.

Reading an error

A typical message looks like this:

[SEMANTIC][ERROR] E013: cannot reassign immutable variable 'total'; declare it 'mut' to reassign it, or assign to its elements or fields instead (app.salam:3:5)

  • E013 is the error code. It is the same in English and Persian, so it is the thing to search for.
  • Then comes the problem, and after the semicolon the usual fix. Read the message to the end; the fix is often all you need.
  • The end of the line gives the file, line and column: line 3, column 5 of app.salam.

Mistakes in the shape of the code, such as a missing end or a word that is not Salam, are reported by the parser instead. Those show the line itself with a caret under the spot, and often a help: line, for example error: '&&' is not a Salam operator; write 'and'. A Persian file gets its messages in Persian.

Fix the first error first. One mistake can cause others further down: misspell a name, and the compiler reports both the unknown name (E001) and the variable you meant, which is now unused (E059).

Nothing unused

A variable, parameter, private function or import that nothing uses is an error: E059, E062, E066 and E082. Usually the right fix is to delete it, or to notice that you forgot to use it. Starting the name with _ silences the error, but keep that for the one real case: a signature you do not control. Here every handler must take a user and a text, and Shout has no use for the user:

rules-unused.salam
interface Handler:
    func handle(user: str, text: str): str
end

struct Echo:
    pub func handle(user: str, text: str): str:
        ret user + " said " + text
    end
end

struct Shout:
    pub func handle(_user: str, text: str): str:
        ret text + "!"
    end
end

func run(h: dyn Handler):
    println h.handle("sara", "hello")
end

func main:
    run(Echo {})
    run(Shout {})
end
Outputsara said hello hello!

Without the _, the compiler would say E062: unused parameter 'user', and its message itself says to use _ only when the signature is fixed.

mut only where things change

A variable made with := cannot be reassigned (E013). Add mut when it must change, and only then: a mut that never changes is also an error (E069). Adding to a Vector or a HashMap changes the data it points to, not the variable, so push works without mut. A value fixed for the whole program is a const.

rules-mut.salam
const LIMIT := 3

func main:
    names := Vector {} as Vector<str>
    defer names.free()
    names.push("Sara")
    names.push("Reza")
    names.push("Mina")
    names.push("Ali")
    mut shown := 0
    each n in names:
        if shown == LIMIT:
            break
        end
        println n
        shown += 1
    end
    println shown, "of", names.len(), "shown"
end
OutputSara Reza Mina 3 of 4 shown

Types are never guessed

Salam does not convert between types behind your back. Putting a str where an int belongs is E002 in an assignment and E012 in a call, and a condition must be a real bool: if items: with a number is E021, so write if items > 0:. The two branches of ?: must have the same type. Convert explicitly with as, but not when the value already has that type: n as int on an int is a useless cast, E093.

Every path is checked

The compiler follows every path through a function. A function that returns a value must return it on every path (E071: function 'sign' can fall off its end), a match on an enum must cover every member or have an else (E080 names the missing ones), and code after a ret can never run (E070). The same goes for a condition that is always false (E068), an empty if branch (E060) and a statement whose value is thrown away, like n + 1 on its own line (E110).

rules-flow.salam
enum Light: Red, Yellow, Green end

func action(l: Light): str:
    ret match l:
        Red: "stop" end
        Yellow: "slow down" end
        Green: "go" end
    end
end

func sign(n: int): str:
    if n > 0:
        ret "positive"
    else n < 0:
        ret "negative"
    end
    ret "zero"
end

func main:
    println action(Light.Yellow), action(Light.Green)
    println sign(-4), sign(0), sign(9)
end
Outputslow down go negative zero positive

When a new member is added to Light later, every match that does not handle it stops compiling, which is exactly where you need to look.

No exceptions, and main returns the exit code

Salam has no exceptions and no try and catch. A function that can fail says so in what it returns: a bool with the result in a &: parameter, as below, or a Result enum with the ? operator from the enums lesson. The caller checks it right away.

rules-exit.salam
func parse_age(text: str, age &: int): bool:
    n := text.to_int()
    if n <= 0 or n > 150:
        ret false
    end
    age = n
    ret true
end

func main:
    mut age := 0
    each text in ["42", "abc", "900"]:
        if parse_age(text, age):
            println text, "is a valid age"
        else:
            println text, "is not an age"
        end
    end
    if age == 0:
        printerrln "no valid age found"
        ret 1
    end
    println "last valid age:", age
end
Output42 is a valid age abc is not an age 900 is not an age last valid age: 42

The value main returns is the program's exit code: ret 1 reports failure to the shell, and no ret means 0. Calling os.Exit inside main is E109, because it would skip the cleanup that main deferred.

A few mistakes are caught by the parser and have no code: while (the loop is until, see the loops lesson), && and || (write and and or), a typed declaration like n: int = 2 (write n := 2), and a reserved word used as a name, such as a parameter called to.

A few hints

  • Fix the first message first, then build again; many of the later ones disappear with it.
  • Read every message to the end. The part after the semicolon is usually the fix.
  • Do not reach for _ or pub to make an error go away. The compiler is pointing at code that is dead, unfinished or in the wrong place.
  • Search the code, such as E071, rather than the wording: the code is the same in every language.
  • Run salam format before chasing order errors; it moves many definitions into place for you.
