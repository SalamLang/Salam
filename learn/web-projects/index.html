Whole pages: six projects

Elements, styles and events are easier to learn one at a time and easier to use together. This lesson builds six whole pages, each the size of something you might really publish. For every project you get the goal, the code running in the preview, the decisions that matter and a few ideas for taking it further.

How to build a page

Every project below was built in the same order, and the order is a good habit. First the content: write the headings and the text in plain elements, with no styling, and check that the page makes sense. Second the structure: put the parts in landmarks such as header, main, section and footer (page structure), because they give the page its outline. Third the look: colours, spacing and layout (styles, layout, responsive pages). Last the behaviour: state, handlers and the dom helpers (state, the DOM and timers). A page that works at each step is easy to repair. A page that was styled before it had content is not.

Two habits keep the code short. Values used in many places, such as a brand colour, go into a constant above the page. A piece that appears more than once, such as a price card or a statistic, becomes a component. All the previews are live: click, type and resize your browser window to see how the pages react.

Walkthrough. The page is a stack of full width bands inside main, and each band is a section that sets its own background and its own padding. 6vw of padding left and right keeps the text away from the edges on every screen size, and the heading uses clamp(2rem, 6vw, 3.4rem) so it grows with the window but never gets too small or too big.

The columns need no media query. repeat(auto-fit, minmax(220px, 1fr)) says: make as many columns as fit, each at least 220 pixels wide, and share the rest equally. Three cards sit side by side on a laptop, and the same rule stacks them on a phone. The price cards are one component, Plan, with three parameters. The content: end line inside it is a slot: whatever you write between Plan: and its end lands there, so each plan can list different details. Its look on hover, a small lift and a shadow, is written once with the hover prefix and a transition that makes the change smooth. BRAND and ACCENT are constants, so changing the colour of the whole page is a one line edit.

Change it next. Make the middle plan stand out with a darker border and a small badge. Add a media rule that stacks the header on very narrow screens. Turn the call to action into a link to a sign up page, and add a form such as the one in project 3.

Walkthrough. Reading is the whole point, so the text rules come first: a serif font, a line height of 1.75 and a column that never gets wider than the page allows. The two column layout is a grid with minmax(0, 1fr) 17rem: the sidebar is a fixed 17rem and the article takes the rest. The 0 in minmax matters, because without it a long word or a wide picture can force the column wider than the screen. The box has a max width and margin = 0, "auto", which centres it on a big monitor.

The responsive part is the media: child of the grid. Below 760 pixels it replaces the two columns with one, and since the sidebar comes second in the source, it lands under the article. Order in the source is order on a phone, so write the parts in the order a phone reader should meet them. The meta line uses time with a machine readable datetime, the picture sits in a figure with a figure caption, and the quotation is a block quote whose bar is border inline start. Start and end are logical sides: in a right to left page the bar moves to the right edge by itself. Tag is a small component for the topic pills.

Change it next. Add a table of contents as a nav with links to the headings (give the headings ids). Add a dark version with a style element and prefers-color-scheme. Print it: a media = "print" rule that hides the sidebar.

Project 3: a sign up form with live checks

Goal. A form that tells people what is wrong while they type, not after they press the button: a green or red border on every field, a message under it, a strength bar for the password, and a Join button that stays off until everything is right.

web-project-signup.salam
import dom

func strength(word: str): int:
    mut score := 0
    if word.Len() >= 8:
        score++
    end
    if word.Lower() != word:
        score++
    end
    repeat 10 in d:
        if word.Includes("" + d):
            score++
            break
        end
    end
    ret score
end

func good_name(name: str): bool:
    ret name.Len() >= 2
end

func good_mail(mail: str): bool:
    ret mail.Includes("@") and mail.Includes(".") and mail.Len() >= 6
end

func good_again(word: str, again: str): bool:
    ret word.Len() > 0 and again == word
end

Walkthrough. The page remembers four strings, one for each field, and a flag for the Show button. Every field has one job: its input handler writes the new text into its variable. Everything else is worked out from the four strings and drawn again whenever one changes, so the form can never be half updated. That is the pattern from the lesson on state. Small functions say whether a value is good (good_name, good_mail, strength, good_again). Each field draws itself from them: an if inside the input gives it the green border when the field is not empty and good, another gives it the red one when it is not empty and bad (nobody wants red on a form they have not touched), and the note under it is empty or holds the message. The colours sit next to focus: because they are states of an element and not decisions of the script.

The password score counts three things, length, a capital letter and a digit, and the bar shows score * 33 percent. The Show button flips a variable and the field takes its type from it. The email field has type = "email" and autocomplete values, so phones show the right keyboard and password managers know what to fill. The form's submit handler calls dom.PreventDefault(e) and shows a greeting in place of sending anything, because the preview has no server. The Join button is disabled until all four checks pass, and a disabled: block dims it.

Keep the names of your handler functions different from the id of every button and field in the form. A button with id = "join" and a function called join do not get along: inside a form the browser finds the button before the function, and the click does nothing. The functions here are called welcome and reveal. And remember that checks like these are help for the visitor. The server must check the same things again.

Change it next. Add a checkbox "I accept the rules" that must be ticked before the button turns on. Check the name for letters only. Replace the strength bar with a meter element. Send the form to a real address with action and method and validate it on the server (see the last section).

Walkthrough. This is the state pattern at full size. The state is three variables of one component: items, one string per task with 1 or 0 in front of the text to say whether it is done, mode, the filter, and draft, the text in the box. The page keeps nothing else. The list is an each over items, an if inside it lets a row through only when it passes the filter, and every row is a small component that draws itself from its own string: the tick, the grey colour and the strike-through all come from is_done. A row cannot change the list, so the page passes it two functions, flip and remove, and the row calls them with its text. They find the task in items, change it and save. There is no draw function to call and no handler to keep in step: changing items or mode is all it takes.

A row copies its entry into its own variable (held := entry) because a handler reads the variable of its own component, not the loop variable it was made with. Saving writes one string, one line per task, with 1 or 0 in front of the text. Loading is load, which gives items its first value when the page opens. A ternary expression picks between two values where the code needs a choice.

The preview runs in a frame that does not allow storage, so there the list works but does not survive a reload. On a real page it does. Task text is always put in with SetText, never SetHtml.

Serving a page from a Salam program

Everything above is a fixed page: its structure is decided when you compile it, and the preview is the finished result. A real site needs pages that depend on the visitor, such as a greeting with their name or a dashboard with today's numbers. For that, the page gets a name and parameters, and it becomes a function that returns the page as HTML. A web server written in Salam calls it for each request. The first lesson of this part explains these pages in detail; here is the smallest complete program, which would serve the landing page with a name and a plan taken from the address.

web-project-serve.salam
import net.http
import net.router

page Welcome(name: str, plan: str):
    title = "Welcome, " + name
    font = system, sans
    margin = 0
    background = "#fafaf9"
    main:
        max width = 30rem
        margin = 48px, auto
        padding = 28
        background = "white"
        radius = 16
        heading:
            size = 1
            content = "Welcome, " + name
        end
        paragraph:
            content = "Your " + plan + " plan starts on Monday."
        end
    end
end

func home(ctx: i64):
    mut name := http.Query(ctx, "name")
    mut plan := http.Query(ctx, "plan")
    if name == "":
        name = "friend"
    end
    if plan == "":
        plan = "Solo"
    end
    http.Html(ctx, Welcome(name, plan))
end

func main:
    mut r := router.NewRouter()
    router.Get(r, "/", home)
    mut s := http.NewServer(8080)
    http.Use(s, r)
    http.Run(s)
end

The program starts a server and has no output, so it is only checked here. Run it, open http://localhost:8080/?name=Ada&plan=Duo and you get the page. Text that arrives in a parameter is escaped for you, so a visitor who sends ?name=<b> sees the characters and no markup. For the server side, the net.http and net.router packages handle requests, query strings and answers, and net.http.validate checks the form data that project 3 collected in the browser. A static page like projects 1 to 6 is also complete as it is: salam page build page.salam --inline writes it to a single HTML file that any web host will serve. To serve the site, run several domains, connect PHP and deploy, the salam serve web server lesson covers all of it.

Routes: one page, many screens

A single-page app has one HTML file and many screens: /, /users/3, /settings. The pages/ folder next to main.salam is the route table: one file per screen, and the file name is the path. An Outlet element shows the component of the current path. Changing the route does not reload the page; it is a state change that redraws only the outlet.

main.salam
pages/
  index.salam           /
  login.salam           /login
  admin.salam           /admin
  users/
    [id].salam          /users/:id
  _404.salam            every other path

Each file declares exactly one pub component. page.Guard(condition), when the page has one, is the first line of its body, and the title setting comes after it.

mut signed_in := false

page:
    nav:
        link: to = "/" content = "Home" end
        link: to = "/users/1" content = "User 1" end
    end
    Outlet: end
end
pub component User(id: int):
    title = "User " + id
    heading: content = "User " + id end
    button: click = (): page.route.GoTo("/users/" + (id + 1)) end content = "Next" end
end
pub component Admin:
    page.Guard(signed_in)
    paragraph: content = "Admin area" end
end
pub component Login:
    button:
        click = ():
            signed_in = true
            page.route.Redirect("/admin")
        end
        content = "Sign in"
    end
end
  • A file or folder name is a literal segment, [id] is one segment that fills the parameter id, [[id]] is one that may be missing, and [...rest] takes the rest of the path. The most specific path wins, so users/new.salam beats users/[id].salam. _404.salam catches every other path, and index.salam is its folder itself.
  • A :name segment fills the component parameter with the same name. An int parameter only matches a whole number that fits in an int (digits with an optional minus sign), so /users/abc falls to _404.salam.
  • page.Guard(condition) lets the route match only while the condition is true. It must be the first line of the component, above every setting, style and element, and never inside an if. A _layout.salam in a folder gives the same guard to every page below it. When it is false the route is skipped and the next one that matches is shown, usually _404.salam, while the address stays the same. Guards are checked again after every state change, so signing out leaves a guarded screen at once. To send the visitor somewhere else, call page.route.Redirect(path) in code, as Login does after signing in. title sets the document title.
  • A file name uses ASCII letters, digits, - and _. For a path in another script, set route = "/users/:id" (any text, here a Persian one is the usual case) at the top of the component body: it replaces the path taken from the file name. The Persian names are عنوان, مسیر and پیش ساخت (for prerender, see serving) for the settings and صفحه.نگهبان for page.Guard.
  • A _layout.salam is not a route. It declares one pub component with an Outlet, and it wraps every page in its folder and below, from the outside in. Its page.Guard protects the whole folder once. Put the shared navigation in it:
pub component AdminLayout:
    page.Guard(signed_in)
    nav:
        link: to = "/admin/users" content = "Users" end
    end
    Outlet: end
end
  • A mistake in the folder is an error that names the file: E280 when two files give the same route (a.salam and a/index.salam), E281 when [id] has no parameter id in its component, E282 when a route file has no pub component or more than one, E283 when a layout has no Outlet and E284 for a file name that is not valid.
  • link: to = "/path" is a normal link: middle click, open in a new tab and crawlers work, and a plain click changes the route without a reload. The link of the current route gets aria-current="page". A link with url instead of to always loads the page from the server.
  • In code, page.route.GoTo(path) opens a screen, page.route.Redirect(path) opens one in place of the current screen, so Back skips it (good after a sign in), and page.route.Back() and page.route.Forward() move through the history like the browser buttons. page.route.path, page.route.query and page.route.pattern are state you can read anywhere, and page.route.Param("id") and page.route.Query("q") read single values. A relative path in page.route.GoTo is resolved under the current one, so page.route.GoTo("edit") from /users/3 opens /users/3/edit.
  • The Persian names are نمای مسیر, مقصد, صفحه.مسیر.برو, صفحه.مسیر.هدایت, صفحه.مسیر.عقب, صفحه.مسیر.جلو, صفحه.مسیر, صفحه.مسیر.پارامتر and صفحه.مسیر.مقدار پرسمان.

There are two modes. The default, mode = "history" (a setting of the page: block), uses clean paths such as /users/3. A visitor can open such a path directly, so the server must answer every page path with the app: salam serve does that on its own for a page built in this mode, salam web writes an .htaccess file for Apache next to the page, and nginx needs try_files $uri /index.html; (see serving a single-page app). mode = "hash" keeps the route after a #, as in /#/users/3, and works on any static host with no server setting at all. base = "/app" serves the app under a sub path.

A page project with a pages/ folder can also be served as finished HTML. salam page build --ssr=dist writes dist/server, a native program, and dist/public with the script, the style sheet and a copy of every page that needs no parameter. Start it with PORT=8080 dist/server (HOST defaults to 127.0.0.1, PORT=0 picks a free port). For each request the server finds the route, checks the guards (a page whose guard fails is skipped like an unknown path), builds the layouts and the page into HTML with the same code the browser would run, and answers 404 with your _404 page for an unknown path. Text that comes from the address is escaped in the page and in the state block <script type="application/json" id="__salam">. salam serve --render does the build, runs the server and rebuilds when you save a file. The server rendering lesson has the details and explains hydration.

Several files: the components folder

A page project follows one convention: components/ holds the pub component of the project, pages/ holds the routes, and everything else is included explicitly. When the entry file is main.salam and a folder named components/ sits next to it, the compiler reads every .salam file in it (subfolders too, in sorted order) and each pub component in them can be used from any file with no include. A component without pub stays private to its own file (using it elsewhere is E232). A file in components/ that declares no component is ignored.

main.salam                  page: Card: title = "hi" end end
pages/index.salam           pub component Home: ... end
components/card.salam       pub component Card(title): ... Badge: ... end
components/shop/badge.salam pub component Badge(label): ... end
lib/format.salam            reached only with include = "lib/format.salam"

Two pub component with the same name among components/, main.salam and the route files in pages/ are error E291, and the message names both files and lines. Because the names are shared, an English name must be written in PascalCase: a capital first letter and no _, as in PriceCard. price_card or priceCard is error E290 and the message shows the spelling it wants. Persian names are exempt from the rule.

  • Without a components/ folder nothing is imported by name. A component in any other file, for example ui/card.salam, is used only with include = "ui/card.salam". If you use it without that line, the unknown element error says that a pub component with that name exists outside components/: move it there or include it.
  • Not read inside components/: hidden folders, node_modules, build, dist, out, target, vendor, tests, test and __tests__, any folder that has its own main.salam (another project), and files ending in _test.salam or .test.salam. The pages/ folder is route files only.
  • Building one file that is not named main.salam (salam page build card.salam), the playground and layouts used from a Salam program work as before: nothing is imported unless you write include, and a repeated pub name only gives a warning.
