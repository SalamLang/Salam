result

Returning either a value or an error from a function, instead of throwing an exception.

import result
On this page

  3. Collecting every error in a batch
  4. Which tool for which job
  5. Types
  6. Functions

Salam has no exceptions. A function that may fail returns a Result rather than throwing: either Ok with a value, or Err with an explanation of what went wrong. The caller checks both cases with match, and the compiler will not let either be forgotten.

Inside a function that returns a Result itself, the ? operator shortens the work: written after a call, it pulls out the successful value, and on an error returns that error straight away. The enums lesson walks through the pattern step by step.

Use Result when a caller needs to know why something failed. When "nothing there" is a normal answer with no reason attached, such as a lookup that found no match, option is the better fit. When the failure is a bug in the program itself, core.Panic is. Many std packages use a third style, a bool result plus an Error out-parameter, and you can wrap such a call in a Result where that reads better.

Things that catch people out:

  • ? only works when the error types match: inside a function returning Result<int, str>, a call that returns Result<int, int> cannot be passed up with ?. Convert it with a match first.
  • A match without an Err arm does not compile (error E079). Add the arm, or an else arm when you really mean to ignore failures.
  • Expect stops the program with your message only; the error inside the result is not printed. Put what you know into the message.
  • There are no map or and_then helpers. Use ? to chain steps and match to transform a value.

Passing errors up with ?

Real input is checked in several steps, and each step can fail with its own message. Write each step as a small function that returns a Result, then join them with ?. The first step that fails ends the whole chain and its message reaches the caller unchanged, so the top level needs only one match.

result-guide-address.salam
import result
import str

struct Address:
    pub host: str = ""
    pub port: int = 0
end

func parse_port(text: str): result.Result<int, str>:
    n := text.to_int()
    if str.FromInt(n) != text:
        ret result.Result.Err("port is not a number: '" + text + "'")
    end
    if n < 1 or n > 65535:
        ret result.Result.Err("port out of range: " + n)
    end
    ret result.Result.Ok(n)
end

func parse_address(text: str): result.Result<Address, str>:
    colon := str.LastIndex(text, ":")
    if colon <= 0:
        ret result.Result.Err("expected host:port, got '" + text + "'")
    end
    port := parse_port(str.Substr(text, colon + 1, text.len() - colon - 1))?
    ret result.Result.Ok(Address { host = str.Substr(text, 0, colon), port = port })
end

func main:
    each text in ["db.local:5432", "localhost", "cache:99999", "api:http"]:
        match parse_address(text):
            Ok(a): println "connect to", a.host, "on port", a.port end
            Err(e): println "error:", e end
        end
    end
end
Outputconnect to db.local on port 5432 error: expected host:port, got 'localhost' error: port out of range: 99999 error: port is not a number: 'http'

The success value does not have to be a number: here it is a whole Address struct. Note how the message for cache:99999 comes from parse_port even though the caller only called parse_address. The check str.FromInt(n) != text catches text such as http that to_int would quietly read as 0.

An enum as the error type

A string is fine when the error is only shown to a person. When the caller has to react differently to different failures, make the error an enum with data. The compiler then makes every match on it handle every case, and each case carries exactly the details it needs.

result-guide-enum-error.salam
import result

enum LoginError:
    UnknownUser(name: str)
    WrongPassword(tries_left: int)
    Locked
end

func login(name: str, password: str, failures: int): result.Result<str, LoginError>:
    if name != "sara":
        ret result.Result.Err(LoginError.UnknownUser(name))
    end
    if failures >= 3:
        ret result.Result.Err(LoginError.Locked)
    end
    if password != "s3cret":
        ret result.Result.Err(LoginError.WrongPassword(2 - failures))
    end
    ret result.Result.Ok("token-for-" + name)
end

func explain(e: LoginError): str:
    ret match e:
        UnknownUser(n): "no account called " + n end
        WrongPassword(left): "wrong password, " + left + " tries left" end
        Locked: "account locked, contact support" end
    end
end

func main:
    attempts := [login("sara", "s3cret", 0), login("reza", "x", 0), login("sara", "guess", 1), login("sara", "s3cret", 3)]
    each r in attempts:
        match r:
            Ok(token): println "welcome,", token end
            Err(e): println explain(e) end
        end
    end
end
Outputwelcome, token-for-sara no account called reza wrong password, 1 tries left account locked, contact support

The function that builds the error no longer decides the wording, which keeps the message in one place and makes it easy to translate. A web handler could map UnknownUser and WrongPassword to 401 and Locked to 423 with the same match.

A naming rule worth knowing: the enum name and the names of its data fields are single words, while members may have several words when the members are separated by commas and no word after the first is a keyword. In Persian code this is why a member is called رمز اشتباه rather than using the keyword نادرست.

Collecting every error in a batch

? stops at the first failure, which is right for one request but wrong for an import of many rows, where the user wants to see every bad row at once. Loop over the input, match each result, add up the good values and keep the messages of the bad ones.

result-guide-batch.salam
import result

func parse_score(text: str): result.Result<int, str>:
    n := text.to_int()
    if n == 0 and text != "0":
        ret result.Result.Err("'" + text + "' is not a number")
    end
    if n < 0 or n > 20:
        ret result.Result.Err(text + " is outside 0..20")
    end
    ret result.Result.Ok(n)
end

func main:
    rows := ["18", "abc", "20", "25", "0", "14"]
    mut total := 0
    mut good := 0
    mut errors := Vector {} as Vector<str>
    defer errors.free()
    each i, text in rows:
        match parse_score(text):
            Ok(n):
                total += n
                good += 1
            end
            Err(e): errors.push("row " + (i + 1) + ": " + e) end
        end
    end
    println good, "valid rows, average", total / good
    each e in errors:
        println e
    end
end
Output4 valid rows, average 13 row 2: 'abc' is not a number row 4: 25 is outside 0..20

Put the row number into each message while you still know it. When a default value is good enough and the reason does not matter, UnwrapOr is shorter than a match; IsOk and IsErr answer a yes or no question without taking the value out.

Which tool for which job

You want toWrite
Handle both casesmatch r: Ok(v): ... end Err(e): ... end end
Pass the error to your own callerv := step()? inside a function that returns a Result
Use a fallback valueresult.UnwrapOr(r, fallback)
Only ask whether it workedresult.IsOk(r) or result.IsErr(r)
Stop the program if it failedresult.Expect(r, "message"), only where failure is a bug

Types

Result

enum Result<T, E>:
    Ok(value: T)
    Err(error: E)
end
A generic enum with two cases. T is the type of the successful value and E the type of the error, which is most often a str. Build one with result.Result.Ok(...) or result.Result.Err(...).
NameTypeDescription
Ok(value: T)The work succeeded, and the value is in value.
Err(error: E)The work did not happen, and the explanation is in error.
result-Result.salam
import result

func age(text: str): result.Result<int, str>:
    n := text.to_int()
    if n <= 0 or n > 150:
        ret result.Result.Err("not a valid age: " + text)
    end
    ret result.Result.Ok(n)
end

func main:
    each text in ["30", "200"]:
        r := age(text)
        println match r:
            Ok(n): "age accepted: " + n end
            Err(message): message end
        end
    end
end
Outputage accepted: 30 not a valid age: 200

Functions

IsOk

func IsOk<T, E>(r: Result<T, E>): bool
Returns true when the result is Ok.
result-IsOk.salam
import result

func divide(a: int, b: int): result.Result<int, str>:
    if b == 0:
        ret result.Result.Err("division by zero")
    end
    ret result.Result.Ok(a / b)
end

func main:
    good := divide(9, 3)
    bad := divide(1, 0)
    println result.IsOk(good), result.IsErr(good)
    println result.IsOk(bad), result.IsErr(bad)
    println result.UnwrapOr(good, -1), result.UnwrapOr(bad, -1)
    println result.Expect(good, "this division should have worked")
end
Outputtrue false false true 3 -1 3

IsErr

func IsErr<T, E>(r: Result<T, E>): bool
Returns true when the result is Err.

The example for this item is shown with the ones above: result-IsOk.salam

UnwrapOr

func UnwrapOr<T, E>(r: Result<T, E>, fallback: T): T
Returns the value when the result succeeded, and the default you supplied when it did not.

The example for this item is shown with the ones above: result-IsOk.salam

Expect

func Expect<T, E>(r: Result<T, E>, msg: str): T
Returns the value of a successful result. If the result is an error, the program stops with a panic carrying the message you gave; the error value itself is not shown. Use it only where an error would be a bug.

The example for this item is shown with the ones above: result-IsOk.salam
