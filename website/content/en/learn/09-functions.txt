<h2 id="define">Declaring and calling</h2>
<p>A function is declared as <code>func name(parameters): result type:</code> and its body ends with <code>end</code>. Every parameter is written as <code>name: type</code>, and <code>ret</code> hands the result back to the caller. A function that gives nothing back simply leaves out the result type.</p>
{{example.fn-basics}}
<p>The order of functions in a file does not matter: <code>main</code> may call a function that is declared further down. A call always needs its parentheses, even when there are no arguments.</p>

<h2 id="ret">Returning early</h2>
<p><code>ret</code> leaves the function at once, wherever it stands. That lets you deal with the bad cases first, each with its own <code>ret</code>, and keep the normal path at the bottom without deep nesting. In a function with no result type, a bare <code>ret</code> just leaves.</p>
{{example.fn-early-return}}
<div class="note"><p>A function with a result type must reach a <code>ret</code> on every path. If it can fall off its end, the compiler stops with E071 and asks for a final <code>ret</code>.</p></div>

<h2 id="defaults">Default values</h2>
<p>A parameter with a default value is optional at the call. Put such parameters after the ones without a default.</p>
{{example.fn-params}}
<p>A default value must be a constant or built from globals; it cannot refer to another parameter, so <code>func box(w: int, h: int = w)</code> fails with "unknown identifier". Write an overload instead (see below). Salam has no named arguments: the arguments always go in the order of the parameters.</p>

<h2 id="infer">Inferring the result type</h2>
<p>Leave the result type out and Salam works it out from the <code>ret</code> statements. This is handy for short helpers; for a function others will call, writing the type out makes it easier to read.</p>
{{example.fn-infer}}

<h2 id="results">Returning several values</h2>
<p>A function returns one value. When you need to give back more than one, put them in a small struct and return that. The caller reads the parts by name, which is clearer than remembering an order. Structs have a <a href="/learn/structs/">lesson of their own</a>; here all you need is that the fields are marked <code>pub</code> so that code outside the struct can read them.</p>
{{example.fn-results}}

<h2 id="recursion">Recursion</h2>
<p>A function may call itself. Each call gets its own copy of the parameters, and a recursive function always needs a base case, a condition where it returns without calling itself again. Here that is <code>n &lt; 2</code>.</p>
{{example.functions}}
<p>This version of <code>fibonacci</code> is easy to read but slow: every call makes two more, so the work roughly doubles with each step of <code>n</code>. For large inputs, a loop that carries the last two values is far faster. Very deep recursion can also run out of stack, so prefer a loop when the depth grows with the size of the input.</p>

<h2 id="overload">Overloading</h2>
<p>Several functions may share a name as long as their parameters differ, either in type or in number. Salam picks the right one from the arguments at compile time.</p>
{{example.fn-overload}}

<h2 id="names">Multi-word names</h2>
<p>A function name can be several words, so that a call reads like a sentence. Every word is part of the name, so none of them may be a keyword: <code>func print line</code> or <code>func each item</code> is rejected because of <code>print</code> and <code>each</code>.</p>
{{example.fn-multiword}}

<h2 id="ref">Reference parameters</h2>
<p>Parameters are copied by default, so changing one inside the function is invisible outside it. Write <code>&amp;:</code> after the parameter name and the function works on the caller's own variable and can change it. The variable you pass should be declared <code>mut</code>. A reference parameter also saves copying a large struct on every call.</p>
{{example.fn-ref}}
<p>Prefer returning a value when you can: <code>score = next score(score)</code> shows what changes right at the call. Use <code>&amp;:</code> when a function updates something in place, such as a struct or a <code>Vector</code>.</p>

<h2 id="values">Functions as values</h2>
<p>A function can also be handed to another function. The bare name of a named function, without parentheses, is its address in memory, typed <code>i64</code>; that is the form C-style callback registries take. To pass a function to a parameter with a function type such as <code>func (int) int</code>, wrap it in a short anonymous function. The <a href="/learn/lambdas/">next lesson</a> covers both.</p>

<h2 id="main">main and the exit code</h2>
<p><code>main</code> is where the program starts, and what it returns is the program's exit code. Falling off its end, or a bare <code>ret</code>, exits with 0, which means success. <code>ret 1</code> (or any other number) reports a failure to the shell or the script that started the program. Error messages go through <code>printerrln</code>, so they do not mix with the normal output.</p>
{{example.fn-main-exit}}
<p>With 20 ordered and only 12 in stock, the program would print the message to the error stream and exit with 1. The deferred line still runs either way. Calling <code>os.Exit</code> inside <code>main</code> is an error (E109), because it would skip <code>main</code>'s <code>defer</code> statements, while <code>ret</code> runs them. The <a href="/learn/defer/">defer lesson</a> explains those.</p>

<h2 id="rules">Rules of thumb</h2>
<ul>
<li>Give each function one job and a name that says what it does.</li>
<li>Handle the bad cases first, each with an early <code>ret</code>.</li>
<li>Return a struct to give back several values.</li>
<li>Make sure every path of a function with a result type ends in <code>ret</code>.</li>
<li>Report failure from <code>main</code> with <code>ret 1</code>, not with <code>os.Exit</code>.</li>
</ul>
