Because the compiler knows every case, it can tell you when your code forgets one. <h2 id="basic">A plain enum</h2>
<p>Cases are separated by commas and numbered from zero. You can give a case a value of your own, and the cases after it carry on from there. <code>as int</code> gives you the number behind a case.</p>
{{example.enum-values}}
<p><code>.name()</code> gives the name of a case as a string, and <code>.Count()</code> on the enum itself gives the number of cases:</p>
{{example.enum-name}}

<h2 id="match">Enums and match</h2>
<p><code>match</code> on an enum lists the cases by their bare names. It must cover every case or end with <code>else</code>; leave one out and the program does not compile: <code>E080: non-exhaustive match on enum 'Light': missing member Yellow</code>. That check is the main reason to use an enum instead of plain numbers or strings. When you add a case later, the compiler points at every <code>match</code> that has to learn about it.</p>
{{example.enum-state}}
<p>Each function describes one fact about every state, and <code>Light.Count()</code> makes the loop go round exactly once, however many cases there are. A small state machine like this, where each state knows the next one, turns up everywhere: order processing, game turns, connection status.</p>
<div class="note"><p>Write <code>else</code> only when the remaining cases really share one answer. A catch-all <code>else</code> also swallows the cases you add later, and the compiler can no longer remind you about them.</p></div>

<h2 id="fields">Enums in structs and stored values</h2>
<p>An enum is a good type for a struct field with a fixed set of states. Printing the struct shows the field as its number, so use <code>name()</code> when a person will read it.</p>
{{example.enum-order}}
<p>The number is what you store in a file or a database, and <code>code as Status</code> turns it back into a case. That conversion is not checked: <code>9 as Status</code> is accepted even though no case has the value 9, and its <code>name()</code> is an empty string. When the number comes from outside the program, check it first, as <code>status_from</code> does with <code>Status.Count()</code>. When the cases have values of their own, such as <code>Published = 10</code>, compare against those instead.</p>

<h2 id="data">Enums that carry data</h2>
<p>A case can carry named data, such as a radius for a circle. Build one with <code>Shape.Circle(2.0)</code>, and use <code>match</code> to tell the cases apart and pull the data out. A branch may add a condition with <code>if</code>. A guarded branch does not count as covering its case, so keep an unguarded branch for the same case after it.</p>
{{example.enum-data}}
<p>In a pattern, <code>_</code> skips a value you do not need, and <code>Voucher v</code> binds the whole case to one name, so you can read its fields as <code>v.code</code>. Cases with data compare with <code>==</code> on all of their values, and <code>name()</code> and <code>Count()</code> work as they do on a plain enum:</p>
{{example.enum-payment}}
<p>An enum with data needs at least two cases, and its cases cannot also have <code>= value</code>.</p>

<h2 id="generic">Generic enums</h2>
<p>An enum that carries data can be generic too. <code>Maybe&lt;T&gt;</code> either holds a value or holds nothing: a safe way to say "there is no result" without a null.</p>
{{example.enum-generic}}
<p>Type parameters themselves are covered in <a href="/learn/generics/">generics and interfaces</a>.</p>

<h2 id="result">Result and the ? operator</h2>
<p>Salam has no exceptions. The <code>result</code> package provides <code>Result&lt;T, E&gt;</code>, which is either <code>Ok</code> with a value or <code>Err</code> with an error. Inside a function that returns a Result, writing <code>?</code> after a call unwraps the successful value, and on an error returns that error straight away.</p>
{{example.result-try}}
<p>The <code>?</code> has to be the whole value of its statement: <code>x := f()?</code>, <code>x = f()?</code>, <code>f()?</code> or <code>ret f()?</code>. A <code>defer</code> in the function still runs when <code>?</code> returns early.</p>

<h2 id="result-helpers">Working with a Result</h2>
<p>Where the error does not need to travel further, the package has small helpers. <code>result.IsOk</code> and <code>result.IsErr</code> tell you which case you have, <code>result.UnwrapOr(r, fallback)</code> gives the value or a fallback, and <code>result.Expect(r, message)</code> gives the value or stops the program with the message. A Result is an ordinary enum, so <code>match</code> works on it too.</p>
{{example.result-helpers}}
<p>Keep <code>Expect</code> for errors that mean a bug in the program, not for bad input from a user: when it fails, the program ends with <code>salam panic:</code> followed by your message.</p>

<h2 id="rules">Rules of thumb</h2>
<ul>
<li>Use an enum whenever a value is one of a known, fixed list. A string can be misspelled or written in the wrong case (<code>"shipped"</code> where the code expects <code>"Shipped"</code>) without anyone noticing, while a wrong enum case does not compile.</li>
<li>Prefer <code>match</code> without <code>else</code> on your own enums, so the compiler finds every place a new case must be handled.</li>
<li>Check numbers that come from outside the program before converting them with <code>as</code>.</li>
<li>Give each case the data that belongs to it, instead of one struct with fields that are only sometimes used.</li>
<li>Return a <code>Result</code> from functions that can fail, and pass errors up with <code>?</code>.</li>
</ul>
