<h2 id="package">Packages</h2>
<p>A file that begins with <code>package name</code> belongs to that package. Only the functions, constants, types and fields marked <code>pub</code> can be used from outside it; everything else is an internal detail that you are free to change later without breaking anyone. A file without a <code>package</code> line is in the package <code>main</code>.</p>
{{example.pkg-lib}}
<p>This file has no <code>main</code> of its own, so on its own it does not run; it is meant to be included by a program, as in the next section.</p>

<h2 id="include">Including your own files</h2>
<p><code>include name "file.salam"</code> brings in a file of your own project under a short name, and you reach its public members as <code>name.thing</code>. The path is relative to the file that does the including.</p>
{{example.pkg-include}}
<ul>
<li>The name is optional: <code>include "lib/money.salam"</code> is reached as <code>money.Format(...)</code>, after the file name. Give it a name whenever the file name is long or unclear.</li>
<li>A path that starts with <code>@/</code> starts at the project root instead of at the current file, so <code>include "@/lib/money.salam"</code> means the same file from every folder of the project. Build from the project's folder so the root is where you expect it.</li>
<li>Do not start a path with <code>./</code>. The compiler stops with <code>E008: include path './lib/money.salam' must not start with './'</code> and tells you the two spellings it does accept.</li>
<li>A file that cannot be found is an error too (<code>E008: included file not found</code>), never something skipped quietly.</li>
</ul>

<h2 id="import">Importing a library</h2>
<p>Standard library packages are imported by name, without quotes: <code>import str</code>, <code>import os</code>. A package inside another one is written with a dot, as in <code>import encoding.json</code>, and is used through its last part, <code>json.Get(...)</code>. In short: <code>import</code> is for libraries and <code>include</code> is for your own files.</p>
{{example.pkg-import}}
{{example.pkg-dotted}}
<p>An import nobody uses is an error (<code>E082: unused import</code>), so the imports at the top of a file always tell the truth about what the file depends on.</p>

<h2 id="private">pub and private</h2>
<p>Privacy works on struct members too. In this bank package, <code>owner</code> is public but <code>balance</code> is not, so the only way to change a balance is through <code>Deposit</code> and <code>Withdraw</code>, which check every amount. The helper <code>valid_amount</code> is private as well. <code>Account.Open</code> is a static constructor, the usual way to hand out a ready-made value of a type whose fields are private.</p>
{{example.pkg-bank}}
{{example.pkg-private}}
<p>From the program, <code>acc.balance</code> would be refused with <code>E017: field 'balance' is private in struct 'Account' (mark it 'pub')</code>, and calling the private helper with <code>E017: 'valid_amount' is not exported by package 'bank' (mark it 'pub')</code>. Make something <code>pub</code> because other code is meant to use it, not to silence an error: everything public is a promise you have to keep.</p>

<h2 id="folder">A package across a folder</h2>
<p>When a package grows, split it across several files in one folder. Name the folder after the package and give it a file of the same name: <code>shop/shop.salam</code>. Including that file brings in every other <code>.salam</code> file in the folder as part of the same package.</p>
<div class="table-wrap"><table>
<thead><tr><th>File</th><th>What it holds</th></tr></thead>
<tbody>
<tr><td><code>pkg-folder.salam</code></td><td>The program; it includes <code>shop/shop.salam</code></td></tr>
<tr><td><code>shop/shop.salam</code></td><td><code>package shop</code>, <code>import str</code>, the private <code>price_label</code> and the public <code>Welcome</code></td></tr>
<tr><td><code>shop/cart.salam</code></td><td><code>package shop</code> and the public <code>Total</code></td></tr>
</tbody>
</table></div>
{{example.pkg-folder}}
<p>The files of one package share everything: <code>cart.salam</code> calls the private <code>price_label</code> from <code>shop.salam</code>, and uses <code>str</code> without importing it, because the package already imports it once.</p>

<h2 id="bilingual">Names in two languages</h2>
<p>In an English file you write the English names, and a Persian one such as <code>str.طول</code> is an error; a Persian file needs the Persian names. Every standard library function carries both: its Persian name is written next to it in the library source with <code>@fa</code>. Give your own public functions both names the same way, and Persian files can call them too:</p>

<h2 id="order">The order of definitions</h2>
<p>Salam asks for a fixed order of the top-level definitions in every file, so that every file reads the same way, and each step has its own error code:</p>
<ol>
<li><code>package</code></li>
<li>Imports, then includes (an import after an include is <code>E108</code>)</li>
<li>Constants and global variables (<code>E084</code> and <code>E085</code> when they come after a function or type)</li>
<li>Types: structs, enums, interfaces and <code>impl</code> blocks (<code>E087</code> when one comes after a function)</li>
<li>Functions, private ones first and public ones last</li>
</ol>
<p><code>salam format</code> tidies a file up and does much of this moving for you.</p>

<h2 id="project">Laying out a project</h2>
<p><code>salam new shop</code> creates a folder <code>shop</code> with one file, <code>salam.salam</code>, which holds <code>main</code>. Inside that folder a bare <code>salam build</code> builds that file into a program named after the folder. From there a project usually grows like this:</p>
<ul>
<li><code>salam.salam</code> stays short: it reads arguments, calls into the packages and prints results.</li>
<li>Each area of the program gets a folder that is a package: <code>cart/cart.salam</code>, <code>store/store.salam</code>, each split into more files as it grows.</li>
<li>Packages include each other with <code>@/</code> paths, so moving a file does not break the includes inside it.</li>
<li>Each package keeps its public surface small and documents it with <code>@en</code> and <code>@fa</code> names.</li>
</ul>
