<h2 id="why">Why so strict?</h2>
<p>Every error the compiler catches is an error that never reaches a user. That is why Salam treats as errors several things that other languages only warn about: a variable nobody reads, a <code>mut</code> that never changes, a branch that can never run. Warnings tend to pile up and get ignored; an error is fixed on the spot, so a Salam program that compiles has no such leftovers in it.</p>

<h2 id="read">Reading an error</h2>
<p>A typical message looks like this:</p>
<p><code>[SEMANTIC][ERROR] E013: cannot reassign immutable variable 'total'; declare it 'mut' to reassign it, or assign to its elements or fields instead (app.salam:3:5)</code></p>
<ul>
<li><code>E013</code> is the error code. It is the same in English and Persian, so it is the thing to search for.</li>
<li>Then comes the problem, and after the semicolon the usual fix. Read the message to the end; the fix is often all you need.</li>
<li>The end of the line gives the file, line and column: line 3, column 5 of <code>app.salam</code>.</li>
</ul>
<p>Mistakes in the shape of the code, such as a missing <code>end</code> or a word that is not Salam, are reported by the parser instead. Those show the line itself with a caret under the spot, and often a <code>help:</code> line, for example <code>error: '&amp;&amp;' is not a Salam operator; write 'and'</code>. A Persian file gets its messages in Persian.</p>
<p>Fix the first error first. One mistake can cause others further down: misspell a name, and the compiler reports both the unknown name (<code>E001</code>) and the variable you meant, which is now unused (<code>E059</code>).</p>

<h2 id="unused">Nothing unused</h2>
<p>A variable, parameter, private function or import that nothing uses is an error: <code>E059</code>, <code>E062</code>, <code>E066</code> and <code>E082</code>. Usually the right fix is to delete it, or to notice that you forgot to use it. Starting the name with <code>_</code> silences the error, but keep that for the one real case: a signature you do not control. Here every handler must take a user and a text, and <code>Shout</code> has no use for the user:</p>
{{example.rules-unused}}
<p>Without the <code>_</code>, the compiler would say <code>E062: unused parameter 'user'</code>, and its message itself says to use <code>_</code> only when the signature is fixed.</p>

<h2 id="mutability">mut only where things change</h2>
<p>A variable made with <code>:=</code> cannot be reassigned (<code>E013</code>). Add <code>mut</code> when it must change, and only then: a <code>mut</code> that never changes is also an error (<code>E069</code>). Adding to a Vector or a HashMap changes the data it points to, not the variable, so <code>push</code> works without <code>mut</code>. A value fixed for the whole program is a <code>const</code>.</p>
{{example.rules-mut}}

<h2 id="types">Types are never guessed</h2>
<p>Salam does not convert between types behind your back. Putting a <code>str</code> where an <code>int</code> belongs is <code>E002</code> in an assignment and <code>E012</code> in a call, and a condition must be a real <code>bool</code>: <code>if items:</code> with a number is <code>E021</code>, so write <code>if items &gt; 0:</code>. The two branches of <code>?:</code> must have the same type. Convert explicitly with <code>as</code>, but not when the value already has that type: <code>n as int</code> on an <code>int</code> is a useless cast, <code>E093</code>.</p>

<h2 id="flow">Every path is checked</h2>
<p>The compiler follows every path through a function. A function that returns a value must return it on every path (<code>E071: function 'sign' can fall off its end</code>), a <code>match</code> on an enum must cover every member or have an <code>else</code> (<code>E080</code> names the missing ones), and code after a <code>ret</code> can never run (<code>E070</code>). The same goes for a condition that is always false (<code>E068</code>), an empty <code>if</code> branch (<code>E060</code>) and a statement whose value is thrown away, like <code>n + 1</code> on its own line (<code>E110</code>).</p>
{{example.rules-flow}}
<p>When a new member is added to <code>Light</code> later, every <code>match</code> that does not handle it stops compiling, which is exactly where you need to look.</p>

<h2 id="exit">No exceptions, and main returns the exit code</h2>
<p>Salam has no exceptions and no try and catch. A function that can fail says so in what it returns: a <code>bool</code> with the result in a <code>&amp;:</code> parameter, as below, or a <code>Result</code> enum with the <code>?</code> operator from the <a href="/learn/enums/">enums lesson</a>. The caller checks it right away.</p>
{{example.rules-exit}}
<p>The value <code>main</code> returns is the program's exit code: <code>ret 1</code> reports failure to the shell, and no <code>ret</code> means 0. Calling <code>os.Exit</code> inside <code>main</code> is <code>E109</code>, because it would skip the cleanup that <code>main</code> deferred.</p>

<p>A few mistakes are caught by the parser and have no code: <code>while</code> (the loop is <code>until</code>, see the <a href="/learn/loops/">loops lesson</a>), <code>&amp;&amp;</code> and <code>||</code> (write <code>and</code> and <code>or</code>), a typed declaration like <code>n: int = 2</code> (write <code>n := 2</code>), and a reserved word used as a name, such as a parameter called <code>to</code>.</p>

<h2 id="tips">A few hints</h2>
<ul>
<li>Fix the first message first, then build again; many of the later ones disappear with it.</li>
<li>Read every message to the end. The part after the semicolon is usually the fix.</li>
<li>Do not reach for <code>_</code> or <code>pub</code> to make an error go away. The compiler is pointing at code that is dead, unfinished or in the wrong place.</li>
<li>Search the code, such as <code>E071</code>, rather than the wording: the code is the same in every language.</li>
<li>Run <code>salam format</code> before chasing order errors; it moves many definitions into place for you.</li>
</ul>
