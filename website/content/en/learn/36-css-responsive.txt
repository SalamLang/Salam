<h2 id="viewport">One page, many screens</h2>
<p>A phone is a small screen with a lot of pixels, and browsers hide that from you with the <em>viewport</em>: the visible area of the page, measured in CSS pixels. Without a hint, a phone pretends to be about 980 pixels wide and shrinks the page to fit. Salam writes the hint for you: every page it builds contains <code>&lt;meta name="viewport" content="width=device-width, initial-scale=1"&gt;</code>, so the page is laid out at the real width of the screen.</p>
<p>That leaves one job to you: do not fix the size of things. A <code>width = 800</code> is fine on a laptop and wider than the whole phone. Prefer sizes that bend. Four tools cover most of the need. <code>max width</code> sets a limit and lets the box shrink below it. A percentage is a share of the parent. The unit <code>vw</code> is one percent of the viewport width. And <code>clamp(min, preferred, max)</code> picks the preferred value but never goes below the minimum or above the maximum, which makes it ideal for font sizes and padding. <code>min()</code> and <code>max()</code> work the same way with a list of values, and <code>width = "min(100%, 24rem)"</code> means "as wide as the parent, but no more than 24rem".</p>
{{example.web-resp-fluid}}
<p>The line <code>global: box sizing = "border-box"</code> styles every element so that padding and borders count inside the width. Without it the box with <code>max width = "40rem"</code> would be wider than 40rem by its padding, and a box at <code>width = "100%"</code> with padding would overflow its parent. It is the first rule most stylesheets contain.</p>
<div class="note"><p>If your page scrolls sideways on a phone, something has a fixed width, or a long word or a wide image has no <code>max width</code>. Narrow the browser window to find it.</p></div>

<h2 id="media-element">Media queries on one element</h2>
<p>Fluid sizes are not enough when the layout itself has to change: three columns on a laptop, one column on a phone. For that CSS has <em>media queries</em>. In Salam the <code>media</code> element is a child of the element you want to change, and its <code>condition</code> attribute is the query in parentheses. The style properties you write inside <code>media</code> apply to the parent, and only while the condition is true.</p>
{{example.web-resp-media}}
<p>The example reads: this grid has three equal columns and a grey background, and when the viewport is at most 480 pixels wide it has one column and a yellow background. Everything outside the <code>media</code> element is the normal case, and the <code>media</code> element lists only what is different.</p>
<p>Which direction to write the queries in is a matter of habit. <em>Mobile first</em> means the normal rules are for a phone and queries with <code>min-width</code> add the extra layout for larger screens. <em>Desktop first</em> does the opposite with <code>max-width</code>, as above. Mobile first usually means less code, because small screens need the simplest layout. A condition can combine tests with <code>and</code>, and a comma means "or": <code>(min-width: 600px) and (max-width: 900px)</code> is a range, and <code>(orientation: landscape), (min-width: 1200px)</code> is either one. Besides widths you can ask about <code>orientation</code>, the pointer (<code>(pointer: coarse)</code> is a finger), and whether the device can hover.</p>
<pre class="code snip" dir="ltr"><code>button:
    padding = "6 12"
    content = "Buy"
    media: condition = "(hover: none)" padding = "14 22" font size = 18 end
end</code></pre>
<p>A touch screen has no hover, and a finger is less exact than a mouse, so the rule above makes the button bigger there. Test for the ability (<code>hover: none</code>, <code>pointer: coarse</code>) and not for the device name or the width: a tablet with a keyboard and a small laptop window are both real.</p>

<h2 id="page-queries">Queries for the whole page</h2>
<p>A <code>media</code> element styles its parent. Rules for the whole page, such as colors for dark mode or what to hide on paper, are raw CSS and go into a <code>style</code> element, whose <code>content</code> is a CSS string. Most users choose dark mode in their system settings, and a page can read the choice with the <code>prefers-color-scheme</code> query. The usual way is to keep the colors in CSS custom properties, which are names that start with two hyphens and are read with <code>var()</code>, and to swap their values in the query. Then every rule that uses them follows without being written twice.</p>
{{example.web-resp-dark}}
<p>The <code>color scheme</code> property, here <code>color-scheme: light dark</code> on <code>:root</code>, tells the browser that the page can do both. The browser then draws its own parts, form controls, scrollbars and the default page color, in the matching colors. Without it a dark page still has bright scrollbars and white inputs.</p>
<p>Other queries you will use are <code>prefers-reduced-motion: reduce</code>, for people who get ill from motion and who ask their system to cut it (the next lesson uses it), <code>prefers-contrast: more</code>, and <code>print</code>, for paper. Salam's <code>style</code> element also has a <code>media</code> attribute that wraps its CSS in a query: <code>style: media = "print" content = "..." end</code>.</p>
<div class="note"><p>A <code>style</code> element with a <code>media</code> attribute is written into the page before all other rules, so it loses against an equally specific rule that comes later. Use it for rules that only add or hide, and use <code>!important</code> in print rules for that reason. When you need to override a normal rule, as in dark mode, write the <code>@media</code> block inside the same <code>content</code> string, after the normal rule.</p></div>

<h2 id="container-queries">Container queries</h2>
<p>A viewport query asks about the whole window, but a product card does not know where it will be placed. In a wide main column it can lay out its picture and text side by side, and in a narrow sidebar it must stack them, whatever the window is. A <em>container query</em> asks about the size of the nearest ancestor that was declared a container. <code>container type = "inline-size"</code> makes an element a container for queries about its width, <code>container name</code> gives it a name, and <code>container</code> sets both in the form <code>name / type</code>. The query is raw CSS, because it is a rule block like a media query: <code>@container name (min-width: 22rem) { ... }</code>.</p>
{{example.web-resp-container}}
<p>The same card, <code>.item</code>, sits in two containers. In the 200 pixel one it stacks, and in the 380 pixel one it is a row, with no knowledge of the window. If you narrow the window until the second container itself shrinks below 22rem, it stacks too. A container cannot be styled by its own query, only its descendants can, and an <code>inline-size</code> container cannot take its width from its content, so give it a width or let it fill its parent.</p>

<h2 id="states">Hover, focus and active</h2>
<p>Elements change look as the user acts on them. Any style property can be written with a state in front of it, and the property then applies only in that state. <code>hover</code> is while the pointer is over the element. <code>focus</code> is while the element receives the keyboard: a link, a button or an input that was reached with Tab or clicked. <code>active</code> is the moment it is pressed. In Persian files the words are <code>اشاره</code>, <code>تمرکز</code> and <code>فشردن</code>. Combine them with <code>transition</code> (the next lesson) for a smooth change.</p>
{{example.web-resp-states}}
<p>Hover is a convenience and never a requirement. A touch screen has no hover, and a keyboard user never hovers, so anything that appears on hover must also be reachable by focus, and a button must look clickable without a mouse over it. Use <code>cursor = pointer</code> on clickable things so the mouse tells the same story.</p>
<p>Focus deserves care, because it is how keyboard users see where they are. Never write <code>outline = none</code> on its own: that deletes the only marker. If you remove the default outline, replace it with something at least as visible, such as a thicker ring, a shadow or a changed border, as the next example does for the input. The pseudo-class <code>:focus-visible</code> is an even better trigger for a ring, since it is true when the browser thinks the focus should be shown, which is always for the keyboard and rarely for a mouse click. The states above cover only five names, so any other pseudo-class, such as <code>:focus-visible</code>, <code>:disabled</code> or <code>:first-child</code>, goes into a <code>global</code> rule with a <code>selector</code>.</p>
{{example.web-resp-focus}}
<p>Press Tab in the preview to move from the input to the button and the link. Each one gets a visible marker, and the input also gets a ring from <code>focus box shadow</code>. An <code>outline</code>, unlike a border, takes no room, so showing it never moves the layout.</p>

<h2 id="generated">Generated content</h2>
<p>CSS can create a piece of content that is not in the page: <code>before</code> puts it in front of an element's content and <code>after</code> behind it. In Salam they are state prefixes like <code>hover</code>, and the text is set with <code>before content</code> or <code>after content</code>. The generated piece can have its own color, size and anything else: <code>before color = "#15803d"</code>. It is part of the look, not of the page: screen readers may or may not read it, search engines do not see it, and the user cannot select it. So use it for decoration such as check marks, arrows, required markers and quote marks, and never for the information itself.</p>
{{example.web-resp-generated}}
<p>The same rule is used for the first two list items, because they have the same style, and the compiler gives them one class. The value of <code>content</code> is a string; to use a CSS keyword such as <code>open-quote</code> or <code>none</code> write <code>before generated content = open-quote</code>. A generated piece shows only when it has a content, even an empty one: <code>after content = ""</code> is the classic <em>clearfix</em>, an empty block after floated children that makes the parent contain them.</p>
<p>The CSS function <code>attr()</code> reads an attribute of the element into the generated text, and it is the base of a tooltip with no extra element. It cannot be written through <code>before content</code>, which always makes a string, so this is a job for a raw <code>style</code>. Salam writes any attribute starting with <code>data</code> as a <code>data-</code> attribute, so <code>data tip = "..."</code> becomes <code>data-tip</code>.</p>
{{example.web-resp-tooltip}}
<p>The tip is hidden with <code>opacity: 0</code> and <code>pointer-events: none</code> so that it never catches the mouse itself, and shown on <code>:hover</code> and on <code>:focus</code>. The <code>tab index = 0</code> on the span makes it reachable by keyboard, so the tip is not for mouse users only.</p>

<h2 id="pointer">Pointer and touch behaviour</h2>
<p>A group of properties does not change how an element looks but how the mouse, the finger or the selection treats it. <code>cursor</code> picks the mouse pointer: <code>pointer</code> is a hand for clickable things, <code>text</code> an I-beam, <code>not-allowed</code> a forbidden sign, <code>grab</code> and <code>grabbing</code> for things you can drag, <code>help</code>, <code>zoom-in</code> and many more, and <code>url(...)</code> with a fallback word gives your own image. <code>user select</code> says whether text can be selected: <code>none</code> for the labels of a button or a game, <code>all</code> to select a whole code or id with one click, and the default <code>auto</code> everywhere else, so that people can copy what they read.</p>
<p><code>pointer events = none</code> makes an element invisible to the pointer: clicks and hovers go to whatever is below. That is how the tooltip above lets the mouse through, and how you put a decoration over a button. It is not a way to disable a button, though, because the keyboard still reaches it; for that use the <code>disabled</code> attribute. <code>resize</code> shows a handle in the corner so the user can drag the box bigger: <code>vertical</code>, <code>horizontal</code> or <code>both</code> on text areas, and on any element that also has an <code>overflow</code> other than visible.</p>
{{example.web-resp-interact}}
<p>The preview has two buttons that run the same function. The second one has <code>pointer events = none</code>, so a click goes through it and the count does not change. Another group is for touch screens. <code>touch action</code> tells the browser which finger gestures it may handle: <code>manipulation</code> allows scrolling and pinch-zoom but removes the double tap zoom and its small delay, and <code>none</code> turns every gesture over to your own script, which a drawing area or a slider needs. <code>tap highlight color</code> sets the color of the flash that some mobile browsers draw on a tapped link, and <code>transparent</code> turns it off. <code>appearance = none</code> removes the system look of a button, checkbox or select, so you can draw your own, and <code>zoom</code> scales an element and its layout box together (<code>zoom = 1.2</code>), unlike <code>transform: scale</code>, which only scales the picture.</p>
<p>Two new properties are not in every browser yet. <code>interactivity = inert</code> makes an element and everything in it unclickable, unfocusable and unselectable, like the <code>inert</code> attribute, and <code>caret animation = manual</code> stops the blinking of the text cursor so that you can animate its color yourself. Test them before you rely on them.</p>

<h2 id="scrolling">Scrolling</h2>
<p>An element with <code>overflow = auto</code> and a fixed height becomes a scroll container, and a few properties shape how it scrolls. <code>scroll behavior = smooth</code> animates jumps to a position, whether from a link to an id, from <code>scrollIntoView</code> or from setting <code>scrollTop</code>, as the button below does. <code>scrollbar width</code> can be <code>thin</code> or <code>none</code>, <code>scrollbar color</code> takes the color of the thumb and then the track, and <code>scrollbar gutter = stable</code> keeps room for the bar even when it is not needed, so the content does not jump sideways when a long text makes it appear.</p>
<p>When you scroll to the end of an inner box, browsers keep going and scroll the page behind it. That is called scroll chaining, and <code>overscroll behavior = contain</code> stops it at the edge of the box, which suits menus, chat windows and modals. <code>none</code> also turns off the bounce and the pull to refresh. The versions <code>overscroll behavior x</code> and <code>y</code> are for the physical axes and <code>block</code> and <code>inline</code> follow the writing direction.</p>
{{example.web-resp-scroll}}
<div class="note"><p>Smooth scrolling is motion. People who asked the system to reduce motion should get an instant jump, so wrap it: write the <code>scroll-behavior: smooth</code> rule in a <code>@media (prefers-reduced-motion: no-preference)</code> block. The <a href="/learn/css-motion/">motion lesson</a> does the same for animations.</p></div>

<h2 id="print">Paper and special modes</h2>
<p>People do print pages: tickets, invoices, recipes. A <code>style</code> with <code>media = "print"</code> holds the rules that apply only on paper. Hide the navigation and the buttons, use black text, and decide where pages break. <code>page break before</code> and <code>page break after</code> take <code>always</code> to force a new sheet and <code>avoid</code> to keep the element with its neighbour, and <code>page break inside = avoid</code> keeps a table row or a card from being cut in two. <code>page</code> gives an element a named page type that an <code>@page</code> rule can size or rotate, for example one landscape sheet for a wide table.</p>
{{example.web-resp-print}}
<p>Browsers normally drop background colors when printing, to save ink. <code>print color adjust = exact</code> asks them to keep the colors of this element, which matters for a banner or a chart. Use your browser's print preview to see the paper version of the page above, or in the browser tools emulate the <code>print</code> media.</p>
<p>Two more properties deal with devices that change your colors or sizes. In the high contrast mode of an operating system, browsers replace your colors with the user's own, and <code>forced color adjust = none</code> opts an element out of it. Do that only for something like a color swatch whose color is its meaning. On phones, the browser may enlarge text in a page it thinks is hard to read, and <code>text size adjust = "100%"</code> or <code>none</code> keeps the sizes you set.</p>

<h2 id="practice">Try it yourself</h2>
<ul>
<li>Make a page with a header, a sidebar and a main part in a grid. At 700 pixels and below, use a <code>media</code> element to stack them in one column, and check it by dragging the window narrower.</li>
<li>Give a button a <code>hover</code> and a <code>focus</code> style, then put <code>outline = none</code> on it and press Tab. Can you still see where you are? Put a visible replacement back.</li>
<li>Add a dark mode to one of your pages with custom properties and <code>prefers-color-scheme</code>, then switch your system between light and dark to see it change.</li>
<li>Write a print rule that hides every navigation link and starts each <code>h2</code> on a new sheet, and look at it in the print preview.</li>
</ul>
