<h2 id="transitions">Transitions</h2>
<p>Without a transition, a property changes in one frame: a hovered card is suddenly lower, a button is suddenly red. A <em>transition</em> tells the browser to move from the old value to the new one over some time. It runs whenever the value changes, whatever the cause: a hover, a focus, a class that a script toggles. The <code>transition</code> property is a shorthand for four things in this order: the property to animate, the duration, the timing function and the delay. Several transitions are separated by commas.</p>
{{example.web-motion-hover}}
<p>The card moves and its shadow grows, each over 200 milliseconds with <code>ease-out</code>, which starts fast and ends gently. Put the <code>transition</code> on the normal state and not on the <code>hover</code> state: then the card also glides back when the pointer leaves. The longhands set one part each: <code>transition property</code> names the properties (<code>all</code> means every one, which is convenient and wasteful, so list the ones you mean), <code>transition duration</code> is a time such as <code>200ms</code> or <code>0.3s</code>, <code>transition delay</code> waits before it starts, and <code>transition timing function</code> is the speed curve.</p>
<p>The curve matters more than most people expect. <code>linear</code> is a constant speed and feels mechanical. <code>ease</code> is the default, <code>ease-in</code> starts slowly, <code>ease-out</code> ends slowly and suits things that arrive, and <code>ease-in-out</code> does both. <code>cubic-bezier(x1, y1, x2, y2)</code> draws your own curve, and when y goes above 1 or below 0 the movement overshoots and settles back. <code>steps(n)</code> moves in n jumps, like a clock hand, and is the base of sprite animations. Press Run to see five of them side by side.</p>
{{example.web-motion-easing}}
<p>Only properties with a value in between can transition: colors, lengths, opacity, transforms and so on. A switch from <code>display: none</code> to <code>block</code> has nothing in between, so by default it happens at once. <code>transition behavior = "allow-discrete"</code> lets such properties join a transition, so the change happens at the right end of it, and together with the raw <code>@starting-style</code> rule it lets an element fade in when it first appears.</p>
<div class="note"><p>A transition needs two different values. If an element is created already in its final state, nothing moves. And when you give only the hover state a transition, the way back is instant, which is a common reason for a half finished feeling.</p></div>

<h2 id="transforms">Transforms</h2>
<p><code>transform</code> moves, turns, scales and skews an element after the layout is done. It takes one or more functions: <code>translate(x, y)</code> moves, <code>rotate(angle)</code> turns by degrees (<code>45deg</code>) or turns (<code>0.25turn</code>), <code>scale(n)</code> multiplies the size, <code>skew(x, y)</code> slants it, and <code>matrix(a, b, c, d, e, f)</code> is all of them as numbers. The functions apply from the right to the left. In <code>translate(100px) rotate(45deg)</code> the element is turned first and then moved 100 pixels to the right, and in <code>rotate(45deg) translate(100px)</code> it is moved along its own, already turned axis, so it ends up diagonally. Swap the functions and you get another picture.</p>
{{example.web-motion-transform}}
<p>A transformed element keeps its place in the layout: its neighbours do not move, and the picture of the element is drawn somewhere else. That is exactly why transforms are the best tool for animation. The turn happens around the middle of the element unless <code>transform origin</code> says otherwise: the tile called origin turns around its top left corner. <code>transform box</code> chooses the box that the origin is measured in, which matters for SVG pictures, where <code>fill-box</code> means the element's own shape.</p>
<p>The last tile uses the three individual properties, <code>translate</code>, <code>rotate</code> and <code>scale</code>. They do what the functions do, and apply in that order before <code>transform</code>. Their use is that one animation can change <code>rotate</code> while a hover changes <code>scale</code>, and neither overwrites the other, which happens when both write the same <code>transform</code>.</p>

<h2 id="three-d">Perspective and 3D</h2>
<p>Add a third dimension and you can turn a card over. <code>perspective</code> on the parent says how far the viewer is from the page, in pixels: a small number like 300 gives a strong, dramatic depth and a large one a mild depth. <code>perspective origin</code> is where the viewer's eye is, by default the middle. A child is then turned with <code>rotateX</code> or <code>rotateY</code> around the horizontal or vertical axis. For the faces of a card to be two real sides, the turning element needs <code>transform style = "preserve-3d"</code>, which keeps its children in the same 3D space instead of flattening them into its own plane, and each face needs <code>backface visibility = hidden</code>, which hides a face while its back is toward you.</p>
{{example.web-motion-flip}}
<p>Click the card. The front is a normal face, and the back is turned half way round in advance with <code>rotateY(180deg)</code>, so when the whole card turns it comes to the front. A button makes the card reachable by keyboard and screen readers. The handler changes the <code>transform</code> by script, because the state (turned or not) lives in a variable, and the <code>transition</code> does the movement.</p>
<div class="note"><p>Some properties on the turning element flatten <code>preserve-3d</code> and spoil the effect: <code>overflow</code> other than visible, <code>opacity</code> below 1 and <code>filter</code>. If the back face is missing, look for one of them.</p></div>

<h2 id="animations">Keyframe animations</h2>
<p>A transition goes from A to B when something changes. An <em>animation</em> runs by itself, as often as you say, and can pass through any number of steps. It has two parts: the <em>keyframes</em>, which say what the element looks like at points of the animation, and the <code>animation</code> properties on the element, which say which keyframes to play and how. The keyframes are written as an <code>@keyframes</code> rule with a name. Salam has no element for it, because a keyframe list is not part of any element: it is one named list for the whole page that any element may use. So it is raw CSS inside a <code>style</code> element.</p>
{{example.web-motion-spin}}
<p>The keyframes say only where to end: <code>to { transform: rotate(1turn) }</code>. The start is the element's normal state. The <code>animation</code> shorthand on the box names the keyframes and then gives the duration, the timing function and the iteration count: one second, constant speed, forever. The same thing, written with the longhands, is easier to read and to change. Each one gets its own line below, and the dots get a different <code>animation delay</code> so that they bounce one after another.</p>
{{example.web-motion-dots}}
<p>The longhands are: <code>animation name</code>, the keyframes to play; <code>animation duration</code>, the time of one round; <code>animation timing function</code>, the curve of each step between keyframes; <code>animation delay</code>, the wait before the start (a negative delay starts the animation already part of the way through); <code>animation iteration count</code>, a number or <code>infinite</code>; and <code>animation direction</code>. Direction <code>alternate</code> plays forward then backward, which is why the dots go up and down and not up and jump down. <code>reverse</code> plays backward and <code>alternate-reverse</code> starts backward.</p>
<p>Before the start and after the end, an element looks as if there were no animation. That is surprising for things that appear. With a delay, the element is first fully visible, then it jumps to the first keyframe, then it animates, and at the end it jumps back. <code>animation fill mode</code> changes this: <code>backwards</code> applies the first keyframe during the delay, <code>forwards</code> keeps the last keyframe after the end, and <code>both</code> does both. The list below uses <code>both</code> so that each row waits invisibly and then stays in place. Replay restarts it.</p>
{{example.web-motion-enter}}
<p>The Replay button adds a class that turns the animation off for one moment and then removes it, because an animation restarts when its name is removed and set again. In the page, <code>.off &gt; div</code> is a raw rule that sets <code>animation: none</code> while the class is on.</p>
<p><code>animation play state</code> is <code>running</code> or <code>paused</code>, and pausing keeps the animation where it is. Anything that moves by itself for more than a few seconds should have a way to stop it, for people who cannot read while something moves. The next page does it with one line of script, <code>dom.SetStyle(el, "animation-play-state", "paused")</code>.</p>
{{example.web-motion-pause}}
<p>One more property, <code>animation composition</code>, matters when an element already has a value and the animation adds to it. <code>replace</code>, the default, ignores the underlying value, <code>add</code> adds the animated value to it, and <code>accumulate</code> does the same for lists such as several transform functions. It lets two animations that both write <code>transform</code> work together.</p>

<h2 id="smooth">Smooth and cheap</h2>
<p>An animation is redrawn about 60 times a second, so each frame has little more than 16 milliseconds. Changing <code>width</code>, <code>height</code>, <code>top</code> or <code>left</code> makes the browser lay out the page again on every frame, and on a phone that stutters. Changing <code>transform</code> and <code>opacity</code> usually does not need layout or even painting: the browser keeps the element as a picture on the graphics card and only moves it. Whenever you can, move things with <code>translate</code> and hide them with <code>opacity</code>.</p>
<p><code>will change</code> is a hint that a property is about to change, such as <code>will change = transform</code>, so the browser can prepare that picture early. Use it on a few elements just before they animate, and remove it afterwards: every element prepared that way costs memory, and a page that says it about everything gets slower.</p>

<h2 id="path">Motion along a path</h2>
<p>A transform can only go in straight lines, and a curve needs a different tool. <code>offset path</code> gives the element a path to follow, most simply <code>path('M 0 40 C 60 -40, 120 120, 200 40')</code> with the commands of an SVG path. <code>offset distance</code> says how far along the path it is, from <code>0%</code> to <code>100%</code>, and that is the value to animate. <code>offset rotate</code> decides the direction it faces: <code>auto</code> follows the path like a car, and an angle keeps it fixed. <code>offset anchor</code> picks the point of the element that sits on the path, and <code>offset position</code> the starting point for shapes that need one. <code>offset</code> sets several of them at once.</p>
{{example.web-motion-path}}
<p>The arrow is a box cut with <code>clip path</code>, and its distance goes from 0 to 100 percent in the keyframes, back and forth with <code>alternate</code>. The turn of the arrow comes from <code>offset rotate = auto</code>.</p>

<h2 id="scroll-driven">Animations driven by scrolling</h2>
<p>An animation normally follows the clock. With <code>animation timeline</code> it can follow something else, such as how far the page is scrolled, with no script at all. <code>scroll()</code> is the progress of the nearest scrolling ancestor, from the top to the end. The animation then plays from start to end as the user scrolls, and the duration plays no role. The bar below grows from nothing to the full width as the page is read.</p>
{{example.web-motion-progress}}
<p><code>view()</code> is the progress of the element itself through the scroller: it starts when the element begins to enter the view and ends when it has left. <code>animation range</code> picks the part that counts, with names such as <code>entry</code> (while it enters), <code>exit</code>, <code>contain</code> and <code>cover</code> (the whole way through), each with percentages. <code>animation range start</code> and <code>end</code> set the two ends one by one. Scroll the page below: each box fades in while it is entering and is finished when it has fully entered.</p>
{{example.web-motion-reveal}}
<p>When two elements are not nested, one can use the timeline of the other by name. <code>scroll timeline name</code> and <code>axis</code> (or the shorthand <code>scroll timeline</code>) give a scroller's progress a name that starts with two hyphens, <code>view timeline name</code>, <code>axis</code> and <code>inset</code> (or <code>view timeline</code>) do the same for the progress of an element, and <code>animation timeline = "--name"</code> uses it. A name is visible only to the descendants of the element that defines it, and <code>timeline scope</code> on a common ancestor lifts that limit. <code>view timeline inset</code> shrinks the visible area by some pixels at the top and bottom.</p>
<div class="note"><p>Scroll driven animations work in Chromium based browsers such as Chrome and Edge, and not in every other browser yet. Without support the animated element simply stays in its normal state, so write them as decoration that the page does not depend on, and keep the content readable without them. Write <code>animation timeline</code> after the <code>animation</code> shorthand, because the shorthand resets it.</p></div>

<h2 id="view-transitions">View transitions</h2>
<p>A <em>view transition</em> animates a change of the page, even a big one, with almost no work from you. A script calls <code>document.startViewTransition(f)</code> with the function that changes the page. The browser takes a picture of the old page, runs <code>f</code>, takes a picture of the new page, and cross fades between them. An element with a <code>view transition name</code> is treated separately: its old and new picture are moved and scaled from the old place and size to the new, so it seems to travel. The name must be unique on the page at that time. <code>view transition class</code> gives several elements one class name, so one rule can style all their transitions.</p>
{{example.web-motion-viewtransition}}
<p>The page changes class on the tile, and the browser animates it from small and green to big and orange. The raw rule on <code>::view-transition-group(tile)</code> makes the movement last 500 milliseconds. The script asks first whether the browser has <code>startViewTransition</code>: in a browser without it the change simply happens at once. View transitions exist in recent Chromium and Safari browsers.</p>

<h2 id="interpolate">Animating to auto</h2>
<p>A panel that opens to the height of its text is the classic case that CSS could not animate: the height <code>auto</code> is not a number, so there was nothing between 0 and auto. <code>interpolate size = "allow-keywords"</code> allows it, for <code>auto</code>, <code>min-content</code>, <code>max-content</code> and <code>fit-content</code>. The property is inherited, so one rule on <code>:root</code> switches it on for the page, as the example does with a <code>global</code> rule. Where the browser does not know it, the panel still opens, but at once.</p>
{{example.web-motion-expand}}

<h2 id="reduced">Reduced motion</h2>
<p>For some people large movement, parallax and spinning cause dizziness and nausea. Operating systems have a setting for it, and browsers pass it to your page as the <code>prefers-reduced-motion</code> media query. Respecting it is part of building a page: it costs a few lines.</p>
{{example.web-motion-reduced}}
<p>The raw rule at the end of the style says that, when the user asked for less motion, every animation and transition is off. It uses <code>!important</code> so that it also wins over the rules the compiler writes later. It is a blunt tool and a good first step. A finer one keeps the meaning and removes the movement: a panel that slid in can fade in, and a long travel can become a short one. The same query decides whether <code>scroll behavior = smooth</code> from the previous lesson should be on at all. Never let anything flash more than three times a second, whatever the user's settings are.</p>
