<h2 id="forms">Giving an element a handler</h2>
<p>A handler is a function the browser calls when something happens to an element. In Salam you attach it with an attribute named after the event: <code>click = ...</code> on a <code>button</code> says what to do when the button is clicked. Events with two words have a space, as everywhere in the page language: <code>double click</code>, <code>mouse move</code>, <code>context menu</code>. The value of the attribute can be written in four ways.</p>
{{example.web-mouse-forms}}
<p>Here is what each form is for.</p>
<ul>
<li><strong>A named function</strong> declared above the <code>page:</code> block. Use it when the code is longer than a line or when two elements share it. The function may have no parameters, as <code>named</code> has, or one parameter of type <code>i64</code>, as <code>with_event</code> has. That parameter receives the event, and you hand it to the helpers that read it: <code>dom.EventX(e)</code> and <code>dom.EventY(e)</code> for the pointer position, <code>dom.EventTarget(e)</code> for the element that was hit, <code>dom.PreventDefault(e)</code> and <code>dom.StopPropagation(e)</code> to change what the browser does next.</li>
<li><strong>A lambda</strong> written inline as <code>(): ... end</code>. It is the shortest form for one or two statements. In a page attribute a lambda takes no parameters, so it cannot see the event. When you need the event, use a named function.</li>
<li><strong>A JavaScript string</strong> such as <code>"this.textContent = 'hi'"</code>. It is copied into the HTML as it is, so inside it <code>this</code> is the element and <code>event</code> is the event. Use it only for tiny things the Salam helpers do not cover.</li>
</ul>
<p>The functions you write in Salam are compiled to JavaScript and placed in one script at the end of the page. A browser finds the function named in <code>onclick="named()"</code> by looking it up on <code>window</code>, so the compiler also stores every handler there. You never write this yourself, but it explains why a handler must be a plain function of the page and not, say, a method.</p>
<p>State, for example a counter, lives in a top level <code>mut</code> variable above the page. The handler changes it and then writes the new value into the page with <code>dom.SetText</code>. The compiler checks your work: <code>dom.ById("x")</code> must name an id that exists in the same page (error E138), and an event must name a function that exists (error E137).</p>
<div class="note"><p><strong>Do not name a handler like a built-in.</strong> The browser looks a name in an attribute up on the element, then on its form, then on the document, and only then on the window. A function called <code>clear</code>, <code>open</code>, <code>close</code>, <code>write</code>, <code>reset</code>, <code>submit</code>, <code>focus</code>, <code>click</code> or <code>name</code> loses to the built-in of that name, and nothing seems to happen. Some names are worse than useless: the window has read-only properties such as <code>closed</code>, <code>status</code>, <code>top</code> and <code>length</code>, and a handler with one of those names makes the whole page script stop with an error, so none of your handlers work. Choose names such as <code>clear_board</code> or <code>open_menu</code>.</p></div>
<div class="note"><p>A page script only knows the <code>dom</code> helpers and your own code. Helpers that do more than pass one call on, such as <code>dom.RandomInt</code>, and other packages such as <code>math</code> are not part of it. <code>dom.Random()</code> gives a number from 0 up to 1, so <code>(dom.Random() * 85.0) as i64</code> is a whole number from 0 to 84.</p></div>

<h2 id="click">Click: counting and switching</h2>
<p><code>click</code> fires when the user presses and releases the primary mouse button on the element, and also when a keyboard user presses Enter or Space on a focused button, so it is the right event for anything that acts like a button. Use it on a real <code>button</code> element and not on a <code>box</code>: a button can be reached with the Tab key, a box cannot.</p>
<p>The counter below keeps its number in <code>count</code>. Each handler is a lambda that changes the variable and calls <code>show</code>, a small function that copies the number into the heading. The two parts, the state and the code that draws it, stay separate, and that is the habit worth learning first.</p>
{{example.web-mouse-counter}}
<p>The second example needs no variable, because the page itself remembers the state: <code>dom.ToggleClass</code> adds a class when the element does not have it and removes it when it does. The look of each state is written in CSS, in a <code>style</code> element, and the script only flips the class. The <code>transition</code> property makes the change fade instead of jump.</p>
{{example.web-mouse-toggle}}

<h2 id="kinds">Double click, other buttons and the context menu</h2>
<p><code>double click</code> fires after two quick clicks on the same element. The browser still sends the two ordinary <code>click</code> events first, so a handler on <code>click</code> runs twice before the double click arrives. Do not put two different actions on <code>click</code> and <code>double click</code> of the same element. <code>aux click</code> is the click of every button except the main one. The event's <code>button</code> number tells which: 0 is the main button, 1 the middle one, 2 the right one, and 3 and 4 are the back and forward buttons of some mice. <code>context menu</code> fires when the user asks for the context menu, which is a right click, the menu key or Shift and F10. Calling <code>dom.PreventDefault(e)</code> stops the browser's own menu.</p>
{{example.web-mouse-buttons}}
<p>The example reads the button number with <code>dom.GetNum(e, "button")</code>, which reads any number property of the event object. The log holds the last seven events, and <code>white space = "pre-line"</code> turns each <code>\n</code> in the text into a new line. <code>user select = none</code> stops a double click from selecting the words of the box.</p>
<p>That is enough to build your own menu. On <code>context menu</code> the handler prevents the default, moves a hidden box to the pointer and shows it. Any click on the area closes it again, and each item closes it as well.</p>
{{example.web-mouse-menu}}
<p>The menu box has <code>position = fixed</code>, which places it relative to the window, so <code>left</code> and <code>top</code> can be set straight from the pointer position <code>dom.EventX(e)</code> and <code>dom.EventY(e)</code>. Those two are measured from the top left corner of the window, which is the same corner a fixed box uses.</p>
<div class="note"><p>Use a custom context menu only where it adds something, as in an editor or a file list. A right click that does nothing useful, or hides the ordinary menu with its spell check and copy, annoys people. Keep every action of the menu reachable in another way too, because touch screens and keyboards do not right click.</p></div>

<h2 id="position">Pressing, releasing and moving</h2>
<p><code>mouse down</code> fires the moment a button goes down, <code>mouse up</code> when it comes up, and <code>click</code> is what the browser makes of a down and an up on the same element. <code>mouse move</code> fires again and again while the pointer moves, many times a second, so keep its handler short.</p>
<p>The position in the event is measured from the window. Most of the time you want it measured from some box, such as a drawing area. Ask the box where it is with <code>getBoundingClientRect</code> and subtract its <code>left</code> and <code>top</code>. In Salam that is <code>dom.Call0(box, "getBoundingClientRect")</code> for the rectangle and <code>dom.GetNum(rect, "left")</code> for each number. The first example shows the position inside the green box and moves a dot with it. The dot has <code>pointer events = none</code>, so it never gets in the way of the pointer.</p>
{{example.web-mouse-coords}}
<p>The next example draws. A top level <code>mut</code> variable says whether the button is down. <code>mouse down</code> sets it and paints the first dot, <code>mouse move</code> paints while it is set, and <code>mouse up</code> clears it. <code>mouse leave</code> clears it too, because a button released outside the box would never reach the box. Each dot is a new element made with <code>dom.Create</code> and added with <code>dom.Append</code>, and the look of the dots comes from one CSS rule written in a <code>style</code> element.</p>
{{example.web-mouse-draw}}
<p>This draws dots, so a fast stroke leaves gaps. For a smooth line use a canvas, and see <a href="/std/web/canvas/">web/canvas</a>. The pattern of down, move and up is the same for dragging an element by hand, and the next lessons build on it.</p>

<h2 id="enter">Enter and leave, over and out</h2>
<p>Four events tell you that the pointer has come or gone, and two pairs behave differently. <code>mouse enter</code> and <code>mouse leave</code> fire only for the element they are set on: when the pointer first comes into the element, and when it goes out of it altogether. Moving between the element and its children does not count. <code>mouse over</code> and <code>mouse out</code> also fire for the children, because they bubble up from them: moving from the outer box onto the inner one sends an <code>out</code> for the outer box and an <code>over</code> that rises from the inner one. Try both below and watch the counters. The left box says <code>enter 1, leave 0</code> while you are over it or its inner square, and the right box counts every step.</p>
{{example.web-mouse-enter}}
<p>Most of the time you want enter and leave: a menu that opens while the pointer is over it, a tooltip, a highlight. Use over and out when you really want to know about each child, for example to light up the exact cell of a table the pointer touches.</p>
<p>Here is a tooltip that follows the pointer. <code>mouse enter</code> shows it with the right text, <code>mouse move</code> moves it, and <code>mouse leave</code> hides it. It sits 14 and 18 pixels away from the pointer, because a tooltip under the pointer would take the pointer's events and flicker. Its <code>pointer events = none</code> prevents the same problem.</p>
{{example.web-mouse-tooltip}}

<h2 id="bubbling">The target and bubbling</h2>
<p>When you click the word inside a button inside a box, the event first goes to the word, and then it bubbles: it is offered to the button, then to the box, then upwards to the page. Every element on the way that has a <code>click</code> handler runs it. Inside a handler, <code>dom.EventTarget(e)</code> is the element that was really hit, even when the handler is set on an ancestor. This lets one handler on a list serve a hundred items. Call <code>dom.StopPropagation(e)</code> and the event goes no further.</p>
{{example.web-mouse-bubble}}
<p>The outer box has one handler. It reads the target's id with <code>dom.GetAttr</code> and prints it. The plain button has no handler of its own and still reports to the box, and so does the text. The stopping button has a handler that stops the event, so the box never hears from it. Do not stop propagation without a reason: other code that listens higher up, such as a menu that wants to close on any click, stops working for that element.</p>
<div class="note"><p>Most events bubble. A few do not, and <code>mouse enter</code> and <code>mouse leave</code> are the ones from this lesson. This is why they count differently from <code>over</code> and <code>out</code> above.</p></div>

<h2 id="wheel">The wheel</h2>
<p><code>wheel</code> fires when the wheel turns, or two fingers slide on a touchpad. The event's <code>deltaY</code> is negative when the user scrolls up, away from themselves, and positive when they scroll down. By default the wheel scrolls the page. A handler that calls <code>dom.PreventDefault(e)</code> cancels that, which is what you want in a map or an image viewer and what you should not do on a normal page. Most browsers treat wheel handlers on the window, document and body as passive and ignore the cancel there, so put the handler on an element, as the example does.</p>
{{example.web-mouse-wheel}}
<p>The handler multiplies or divides the zoom by 1.1 on each step and keeps it between 0.5 and 3, with two plain <code>if</code> statements, because the page script has no <code>math</code>. The result is written into <code>transform</code> as <code>scale(...)</code>. The box that is scaled is inside a stage with <code>overflow = hidden</code>, so what grows beyond the stage is cut off and the page does not move.</p>

<h2 id="game">Putting it together: a click game</h2>
<p>This game uses what you have seen. The red square has a handler for <code>click</code> that counts a hit and moves the square to a random place. The yellow field around it also has a <code>click</code> handler that counts a miss. A click on the square would bubble to the field and count as a miss as well, so the square's handler first calls <code>dom.StopPropagation(e)</code>. Positions are set in percent, so the game works at any width.</p>
{{example.web-mouse-game}}

<h2 id="css-hover">When CSS is the better tool</h2>
<p>Before you write <code>mouse over</code> and <code>mouse out</code> to change how something looks, remember that CSS can do it alone. A style with the prefix <code>hover</code> applies while the pointer is over the element, and the browser takes it away again, with no code that can forget a case. The two buttons below look the same. The first uses <code>hover background</code> and states each colour once. The second needs two handlers, repeats the colours in the script, and does nothing when the script fails to load. CSS also takes the hover style away by itself in every case, while a script has to remember each way the pointer can leave.</p>
{{example.web-mouse-hover}}
<p>Use a mouse event when something must happen, such as a number that changes, a box that appears, a request that is sent. Use CSS when the page only has to look different. The CSS lessons come back to <code>hover</code>, <code>focus</code> and <code>active</code> in detail.</p>
<div class="note"><p>Touch screens have no pointer to hover with. A tooltip or a menu that appears only on hover is out of reach for a phone, so also offer a click or a tap.</p></div>
