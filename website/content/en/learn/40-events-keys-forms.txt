<h2 id="keys">Keys: down, up and press</h2>
<p>Pressing a key sends <code>key down</code>. If you keep it pressed the browser sends <code>key down</code> again and again, with a property <code>repeat</code> set to true on the repeats. Letting go sends <code>key up</code>. An older third event, <code>key press</code>, fires only for keys that produce a character and is deprecated, so write new code with <code>key down</code> and <code>key up</code> and leave <code>key press</code> to old pages.</p>
<p>Key events go to the element that has focus: a text field the user clicked, a button reached with Tab, or an element with <code>tab index = 0</code>. They then bubble up to its ancestors, as clicks do, so a handler on a wrapper box hears the keys typed into everything inside it. You cannot put a handler on the page itself, so a shortcut works only while the focus is somewhere inside the element that carries the handler.</p>
<p>A handler that wants the event is a named function with one <code>i64</code> parameter, exactly as in the lesson on <a href="/learn/events-mouse/">mouse events</a>. <code>dom.EventKey(e)</code> returns the key as text. Other properties are read from the event with <code>dom.GetStr</code> and <code>dom.GetBool</code>. The example shows the two most useful: <code>code</code> and <code>repeat</code>. Click the field and press different keys, hold one down, and watch the lines change.</p>
{{example.web-keys-echo}}
<p><code>key</code> is what the key means right now: <code>a</code>, <code>A</code> with Shift held, <code>Enter</code>, <code>Escape</code>, <code>Tab</code>, <code>Backspace</code>, a space is the one-character string <code>" "</code>, and the arrows are <code>ArrowUp</code>, <code>ArrowDown</code>, <code>ArrowLeft</code> and <code>ArrowRight</code>. <code>code</code> is which physical key it is, such as <code>KeyA</code>, whatever the keyboard layout. Use <code>key</code> when the character matters and <code>code</code> when the position matters, as in games. Modifiers are the booleans <code>shiftKey</code>, <code>ctrlKey</code>, <code>altKey</code> and <code>metaKey</code> (Command on a Mac), read with <code>dom.GetBool(e, "ctrlKey")</code>.</p>
<div class="note"><p>With a Persian or any other non-Latin layout, <code>key</code> for the key labelled S is a Persian letter, not <code>s</code>, so <code>Ctrl+S</code> written as <code>key == "s"</code> never matches. For shortcuts compare <code>code</code> (<code>KeyS</code>), which does not change with the layout.</p></div>

<h2 id="actions">Enter, Escape, arrows and shortcuts</h2>
<p>Most uses of key events are a small table: this key does that. The first one is a task list. Enter adds the text of the field as a new item, made with <code>dom.Create</code>, and empties the field. Escape only empties it. The handler checks that the field is not empty before it adds an item, with <code>dom.GetValue(field).len() &gt; 0</code>.</p>
{{example.web-keys-enter}}
<p>The second moves a ball with the arrow keys. The box has <code>tab index = 0</code>, which makes it reachable with Tab and lets it have focus, so it receives the key events. Without that attribute a box never gets them. The handler ignores every other key by returning early, and for arrows it calls <code>dom.PreventDefault(e)</code>, because the browser would otherwise scroll the page. The position lives in two <code>mut</code> variables and is written into <code>left</code> and <code>top</code> through <code>dom.SetStyle</code>.</p>
{{example.web-keys-arrows}}
<p>The third reads modifier keys. A wrapper box around a text area listens to <code>key down</code> for everything typed inside. When Ctrl (or Command) is held and the key is S, the handler prevents the default, which would open the browser's own save dialog, and runs its own action. Always prevent the default of a shortcut you take over, and never take over one the user depends on, such as Ctrl+C or Ctrl+W.</p>
{{example.web-keys-shortcut}}

<h2 id="focus">Focus and blur</h2>
<p>An element has focus when it is the one that receives the keys. <code>focus</code> runs when an element gains focus, by a click, by Tab or from a script, and <code>blur</code> when it loses it. Together they are the natural place for a hint that appears next to the field being filled, and for checking a field when the user leaves it. The first example does both: the hint changes with the field, and leaving the name field empty paints it red.</p>
{{example.web-keys-focus}}
<p><code>focus</code> and <code>blur</code> do not bubble, so a handler on a wrapper never hears them from the fields inside. Their two siblings <code>focus in</code> and <code>focus out</code> do bubble, so one handler on a form section or a card can follow the focus of everything in it. They are also the way to style a whole group by what is inside it. CSS can do that too, with the <code>:focus-within</code> selector, and where it can you should use it.</p>
{{example.web-keys-focusin}}
<p>The group has one handler for each event. <code>focus in</code> adds the class that draws the blue border and <code>focus out</code> removes it. When you press Tab from one field to the next, <code>focus out</code> and <code>focus in</code> arrive one right after the other, before the browser draws anything, so the border does not flash. Inside a <code>focus out</code> handler, <code>event.relatedTarget</code> is the element that will receive the focus next, if you ever need to tell leaving the group from moving inside it.</p>

<h2 id="typing">Typing in a field: input, change and before input</h2>
<p>A text field has several events for the same act, and the difference is the moment. <code>input</code> fires after every change to the value: a typed letter, a deletion, a paste, a drop, an undo. <code>change</code> fires when the user is finished: when Enter is pressed in a one line field, or when the field loses focus after its value was changed. <code>before input</code> fires first, before the value changes, and its handler may call <code>preventDefault</code> to refuse the edit. Type into the field below and press Enter, then type some more and click away, and compare the two counters.</p>
{{example.web-keys-input}}
<p>A handler for <code>input</code> is what live features are made of. A character counter shows how much is left. Setting <code>maxlength</code> on the text area makes the browser stop typing at the limit, and the counter only has to show the length. It turns red near the end.</p>
{{example.web-keys-counter}}
<p>A search box filters a list on every keystroke. The handler reads the field, makes it lower case and goes through the items found by <code>dom.QueryAll</code>: a matching item gets <code>display</code> set to an empty string, which puts back its normal look, and the others get <code>none</code>. Empty text matches everything, so clearing the box brings all items back with no extra code.</p>
{{example.web-keys-filter}}
<p>The loop uses <code>dom.CountOf</code> for the number of items and <code>dom.ItemAt</code> for each one. <code>QueryAll</code> returns the elements that exist at that moment, so call it inside the handler, as here, and not once at the start, if items may be added later.</p>

<h2 id="selecting">Selecting text</h2>
<p>Three events report selection. <code>select</code> fires on a text field when the user selects some of its text, and not for a plain caret move. <code>selection change</code> fires whenever the selection or the caret in the field changes, which is also when the caret moves. <code>select start</code> fires when a new selection begins in any element, even one that is not editable, and a handler can call <code>preventDefault</code> to forbid the selection. The positions are the properties <code>selectionStart</code> and <code>selectionEnd</code> of the field, read with <code>dom.GetNum</code>.</p>
{{example.web-keys-select}}
<p>Select with the mouse, or hold Shift and use the arrow keys. The lines under the text area show a count of characters and the caret position, and the yellow paragraph reports that a selection began in it. Support for <code>selection change</code> on a text field is newer than for the other two. A browser may send it only to the document, so test it in the browsers you care about.</p>

<h2 id="submit">Submitting, resetting and form data</h2>
<p>A form sends <code>submit</code> when the user presses a submit button, or presses Enter in a field, and the browser's own checks have passed. Left alone, the browser then sends the fields to the server and loads the answer. A page that handles the form itself calls <code>dom.PreventDefault(e)</code> first and then reads the fields with <code>dom.GetValue</code>. Put the handler on the form, not on the button, because Enter in a field submits without clicking the button. The <code>reset</code> event fires when a reset button is pressed or the form is reset by script, just before the fields go back to their starting values.</p>
{{example.web-keys-submit}}
<div class="note"><p>Give your fields and buttons ids that differ from the names of your functions. Inside a form, the browser looks up a name among the form's fields and buttons first, so a button with <code>id = "send"</code> hides a function called <code>send</code> and the handler reports "is not a function".</p></div>
<p>The third form event is <code>form data</code>. It fires every time the browser builds the list of fields of a form, which a submit does, and so does a script that writes <code>new FormData(form)</code>. A handler gets <code>event.formData</code> and may add or change entries before they are used. The example adds a hidden field when the button builds the data.</p>
{{example.web-keys-formdata}}
<p>The button uses a short JavaScript string, because the <code>dom</code> helpers have no way to write <code>new</code>. The handler is a normal Salam function: <code>dom.GetProp(e, "formData")</code> gives the FormData object and <code>dom.CallS2</code> calls its <code>append</code> method with a name and a value.</p>

<h2 id="validation">Checking fields: invalid</h2>
<p>HTML can check fields without a line of script: <code>required</code>, <code>type = email</code>, <code>min</code>, <code>max</code>, <code>pattern</code> and <code>maxlength</code> all take part. When the browser checks a field and it fails, the field gets an <code>invalid</code> event. A check runs when the form is submitted, and also when a script calls <code>checkValidity()</code> or <code>reportValidity()</code> on the form or on a field. The second one also shows the browser's bubble with the message. <code>invalid</code> does not bubble, so the handler goes on the field itself.</p>
<p>The handler below replaces the browser's message with its own by calling <code>setCustomValidity</code> on the field. It looks at the field's <code>validity</code> object to tell an empty field from a wrong one. The message stays on the field until you remove it, so another handler, on <code>input</code>, sets it back to an empty string every time the user types. If you forget that, the field stays invalid forever, even after the user fixes it.</p>
{{example.web-keys-validate}}
<div class="note"><p>Checks in the browser are help for the user, not protection. Anybody can send a request with any values, so the server must check everything again.</p></div>

<h2 id="clipboard">Copy, cut and paste</h2>
<p>The three clipboard events fire when the user copies, cuts or pastes by keyboard or menu. They fire on the element that has the selection or the focus, and they bubble. <code>copy</code> and <code>cut</code> run before the browser does its part, so a handler can call <code>preventDefault</code> and put its own text on the clipboard with <code>clipboardData.setData</code>. <code>paste</code> gives the pasted content in <code>event.clipboardData</code>, and <code>getData("text")</code> is the plain text. A handler may prevent the default and insert a cleaned up version instead. A page cannot read the clipboard at any other time without the user's permission, and that is intended.</p>
{{example.web-keys-clipboard}}
<p>The paste handler passes the string to the page without touching it: <code>dom.CallS1</code> returns it as a JavaScript value, and <code>dom.SetProp</code> sets the <code>textContent</code> of the span with it. Select all in the box with Ctrl+A, then copy, cut and paste, and watch the counters and the last line.</p>

<h2 id="elements">Details, popovers, dialogs and find in page</h2>
<p>Some elements open and close by themselves, and they have events for it. <code>toggle</code> fires on a <code>details</code> element after it opens or closes, and on an element with the <code>popover</code> attribute after it is shown or hidden. A popover event carries <code>newState</code>, which is the text <code>open</code> or <code>closed</code>. The event fires a moment after the change, not at the same time. <code>before toggle</code> fires first, can be cancelled, and exists for popovers (and, in newer browsers, for dialogs). The example below shows the state that is about to start, <code>newState</code>, before the popover changes, and the state it reached after.</p>
{{example.web-keys-toggle}}
<p>A <code>dialog</code> opened with <code>showModal()</code> is shown over the page and blocks everything behind it until it closes. <code>dom.Call0(dialog, "showModal")</code> opens it. When the user presses Escape the dialog sends <code>cancel</code>, which can be prevented to keep it open, and then it closes and sends <code>close</code>. A dialog closed by code, with <code>dom.CallS1(dialog, "close", "deleted")</code>, sends only <code>close</code>, and the text you passed is its <code>returnValue</code>.</p>
{{example.web-keys-dialog}}
<p>The last event is <code>before match</code>. An element with <code>hidden = "until-found"</code> is not drawn, but its text stays searchable. When the user finds it with the browser's find in page, or opens a link to its id, the browser shows it and sends <code>before match</code> just before. A handler can open the section around it, such as a closed accordion, so the match is visible. In the example, try Ctrl+F and look for pomegranate, or open the page with <code>#secret</code> at the end of its address. Not all browsers support it yet; in those the text simply stays hidden until a script shows it. Chrome does not run an inline <code>onbeforematch</code> attribute even though it fires the event, so this one event is registered from a <code>script</code> element with <code>addEventListener</code>, as the example does. The attribute <code>before match</code> is the spelling the standard defines, and where a browser honours it you can use it instead.</p>
{{example.web-keys-match}}
