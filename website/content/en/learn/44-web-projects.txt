<h2 id="plan">How to build a page</h2>
<p>Every project below was built in the same order, and the order is a good habit. First the <strong>content</strong>: write the headings and the text in plain elements, with no styling, and check that the page makes sense. Second the <strong>structure</strong>: put the parts in landmarks such as <code>header</code>, <code>main</code>, <code>section</code> and <code>footer</code> (<a href="/learn/page-structure/">page structure</a>), because they give the page its outline. Third the <strong>look</strong>: colours, spacing and layout (<a href="/learn/css-basics/">styles</a>, <a href="/learn/css-layout/">layout</a>, <a href="/learn/css-responsive/">responsive pages</a>). Last the <strong>behaviour</strong>: state, handlers and the <code>dom</code> helpers (<a href="/learn/events-dom/">state, the DOM and timers</a>). A page that works at each step is easy to repair. A page that was styled before it had content is not.</p>
<p>Two habits keep the code short. Values used in many places, such as a brand colour, go into a constant above the page. A piece that appears more than once, such as a price card or a statistic, becomes a component. All the previews are live: click, type and resize your browser window to see how the pages react.</p>

<h2 id="landing">Project 1: a landing page</h2>
<p><strong>Goal.</strong> One page that sells one thing: a header with navigation, a hero with a single call to action, three reasons to buy, three plans and a footer. It has to look right on a phone without a separate mobile version.</p>
{{example.web-project-landing}}
<p><strong>Walkthrough.</strong> The page is a stack of full width bands inside <code>main</code>, and each band is a <code>section</code> that sets its own background and its own padding. <code>6vw</code> of padding left and right keeps the text away from the edges on every screen size, and the heading uses <code>clamp(2rem, 6vw, 3.4rem)</code> so it grows with the window but never gets too small or too big.</p>
<p>The columns need no media query. <code>repeat(auto-fit, minmax(220px, 1fr))</code> says: make as many columns as fit, each at least 220 pixels wide, and share the rest equally. Three cards sit side by side on a laptop, and the same rule stacks them on a phone. The price cards are one <code>component</code>, <code>Plan</code>, with three parameters. The <code>content: end</code> line inside it is a slot: whatever you write between <code>Plan:</code> and its <code>end</code> lands there, so each plan can list different details. Its look on hover, a small lift and a shadow, is written once with the <code>hover</code> prefix and a <code>transition</code> that makes the change smooth. <code>BRAND</code> and <code>ACCENT</code> are constants, so changing the colour of the whole page is a one line edit.</p>
<p><strong>Change it next.</strong> Make the middle plan stand out with a darker border and a small badge. Add a <code>media</code> rule that stacks the header on very narrow screens. Turn the call to action into a <code>link</code> to a sign up page, and add a form such as the one in project 3.</p>

<h2 id="blog">Project 2: a blog post with a sidebar</h2>
<p><strong>Goal.</strong> A comfortable reading page: a header, one article with a picture, a quotation and a sidebar, which drops below the article when the screen is narrow.</p>
{{example.web-project-blog}}
<p><strong>Walkthrough.</strong> Reading is the whole point, so the text rules come first: a serif font, a <code>line height</code> of 1.75 and a column that never gets wider than the page allows. The two column layout is a grid with <code>minmax(0, 1fr) 17rem</code>: the sidebar is a fixed 17rem and the article takes the rest. The <code>0</code> in <code>minmax</code> matters, because without it a long word or a wide picture can force the column wider than the screen. The box has a <code>max width</code> and <code>margin = "0 auto"</code>, which centres it on a big monitor.</p>
<p>The responsive part is the <code>media:</code> child of the grid. Below 760 pixels it replaces the two columns with one, and since the sidebar comes second in the source, it lands under the article. Order in the source is order on a phone, so write the parts in the order a phone reader should meet them. The meta line uses <code>time</code> with a machine readable <code>datetime</code>, the picture sits in a <code>figure</code> with a <code>figure caption</code>, and the quotation is a <code>block quote</code> whose bar is <code>border inline start</code>. Start and end are logical sides: in a right to left page the bar moves to the right edge by itself. <code>Tag</code> is a small component for the topic pills.</p>
<p><strong>Change it next.</strong> Add a table of contents as a <code>nav</code> with links to the headings (give the headings ids). Add a <code>dark</code> version with a <code>style</code> element and <code>prefers-color-scheme</code>. Print it: a <code>media = "print"</code> rule that hides the sidebar.</p>

<h2 id="signup">Project 3: a sign up form with live checks</h2>
<p><strong>Goal.</strong> A form that tells people what is wrong while they type, not after they press the button: a green or red border on every field, a message under it, a strength bar for the password, and a Join button that stays off until everything is right.</p>
{{example.web-project-signup}}
<p><strong>Walkthrough.</strong> There is no handler per field. Every field has the same <code>input = check</code>, and <code>check</code> reads all four fields and decides about all of them again. That is the pattern from <a href="/learn/events-dom/">the lesson on state</a>: the form is redrawn from its values every time, so it can never be half updated. <code>judge</code> does the drawing for one field. It clears both classes, adds <code>good</code> or <code>bad</code> only when the field is not empty (nobody wants red on a form they have not touched), and writes or clears the message. The three colours live in the CSS in the <code>style</code> element, next to <code>input:focus</code>, because they are states of an element and not decisions of the script.</p>
<p>The password score counts three things, length, a capital letter and a digit, and the bar shows <code>score * 33</code> percent. The Show button swaps the <code>type</code> of the field between <code>password</code> and <code>text</code> with <code>dom.SetAttr</code>. The email field has <code>type = email</code> and <code>autocomplete</code> values, so phones show the right keyboard and password managers know what to fill. The form's <code>submit</code> handler calls <code>dom.PreventDefault(e)</code> and shows a greeting in place of sending anything, because the preview has no server.</p>
<div class="note"><p>Keep the names of your handler functions different from the <code>id</code> of every button and field in the form. A button with <code>id = "join"</code> and a function called <code>join</code> do not get along: inside a form the browser finds the button before the function, and the click does nothing. The functions here are called <code>welcome</code> and <code>reveal</code>. And remember that checks like these are help for the visitor. The server must check the same things again.</p></div>
<p><strong>Change it next.</strong> Add a checkbox "I accept the rules" that must be ticked before the button turns on. Check the name for letters only. Replace the strength bar with a <code>meter</code> element. Send the form to a real address with <code>action</code> and <code>method</code> and validate it on the server (see <a href="#serving">the last section</a>).</p>

<h2 id="dashboard">Project 4: a dashboard with a CSS bar chart</h2>
<p><strong>Goal.</strong> A page for looking at numbers: four statistic cards, a bar chart, and a table of the latest orders. No script at all.</p>
{{example.web-project-dashboard}}
<p><strong>Walkthrough.</strong> The chart is made of boxes. <code>Bar</code> is a component with a day and a value. Inside is a track of fixed height (150 pixels, a flex container whose items sit at the bottom with <code>align items = flex-end</code>), and in the track a box whose <code>height = value + "%"</code>. A value of 80 gives a box 80 percent as high as the track. Putting the height in a track of known size is the trick: a percentage height needs a parent whose height is known. The number is written inside the bar, so the chart can be read with a screen reader, and the bar gets a darker colour on hover. The statistics are the component <code>Stat</code>, and the coloured status labels in the table are <code>Pill</code>, a component that is just one <code>span</code>.</p>
<p>The layout is two nested grids. The cards use <code>auto-fit</code> with a minimum of 180 pixels, and the lower row uses a minimum of 300, so the chart and the table sit side by side when there is room and stack when there is not. The table is a real <code>table</code> with a <code>header</code> and a <code>main</code> section, and its card has <code>overflow = auto</code>, so on a narrow screen the table scrolls inside its card instead of breaking the page. The global rule for <code>td, th</code> gives all cells the same padding and a thin line below. Colour carries meaning here, green for good and red for bad, so every figure also has a sign or a word: never let colour be the only message.</p>
<p><strong>Change it next.</strong> Make the bars grow when the page opens, with a CSS animation (<a href="/learn/css-motion/">transitions and animations</a>). Add a column of buttons that filter the table, using the pattern of project 5. Fill the numbers from the server instead of the source, as in the last section.</p>

<h2 id="todo">Project 5: a task list that remembers</h2>
<p><strong>Goal.</strong> A small application: add tasks, tick them, remove them, filter by All, Active and Done, count what is left, and find the list again after a reload.</p>
{{example.web-project-todo}}
<p><strong>Walkthrough.</strong> This is the state pattern at full size. The state is three top level variables: <code>texts</code> and <code>flags</code>, two vectors that hold the text and the done mark of every task, and <code>mode</code>, the filter. The page keeps nothing else. <code>draw</code> empties the list, goes through the vectors and builds a row for every task that passes the filter, and counts what is open. Every change, adding, ticking, removing and filtering, ends with a call to <code>draw</code>, so there is one place where the screen is made. Rebuilding the whole list is a little wasteful and very safe. For a list of a few hundred tasks nobody can tell.</p>
<p>The handlers of the rows are made while the page runs, with <code>dom.OnEvent</code>, and each lambda remembers its own <code>i</code>, so the tick of the third row changes the third task. After a change the rows are made again, so those indexes are never out of date. Saving is <code>keep</code>: it writes one string, one line per task, with <code>1</code> or <code>0</code> in front of the text to say whether it is done. Loading is the reverse, in <code>show_all</code>, which is also the handler of the All button; the <code>script</code> element on the last line calls it when the page has been read, as in <a href="/learn/events-dom/#storage">the storage section</a>. Salam has no inline <code>if</code>, so a tiny function, <code>choose</code>, picks between two strings and keeps the other code short.</p>
<p>The preview runs in a frame that does not allow storage, so there the list works but does not survive a reload. On a real page it does. Task text is always put in with <code>SetText</code>, never <code>SetHtml</code>.</p>
<p><strong>Change it next.</strong> Let a double click edit a task. Add a "clear done" button. Store the creation time and sort by it. Move the saving to a server, so the list follows the person to another device.</p>

<h2 id="gallery">Project 6: a gallery with a lightbox</h2>
<p><strong>Goal.</strong> A grid of pictures. Clicking one opens it large in a window with Previous, Next and Close buttons, and the arrow keys and Escape work too. The pictures here are gradients, so the page needs no files, and the code is the same for photos.</p>
{{example.web-project-gallery}}
<p><strong>Walkthrough.</strong> The window is a <code>dialog</code> element. Calling <code>showModal</code> on it, with <code>dom.Call0(dialog, "showModal")</code>, puts it on top of everything, dims the page behind it, moves the keyboard focus inside and closes it on Escape. All of that comes from the browser. The dim layer is styled with <code>dialog::backdrop</code> in a <code>style</code> element. Clicking on the backdrop counts as a click on the dialog itself, so the <code>backdrop</code> handler closes the window when <code>dom.EventTarget(e)</code> is the dialog and not one of its children. (A click on the dialog's own padding counts as well, so keep the padding small.)</p>
<p>Each tile is a <code>button</code> from the component <code>Shot</code>, and the button carries its own data in attributes: <code>data n</code>, <code>data title</code> and <code>data bg</code>. One handler, <code>open_shot</code>, serves all six tiles. It asks the event which button was clicked and reads the attributes, and <code>show_shot</code> copies them into the window. Previous and Next call <code>show_shot</code> with a number one lower or higher, and the <code>%</code> in <code>(n + total) % total</code> wraps around from the last picture to the first. The tiles are found with <code>QueryAll("[data-n]")</code> and not with a class. Two elements with the same class must look the same, and every tile has its own gradient, so the compiler would refuse a shared class (error E136).</p>
<p><strong>Change it next.</strong> Put real images in the tiles (<a href="/learn/page-media/">links, images and media</a>) and keep a small and a large version of each. Close the window when the user swipes down. Move the focus back to the tile that opened it.</p>

<h2 id="serving">Serving a page from a Salam program</h2>
<p>Everything above is a fixed page: its structure is decided when you compile it, and the preview is the finished result. A real site needs pages that depend on the visitor, such as a greeting with their name or a dashboard with today's numbers. For that, the page gets a name and parameters, and it becomes a function that returns the page as HTML. A web server written in Salam calls it for each request. <a href="/learn/layout/">The first lesson of this part</a> explains these pages in detail; here is the smallest complete program, which would serve the landing page with a name and a plan taken from the address.</p>
{{example.web-project-serve}}
<p>The program starts a server and has no output, so it is only checked here. Run it, open <code>http://localhost:8080/?name=Ada&amp;plan=Duo</code> and you get the page. Text that arrives in a parameter is escaped for you, so a visitor who sends <code>?name=&lt;b&gt;</code> sees the characters and no markup. For the server side, the <code>net.http</code> and <code>net.router</code> packages handle requests, query strings and answers, and <a href="/std/net/http/validate/">net/http/validate</a> checks the form data that project 3 collected in the browser. A static page like projects 1 to 6 is also complete as it is: <code>salam page build page.salam --inline</code> writes it to a single HTML file that any web host will serve.</p>

<li>Make the blog post into a reusable page: a component <code>Post</code> with a title and a date, and two posts that use it. Which parts stay fixed, and which become parameters?</li>
<li>Put the dashboard on a phone: open the preview in a narrow window and fix whatever looks cramped, using only <code>auto-fit</code> and one <code>media</code> rule.</li>
<li>Translate one project into Persian, or into English if you started in Persian. Which style properties need to change for a right to left page, and which ones change by themselves?</li>
</ul>
