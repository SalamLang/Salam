<h2 id="plan">How to build a page</h2>
<p>Every project below was built in the same order, and the order is a good habit. First the <strong>content</strong>: write the headings and the text in plain elements, with no styling, and check that the page makes sense. Second the <strong>structure</strong>: put the parts in landmarks such as <code>header</code>, <code>main</code>, <code>section</code> and <code>footer</code> (<a href="/learn/page/structure/">page structure</a>), because they give the page its outline. Third the <strong>look</strong>: colours, spacing and layout (<a href="/learn/css/basics/">styles</a>, <a href="/learn/css/layout/">layout</a>, <a href="/learn/css/responsive/">responsive pages</a>). Last the <strong>behaviour</strong>: state, handlers and the <code>dom</code> helpers (<a href="/learn/events/dom/">state, the DOM and timers</a>). A page that works at each step is easy to repair. A page that was styled before it had content is not.</p>
<p>Two habits keep the code short. Values used in many places, such as a brand colour, go into a constant above the page. A piece that appears more than once, such as a price card or a statistic, becomes a component. All the previews are live: click, type and resize your browser window to see how the pages react.</p>

<h2 id="landing">Project 1: a landing page</h2>
<p><strong>Goal.</strong> One page that sells one thing: a header with navigation, a hero with a single call to action, three reasons to buy, three plans and a footer. It has to look right on a phone without a separate mobile version.</p>
{{example.web-project-landing}}
<p><strong>Walkthrough.</strong> The page is a stack of full width bands inside <code>main</code>, and each band is a <code>section</code> that sets its own background and its own padding. <code>6vw</code> of padding left and right keeps the text away from the edges on every screen size, and the heading uses <code>clamp(2rem, 6vw, 3.4rem)</code> so it grows with the window but never gets too small or too big.</p>
<p>The columns need no media query. <code>repeat(auto-fit, minmax(220px, 1fr))</code> says: make as many columns as fit, each at least 220 pixels wide, and share the rest equally. Three cards sit side by side on a laptop, and the same rule stacks them on a phone. The price cards are one <code>component</code>, <code>Plan</code>, with three parameters. The <code>content: end</code> line inside it is a slot: whatever you write between <code>Plan:</code> and its <code>end</code> lands there, so each plan can list different details. Its look on hover, a small lift and a shadow, is written once with the <code>hover</code> prefix and a <code>transition</code> that makes the change smooth. <code>BRAND</code> and <code>ACCENT</code> are constants, so changing the colour of the whole page is a one line edit.</p>
<p><strong>Change it next.</strong> Make the middle plan stand out with a darker border and a small badge. Add a <code>media</code> rule that stacks the header on very narrow screens. Turn the call to action into a <code>link</code> to a sign up page, and add a form such as the one in project 3.</p>

<h2 id="blog">Project 2: a blog post with a sidebar</h2>
<p><strong>Goal.</strong> A comfortable reading page: a header, one article with a picture, a quotation and a sidebar, which drops below the article when the screen is narrow.</p>
{{example.web-project-blog}}
<p><strong>Walkthrough.</strong> Reading is the whole point, so the text rules come first: a serif font, a <code>line height</code> of 1.75 and a column that never gets wider than the page allows. The two column layout is a grid with <code>minmax(0, 1fr) 17rem</code>: the sidebar is a fixed 17rem and the article takes the rest. The <code>0</code> in <code>minmax</code> matters, because without it a long word or a wide picture can force the column wider than the screen. The box has a <code>max width</code> and <code>margin = 0, auto</code>, which centres it on a big monitor.</p>
<p>The responsive part is the <code>media:</code> child of the grid. Below 760 pixels it replaces the two columns with one, and since the sidebar comes second in the source, it lands under the article. Order in the source is order on a phone, so write the parts in the order a phone reader should meet them. The meta line uses <code>time</code> with a machine readable <code>datetime</code>, the picture sits in a <code>figure</code> with a <code>figure caption</code>, and the quotation is a <code>block quote</code> whose bar is <code>border inline start</code>. Start and end are logical sides: in a right to left page the bar moves to the right edge by itself. <code>Tag</code> is a small component for the topic pills.</p>
<p><strong>Change it next.</strong> Add a table of contents as a <code>nav</code> with links to the headings (give the headings ids). Add a <code>dark</code> version with a <code>style</code> element and <code>prefers-color-scheme</code>. Print it: a <code>media = "print"</code> rule that hides the sidebar.</p>

<h2 id="signup">Project 3: a sign up form with live checks</h2>
<p><strong>Goal.</strong> A form that tells people what is wrong while they type, not after they press the button: a green or red border on every field, a message under it, a strength bar for the password, and a Join button that stays off until everything is right.</p>
{{example.web-project-signup}}
<p><strong>Walkthrough.</strong> The page remembers four strings, one for each field, and a flag for the Show button. Every field has one job: its <code>input</code> handler writes the new text into its variable. Everything else is worked out from the four strings and drawn again whenever one changes, so the form can never be half updated. That is the pattern from the lesson on state. Small functions say whether a value is good (<code>good_name</code>, <code>good_mail</code>, <code>strength</code>, <code>good_again</code>). Each field draws itself from them: an <code>if</code> inside the input gives it the green border when the field is not empty and good, another gives it the red one when it is not empty and bad (nobody wants red on a form they have not touched), and the note under it is empty or holds the message. The colours sit next to <code>focus:</code> because they are states of an element and not decisions of the script.</p>
<p>The password score counts three things, length, a capital letter and a digit, and the bar shows <code>score * 33</code> percent. The Show button flips a variable and the field takes its type from it. The email field has <code>type = email</code> and <code>autocomplete</code> values, so phones show the right keyboard and password managers know what to fill. The form's submit handler calls <code>dom.PreventDefault(e)</code> and shows a greeting in place of sending anything, because the preview has no server. The Join button is <code>disabled</code> until all four checks pass, and a <code>disabled:</code> block dims it.</p>
<div class="note"><p>Keep the names of your handler functions different from the <code>id</code> of every button and field in the form. A button with <code>id = "join"</code> and a function called <code>join</code> do not get along: inside a form the browser finds the button before the function, and the click does nothing. The functions here are called <code>welcome</code> and <code>reveal</code>. And remember that checks like these are help for the visitor. The server must check the same things again.</p></div>
<p><strong>Change it next.</strong> Add a checkbox "I accept the rules" that must be ticked before the button turns on. Check the name for letters only. Replace the strength bar with a <code>meter</code> element. Send the form to a real address with <code>action</code> and <code>method</code> and validate it on the server (see <a href="#serving">the last section</a>).</p>

<h2 id="dashboard">Project 4: a dashboard with a CSS bar chart</h2>
<p><strong>Goal.</strong> A page for looking at numbers: four statistic cards, a bar chart, and a table of the latest orders. No script at all.</p>
{{example.web-project-dashboard}}
<p><strong>Walkthrough.</strong> The chart is made of boxes. <code>Bar</code> is a component with a day and a value. Inside is a track of fixed height (150 pixels, a row whose items sit at the bottom with <code>align = end</code>), and in the track a box whose <code>height = value + "%"</code>. A value of 80 gives a box 80 percent as high as the track. Putting the height in a track of known size is the trick: a percentage height needs a parent whose height is known. The number is written inside the bar, so the chart can be read with a screen reader, and the bar gets a darker colour on hover. The statistics are the component <code>Stat</code>, and the coloured status labels in the table are <code>Pill</code>, a component that is just one <code>span</code>.</p>
<p>The layout is two nested grids. The cards use <code>auto-fit</code> with a minimum of 180 pixels, and the lower row uses a minimum of 300, so the chart and the table sit side by side when there is room and stack when there is not. The table is a real <code>table</code> with a <code>header</code> and a <code>main</code> section, and its card has <code>overflow = auto</code>, so on a narrow screen the table scrolls inside its card instead of breaking the page. The global rule for <code>td, th</code> gives all cells the same padding and a thin line below. Colour carries meaning here, green for good and red for bad, so every figure also has a sign or a word: never let colour be the only message.</p>
<p><strong>Change it next.</strong> Make the bars grow when the page opens, with a CSS animation (<a href="/learn/css/motion/">transitions and animations</a>). Add a column of buttons that filter the table, using the pattern of project 5. Fill the numbers from the server instead of the source, as in the last section.</p>

<h2 id="todo">Project 5: a task list that remembers</h2>
<p><strong>Goal.</strong> A small application: add tasks, tick them, remove them, filter by All, Active and Done, count what is left, and find the list again after a reload.</p>
{{example.web-project-todo}}
<p><strong>Walkthrough.</strong> This is the state pattern at full size. The state is three variables of one component: <code>items</code>, one string per task with <code>1</code> or <code>0</code> in front of the text to say whether it is done, <code>mode</code>, the filter, and <code>draft</code>, the text in the box. The page keeps nothing else. The list is an <code>each</code> over <code>items</code>, an <code>if</code> inside it lets a row through only when it passes the filter, and every row is a small component that draws itself from its own string: the tick, the grey colour and the strike-through all come from <code>is_done</code>. A row cannot change the list, so the page passes it two functions, <code>flip</code> and <code>remove</code>, and the row calls them with its text. They find the task in <code>items</code>, change it and save. There is no draw function to call and no handler to keep in step: changing <code>items</code> or <code>mode</code> is all it takes.</p>
<p>A row copies its entry into its own variable (<code>held := entry</code>) because a handler reads the variable of its own component, not the loop variable it was made with. Saving writes one string, one line per task, with 1 or 0 in front of the text. Loading is <code>load</code>, which gives <code>items</code> its first value when the page opens. A ternary expression picks between two values where the code needs a choice.</p>
<p>The preview runs in a frame that does not allow storage, so there the list works but does not survive a reload. On a real page it does. Task text is always put in with <code>SetText</code>, never <code>SetHtml</code>.</p>
<p><strong>Change it next.</strong> Let a double click edit a task. Add a "clear done" button. Store the creation time and sort by it. Move the saving to a server, so the list follows the person to another device.</p>

<h2 id="gallery">Project 6: a gallery with a lightbox</h2>
<p><strong>Goal.</strong> A grid of pictures. Clicking one opens it large in a window with Previous, Next and Close buttons, and the arrow keys and Escape work too. The pictures here are gradients, so the page needs no files, and the code is the same for photos.</p>
{{example.web-project-gallery}}
<p><strong>Walkthrough.</strong> The window is not a dialog element but a box that exists only while a variable says so. <code>current</code> holds the number of the open picture, and minus one means none. When it is zero or more, an <code>if</code> adds a box with <code>position = fixed</code> and <code>inset = 0</code> that covers the page, laid out as a <code>stack</code>: a dim box that fills it, with a click handler that sets <code>current</code> back to minus one, and the white card on top. The dim layer is a colour with some transparency, so there is no backdrop pseudo element and no style element. Clicking the dim box closes the window and clicking the card does not, because the two are siblings, not parent and child. The Close button has <code>autofocus</code>, so the keyboard focus is inside the window as soon as it opens. The card is <code>width = 92%</code> with <code>max width = 544</code>, which does what <code>min(34rem, 92vw)</code> did.</p>
<p>Each tile is a <code>button</code> from the component <code>Shot</code>, which gets its title and its colours from the page. The page keeps the data in small functions (<code>title_of</code>, <code>light_of</code>, <code>deep_of</code>) and builds the gradient with <code>shade</code>, so the tile and the big picture use the same colours. Previous and Next move <code>current</code> by one, and the <code>%</code> wraps around from the last picture to the first and back. The arrow keys are read by a <code>key down</code> handler with <code>dom.EventKey</code>.</p>
<p><strong>Change it next.</strong> Put real images in the tiles (<a href="/learn/page/media/">links, images and media</a>) and keep a small and a large version of each. Close the window when the user swipes down. Move the focus back to the tile that opened it.</p>

<h2 id="serving">Serving a page from a Salam program</h2>
<p>Everything above is a fixed page: its structure is decided when you compile it, and the preview is the finished result. A real site needs pages that depend on the visitor, such as a greeting with their name or a dashboard with today's numbers. For that, the page gets a name and parameters, and it becomes a function that returns the page as HTML. A web server written in Salam calls it for each request. <a href="/learn/layout/">The first lesson of this part</a> explains these pages in detail; here is the smallest complete program, which would serve the landing page with a name and a plan taken from the address.</p>
{{example.web-project-serve}}
<p>The program starts a server and has no output, so it is only checked here. Run it, open <code>http://localhost:8080/?name=Ada&amp;plan=Duo</code> and you get the page. Text that arrives in a parameter is escaped for you, so a visitor who sends <code>?name=&lt;b&gt;</code> sees the characters and no markup. For the server side, the <code>net.http</code> and <code>net.router</code> packages handle requests, query strings and answers, and <a href="/std/net/http/validate/">net.http.validate</a> checks the form data that project 3 collected in the browser. A static page like projects 1 to 6 is also complete as it is: <code>salam page build page.salam --inline</code> writes it to a single HTML file that any web host will serve. To serve the site, run several domains, connect PHP and deploy, the <a href="/learn/serve/">salam serve web server lesson</a> covers all of it.</p>

<h2 id="routes">Routes: one page, many screens</h2>
<p>A single-page app has one HTML file and many screens: <code>/</code>, <code>/users/3</code>, <code>/settings</code>. The <code>pages/</code> folder next to <code>main.salam</code> is the route table: one file per screen, and the file name is the path. An <code>Outlet</code> element shows the component of the current path. Changing the route does not reload the page; it is a state change that redraws only the outlet.</p>
<pre class="code" dir="ltr"><code>main.salam
pages/
  index.salam           /
  login.salam           /login
  admin.salam           /admin
  users/
    [id].salam          /users/:id
  _404.salam            every other path</code></pre>
<p>Each file declares exactly one <code>pub component</code>. <code>page.Guard(condition)</code>, when the page has one, is the first line of its body, and the <code>title</code> setting comes after it.</p>
<pre class="code" dir="ltr"><code>mut signed_in := false

page:
    nav:
        link: to = "/" content = "Home" end
        link: to = "/users/1" content = "User 1" end
    end
    Outlet: end
end</code></pre>
<pre class="code" dir="ltr"><code>pub component User(id: int):
    title = "User " + id
    heading: content = "User " + id end
    button: click = (): page.route.GoTo("/users/" + (id + 1)) end content = "Next" end
end</code></pre>
<pre class="code" dir="ltr"><code>pub component Admin:
    page.Guard(signed_in)
    paragraph: content = "Admin area" end
end</code></pre>
<pre class="code" dir="ltr"><code>pub component Login:
    button:
        click = ():
            signed_in = true
            page.route.Redirect("/admin")
        end
        content = "Sign in"
    end
end</code></pre>
<ul>
<li>A file or folder name is a literal segment, <code>[id]</code> is one segment that fills the parameter <code>id</code>, <code>[[id]]</code> is one that may be missing, and <code>[...rest]</code> takes the rest of the path. The most specific path wins, so <code>users/new.salam</code> beats <code>users/[id].salam</code>. <code>_404.salam</code> catches every other path, and <code>index.salam</code> is its folder itself.</li>
<li>A <code>:name</code> segment fills the component parameter with the same name. An <code>int</code> parameter only matches a whole number that fits in an <code>int</code> (digits with an optional minus sign), so <code>/users/abc</code> falls to <code>_404.salam</code>.</li>
<li><code>page.Guard(condition)</code> lets the route match only while the condition is true. It must be the first line of the component, above every setting, style and element, and never inside an <code>if</code>. A <code>_layout.salam</code> in a folder gives the same guard to every page below it. When it is false the route is skipped and the next one that matches is shown, usually <code>_404.salam</code>, while the address stays the same. Guards are checked again after every state change, so signing out leaves a guarded screen at once. To send the visitor somewhere else, call <code>page.route.Redirect(path)</code> in code, as <code>Login</code> does after signing in. <code>title</code> sets the document title.</li>
<li><code>link: to = "/path"</code> is a normal link: middle click, open in a new tab and crawlers work, and a plain click changes the route without a reload. The link of the current route gets <code>aria-current="page"</code>. A link with <code>url</code> instead of <code>to</code> always loads the page from the server.</li>
<li>In code, <code>page.route.GoTo(path)</code> opens a screen, <code>page.route.Redirect(path)</code> opens one in place of the current screen, so Back skips it (good after a sign in), and <code>page.route.Back()</code> and <code>page.route.Forward()</code> move through the history like the browser buttons. <code>page.route.path</code>, <code>page.route.query</code> and <code>page.route.pattern</code> are state you can read anywhere, and <code>page.route.Param("id")</code> and <code>page.route.Query("q")</code> read single values. A relative path in <code>page.route.GoTo</code> is resolved under the current one, so <code>page.route.GoTo("edit")</code> from <code>/users/3</code> opens <code>/users/3/edit</code>.</li>
<li>The Persian names are <code>نمای مسیر</code>, <code>مقصد</code>, <code>صفحه.مسیر.برو</code>, <code>صفحه.مسیر.هدایت</code>, <code>صفحه.مسیر.عقب</code>, <code>صفحه.مسیر.جلو</code>, <code>صفحه.مسیر</code>, <code>صفحه.مسیر.پارامتر</code> and <code>صفحه.مسیر.مقدار پرسمان</code>.</li>
</ul>
<p>There are two modes. The default, <code>mode = history</code> (a setting of the <code>page:</code> block), uses clean paths such as <code>/users/3</code>. A visitor can open such a path directly, so the server must answer every page path with the app: <code>salam serve</code> does that on its own for a page built in this mode, <code>salam web</code> writes an <code>.htaccess</code> file for Apache next to the page, and nginx needs <code>try_files $uri /index.html;</code> (see <a href="/learn/serve/#spa">serving a single-page app</a>). <code>mode = hash</code> keeps the route after a <code>#</code>, as in <code>/#/users/3</code>, and works on any static host with no server setting at all. <code>base = "/app"</code> serves the app under a sub path.</p>

<p>A page project with a <code>pages/</code> folder can also be served as finished HTML. <code>salam page build --ssr=dist</code> writes <code>dist/server</code>, a native program, and <code>dist/public</code> with the script, the style sheet and a copy of every page that needs no parameter. Start it with <code>PORT=8080 dist/server</code> (<code>HOST</code> defaults to <code>127.0.0.1</code>, <code>PORT=0</code> picks a free port). For each request the server finds the route, checks the guards (a page whose guard fails is skipped like an unknown path), builds the layouts and the page into HTML with the same code the browser would run, and answers <code>404</code> with your <code>_404</code> page for an unknown path. Text that comes from the address is escaped in the page and in the state block <code>&lt;script type="application/json" id="__salam"&gt;</code>. <code>salam serve --render</code> does the build, runs the server and rebuilds when you save a file.</p>
<h2 id="folders">Several files: components import themselves</h2>
<p>When the entry file is <code>main.salam</code>, the whole project folder is one program. Every <code>pub component</code> in every <code>.salam</code> file under that folder can be used from any other file with no <code>include</code>. A component without <code>pub</code> stays private to its own file (using it elsewhere is E232). Two <code>pub component</code> with the same name anywhere in the project, including a route file in <code>pages/</code>, are error E291 and the message names both files and lines.</p>
<pre class="code" dir="ltr"><code>main.salam          page: Card: title = "hi" end end
ui/card.salam       pub component Card(title): ... Badge: ... end
shop/badge.salam    pub component Badge(label): ... end</code></pre>
<ul>
<li>Skipped folders: the <code>pages/</code> folder (route files only, they are not imported by name), hidden folders, <code>node_modules</code>, <code>build</code>, <code>dist</code>, <code>out</code>, <code>target</code>, <code>vendor</code>, <code>tests</code>, <code>test</code> and <code>__tests__</code>, any folder that has its own <code>main.salam</code> (another project), and files ending in <code>_test.salam</code> or <code>.test.salam</code>. Every other <code>.salam</code> file is read, whether or not it declares components.</li>
<li>Building one file that is not named <code>main.salam</code> (<code>salam page build card.salam</code>), the playground and layouts used from a Salam program work as before: nothing is imported unless you write <code>include</code>, and a repeated <code>pub</code> name only gives a warning.</li>
</ul>
