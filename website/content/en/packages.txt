<div class="note"><p>This page is about packages written by other people, kept in their own repositories. Everything in the <a href="/std/">standard library</a> ships with the compiler and needs no <code>salam add</code>. The language side, <code>package</code>, <code>include</code> and <code>pub</code>, is taught in <a href="/learn/packages/">lesson 18</a>.</p></div>

<h2 id="use">Using a package</h2>
<p>A project is a folder with a <code>main.salam</code> and a <code>salam.toml</code>. <code>salam init</code> turns the current folder into one and keeps any file that is already there:</p>
<pre class="code" dir="ltr"><code>$ mkdir app &amp;&amp; cd app
$ salam init
Created project 'app':
  main.salam
  salam.toml
  .gitignore

Next steps:
  salam run

$ salam add github.com/demo/slug
added github.com/demo/slug v1.1.0</code></pre>
<p><code>salam add</code> looks up the newest release of the repository, downloads it into <code>~/.salam/pkg</code> and writes it down in two files. <code>salam.toml</code> says what you asked for, and <code>salam.lock</code> records exactly what you got, the commit and a checksum, so every machine builds the same code.</p>
<pre class="code" dir="ltr"><code>[dependencies]
"github.com/demo/slug" = "v1.1.0"</code></pre>
<p>A package from a repository is imported with a quoted address. The last part of the address becomes the name you use in the code, so <code>github.com/demo/slug</code> is reached as <code>slug</code>:</p>
<pre class="code" dir="ltr"><code>import "github.com/demo/slug"

func main:
    println slug.Make("Hello, World!")
    println slug.MakeMax("Packages in Salam are simple", 14)
end</code></pre>
<pre class="code" dir="ltr"><code>$ salam run
hello-world
packages-in-sa</code></pre>
<p>If two packages would get the same name, give one of them another: <code>import s "github.com/demo/slug"</code> and then <code>s.Make(...)</code>. To reach a package inside a repository's folder, add the folder to the address, as in <code>import "github.com/owner/repo/sub"</code>.</p>
<p>The commands you will use most:</p>
<div class="table-wrap"><table><thead><tr><th>Command</th><th>What it does</th></tr></thead><tbody>
<tr><td><code>salam add github.com/owner/repo</code></td><td>Adds the newest release; <code>@v1.2.0</code> picks a tag</td></tr>
<tr><td><code>salam remove github.com/owner/repo</code></td><td>Takes it out of <code>salam.toml</code> and <code>salam.lock</code>; the download stays cached</td></tr>
<tr><td><code>salam update</code></td><td>Moves every package, or only the ones you name, to the newest release with the same major version</td></tr>
<tr><td><code>salam deps</code></td><td>Downloads what <code>salam.lock</code> lists and checks every checksum; run it after cloning a project</td></tr>
<tr><td><code>salam search words</code></td><td>Looks in the standard library and in the registry</td></tr>
<tr><td><code>salam install github.com/owner/tool</code></td><td>Builds a program's <code>main.salam</code> and puts it in <code>~/.salam/bin</code></td></tr>
<tr><td><code>salam uninstall tool</code></td><td>Removes it again</td></tr>
</tbody></table></div>
<p>Commit <code>salam.toml</code> and <code>salam.lock</code> with your code, and leave the downloaded packages out. A fresh clone then needs only <code>salam deps</code>:</p>
<pre class="code" dir="ltr"><code>$ salam deps
github.com/demo/slug v1.1.0
downloaded 1 package(s)</code></pre>
<p>Removing a package leaves your imports behind, and the compiler tells you so:</p>
<pre class="code" dir="ltr"><code>$ salam remove github.com/demo/slug
removed github.com/demo/slug
$ salam run
error[E008]: package 'github.com/demo/slug' is not a dependency of this project; run: salam add github.com/demo/slug</code></pre>

<h2 id="create">Writing a package</h2>
<p>A package is a git repository with a manifest and one entry file. The entry file carries the repository's name, so the repository <code>github.com/demo/slug</code> looks like this:</p>
<pre class="code" dir="ltr"><code>slug/
  salam.toml        the manifest
  slug.salam        the entry file: package slug
  slug_test.salam   tests, run by salam test
  README.md
  LICENSE</code></pre>
<p>The rule that decides the file names is short. A program, something you run, has a <code>main.salam</code> and nothing else is ever taken as its entry. A library, something other projects import, has no <code>main</code> at all; its entry is <code>&lt;name&gt;.salam</code>, and a package inside a folder of the repository is <code>&lt;folder&gt;/&lt;folder&gt;.salam</code>, which is what <code>import "github.com/owner/repo/sub"</code> loads. Other files of the same package sit next to the entry file and are joined to it, as shown in <a href="/learn/packages/#folder">lesson 18</a>.</p>
<p>The manifest is a few lines:</p>
<pre class="code" dir="ltr"><code>[package]
name = "slug"
version = "1.1.0"
salam = "&gt;=0.6.1"
kind = "lib"

[dependencies]
"github.com/owner/other" = "v1.0.0"</code></pre>
<ul>
<li><code>name</code> is the program or library name, and <code>version</code> is for people; the version that counts for users is the git tag.</li>
<li><code>salam</code> is the oldest compiler the package builds with. <code>salam add</code> refuses a package that needs a newer one and tells you to run <code>salam upgrade</code>.</li>
<li><code>kind = "lib"</code> marks a library. A program leaves it out.</li>
<li><code>[dependencies]</code> lists what your package needs, in the same form <code>salam add</code> writes. The packages of your packages are found from their own manifests, and when two ask for different versions of one package the newer one is used.</li>
</ul>
<p>Now the code. What you mark <code>pub</code> is the package's public face and a promise to the people who use it; everything else you may rename or delete in any later release. Here <code>Make</code> and <code>MakeMax</code> are public and <code>is_word</code> is not. The two <code>@en</code> and <code>@fa</code> lines give each public function a name in both languages, so Persian programs can call it too:</p>
{{example.package-slug}}
<p>While you work, try the package from a small program beside it. <code>include</code> loads a file of your own project, so this runs without any download:</p>
{{example.package-slug-demo}}
<p>Tests go in a file whose name ends in <code>_test.salam</code>, with functions named <code>test_something</code>. <code>salam test</code> runs every such file in the folder, each in its own process:</p>
{{example.package-slug-test}}
<pre class="code" dir="ltr"><code>$ salam test
=== RUN   test_make
--- PASS: test_make
=== RUN   test_make_max
--- PASS: test_make_max
ok   slug_test.salam: 2 tests passed
PASS: 1 test files</code></pre>
<p>Users see only <code>pub</code> names. From a project that depends on the package, calling the private helper is refused:</p>
<pre class="code" dir="ltr"><code>error[E017]: 'is_word' is not exported by package 'slug' (mark it 'pub')</code></pre>

<h2 id="publish">Publishing it</h2>
<p>There is no upload step and no <code>salam publish</code>. A package is published when a tag exists in a public git repository, because that is what <code>salam add</code> reads. The whole procedure:</p>
<ol>
<li>Put the package in a repository named after it, with the entry file and <code>salam.toml</code> at the top level (or the folder layout above).</li>
<li>Check it: <code>salam test</code> passes, and <code>salam check slug.salam</code> shows no errors.</li>
<li>Write a <code>README.md</code> that shows how to add and import the package and one short example, and add a <code>LICENSE</code> file. Without a licence nobody is allowed to use your code.</li>
<li>Commit, tag the release as <code>vMAJOR.MINOR.PATCH</code>, and push the tag.</li>
</ol>
<pre class="code" dir="ltr"><code>$ git tag v1.1.0
$ git push origin main v1.1.0</code></pre>
<p>From now on anyone can run <code>salam add github.com/owner/slug</code>. Try it yourself in an empty project before you announce the package: it is the same path your users take, and it catches a missing entry file at once.</p>
<p>Packages on gitlab.com and codeberg.org work too, and any host works when git is installed. Private repositories work with the credentials git already has.</p>

<h3>Making it findable</h3>
<p><code>salam search</code> reads <code>registry/index.toml</code> in the <a href="https://github.com/SalamLang/Salam/blob/main/registry/index.toml">Salam repository</a>, a list kept by pull request. Listing is optional, since <code>salam add</code> works for any public repository, but it lets people find the package by its words:</p>
<pre class="code" dir="ltr"><code>[[package]]
name = "github.com/owner/slug"
description = "Turn text into URL slugs"
tags = ["text", "url"]</code></pre>
<p>Open a pull request that appends one such entry. The repository needs a <code>salam.toml</code> and the entry file, and its releases should be tagged <code>vX.Y.Z</code>. After the entry is merged, <code>salam search slug</code> prints the name and description.</p>
<p>The same repository keeps <code>registry/sums.txt</code>, a reviewed list of checksums, one <code>module@version sum</code> line per release. A download that differs from a published line is refused. Inside a project that uses your package, <code>salam deps sums</code> prints the lines to propose in a pull request:</p>
<pre class="code" dir="ltr"><code>$ salam deps sums
github.com/demo/slug@v1.1.0 sha256:f20515bfd08073aebe3d95568695089f8bc7264437e02bad6d87e8b094b9efde</code></pre>

<h2 id="versions">Versions</h2>
<p>A release is a git tag shaped like <code>v1.2.3</code>. Follow the usual meaning: a patch (<code>v1.2.4</code>) fixes bugs, a minor (<code>v1.3.0</code>) adds things without breaking old code, and a major (<code>v2.0.0</code>) may break it. Tags cannot be moved safely once someone has downloaded them, because the checksum in their <code>salam.lock</code> would stop matching. Publish a new version instead.</p>
<p>The version in <code>salam.toml</code> can be written in four ways:</p>
<div class="table-wrap"><table><thead><tr><th>Written as</th><th>Means</th></tr></thead><tbody>
<tr><td><code>"v1.2.0"</code></td><td>exactly that tag</td></tr>
<tr><td><code>"^1.2"</code></td><td>any 1.x from 1.2.0 up (for 0.x, the same minor)</td></tr>
<tr><td><code>"~1.2"</code></td><td>any 1.2.x</td></tr>
<tr><td><code>"&gt;=1.2"</code></td><td>1.2.0 or anything newer</td></tr>
</tbody></table></div>
<p><code>salam add github.com/owner/repo@^1.2</code> writes the range and locks the newest release inside it. The lock file still holds one exact version, so builds stay repeatable until you run <code>salam update</code>.</p>
<pre class="code" dir="ltr"><code>$ salam add github.com/demo/slug@v1.0.0
added github.com/demo/slug v1.0.0
$ salam update
updated github.com/demo/slug v1.0.0 -> v1.1.0</code></pre>
<p><code>salam update</code> never crosses to a new major version by itself. It tells you when one is out and leaves the choice to you:</p>
<pre class="code" dir="ltr"><code>$ salam update
  github.com/demo/slug v2.0.0 is out; it may break your code, move with: salam update github.com/demo/slug@latest
github.com/demo/slug is up to date (v1.1.0)
$ salam update github.com/demo/slug@latest
updated github.com/demo/slug v1.1.0 -> v2.0.0</code></pre>
<p>A repository with no tags at all can still be added. Salam then pins the exact commit with a pseudo version such as <code>v0.0.0-8177964855e1</code>, and <code>salam update</code> moves it to the newest commit. That is handy while a package is young, and a good reason to tag a first release early.</p>
<p>For an author, a major version means a new import address. <code>import "github.com/owner/repo/v2"</code> only accepts v2 tags, so a program can use v1 and v2 side by side. The v2 code may live in a <code>v2/</code> folder or at the root of the repository; to be used next to v1 its entry is named <code>repo2.salam</code> and declares <code>package repo2</code>.</p>

<h2 id="troubleshoot">When something goes wrong</h2>
<div class="table-wrap"><table><thead><tr><th>You see</th><th>Why, and what to do</th></tr></thead><tbody>
<tr><td><code>package '...' has no entry file (looked for '.../argon.salam')</code></td><td>The repository does not follow the layout of the <em>Writing a package</em> section: <code>import "github.com/owner/name"</code> loads <code>name.salam</code> at the top of the repository. <code>salam add</code> succeeds anyway, since it only fetches. Ask the author to add the entry file, or use the files with <code>include</code> as the package's own README says</td></tr>
<tr><td><code>package '...' is not a dependency of this project; run: salam add ...</code></td><td>The import is not listed in <code>salam.toml</code>. Run the command it prints, or work from the project's folder</td></tr>
<tr><td><code>'name' is not exported by package '...' (mark it 'pub')</code></td><td>The package keeps that name private. Use its public API, or ask the author to export it</td></tr>
<tr><td><code>salam: cannot list the versions of https://github.com/...</code></td><td>The address is misspelled, the repository is private without credentials, or git cannot reach the host</td></tr>
<tr><td><code>salam: git could not fetch v9.0.0 from ...</code></td><td>That tag does not exist. Look at the repository's tags, or leave the version out to get the newest</td></tr>
<tr><td><code>no main.salam in '...': a project's entry file must be named main.salam</code></td><td>You ran <code>salam build</code> or <code>salam run</code> outside a project. Start one with <code>salam init</code></td></tr>
<tr><td><code>'...' has no main.salam, so there is no program to install</code></td><td><code>salam install</code> is for programs. A library is used with <code>salam add</code></td></tr>
<tr><td><code>needs Salam X or newer; run: salam upgrade</code></td><td>The package's <code>salam</code> line asks for a newer compiler than yours</td></tr>
</tbody></table></div>
<p>A few more facts that explain surprises:</p>
<ul>
<li>A tag that was moved after release gives a different checksum, and the command stops instead of building different code. If the new copy is the right one, delete its line from <code>~/.salam/pkg/sums.txt</code>.</li>
<li>Without git on the machine, packages from GitHub, GitLab and Codeberg are downloaded as archives. <code>GITHUB_TOKEN</code> raises GitHub's rate limit for listing tags, and <code>SALAM_NO_GIT=1</code> forces the archive route.</li>
<li><code>SALAM_PKG</code> moves the download folder, and <code>salam deps clean</code> empties it.</li>
<li>If a build seems to use old code, delete the project's <code>.salam-build</code> folder and build again.</li>
</ul>
<div class="note"><p>Looking for a model to follow? The standard library packages are written exactly this way, one folder per package with the entry file named after it. Browse them in the <a href="/std/">library reference</a>.</p></div>
