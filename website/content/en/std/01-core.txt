pkg.intro <<
<p>The <code>core</code> package has exactly one function, but an important one. Sometimes a program reaches a point where carrying on makes no sense: data is corrupt, or a condition that "can never happen" has happened. In that case it is better to stop right there with a clear message than to quietly hand back a wrong answer.</p>
<div class="note"><p>For ordinary errors, such as bad input from a user, declare the function <code>throws</code> and <code>throw</code> an <code>Error</code> instead, so that the caller decides what to do with <code>try</code> and <code>catch</code>. A panic is for when there is no correct way to continue, and <code>catch</code> does not stop it.</p></div>
<p><code>core</code> also defines the built-in error types, <code>Error</code> and <code>ErrorKind</code>, which every program can use without an import. The <a href="/std/error/">error package</a> explains how to throw, pass on and catch them.</p>
<h2 id="guide-invariant">Guarding an invariant</h2>
<p>An invariant is something your own code promises is always true: a balance never drops below zero, a list stays sorted, an index stays in range. Checks for ordinary, expected failures return a value the caller can act on. A check for a broken invariant calls <code>Panic</code>, because if it fails the bug is in the program itself and any result computed after that point would be wrong.</p>
{{example.core-guide-invariant}}
<p>Asking for more money than the account holds is an ordinary situation, so <code>withdraw</code> answers <code>false</code>. The <code>Panic</code> after the subtraction can only run if someone later changes the function and breaks it; it is there so that mistake shows up at once, with the owner's name in the message, instead of as a strange number weeks later.</p>

<h2 id="guide-unreachable">Marking code that should never run</h2>
<p>A function that must return a value for every input still needs something at the end, after all the known cases. When the remaining inputs are impossible by design, a <code>Panic</code> with the bad value in the message is the honest way to finish it. A made up return value, such as an empty string, would hide the bug and let it travel further.</p>
{{example.core-guide-unreachable}}
<p>Because <code>Panic</code> never returns, the compiler accepts it as the last statement of a function with a result type. Put the unexpected value into the message: <code>unknown light: blue</code> tells you far more than <code>unreachable</code>.</p>
<p>When the cases are the members of an enum, prefer <code>match</code>: it must cover every member, so the compiler finds the missing case for you and no <code>Panic</code> is needed.</p>

<h2 id="guide-panic-or-result">Panic, or a value that reports failure?</h2>
<p>The two work together. Anything that comes from outside the program, such as user input, files, the network or another service, can be wrong in normal operation, so make the function <code>throws</code> and let the caller decide with <code>try</code> and <code>catch</code>, or return a value that carries the failure, such as an enum you declare yourself with an <code>Err</code> case, or the <code>?</code> operator on one. Once the value has been checked, inner functions may treat a bad value as a programming error and panic.</p>
{{example.core-guide-vs-result}}

<h2 id="guide-what-happens">What a panic does</h2>
<ul>
<li>It writes <code>salam panic: </code> and your message to standard error, then calls the C <code>abort</code>. The process ends with signal <code>SIGABRT</code>, which a shell reports as exit status 134, and the system may write a core dump.</li>
<li><code>defer</code> statements do not run, so open files are not flushed and temporary files stay behind.</li>
<li>Text the program printed before the panic is written out first, even when standard output is a pipe or a file and <code>println</code> was still holding it in its buffer, so the panic message comes after the last printed line.</li>
<li>In a server, one bad request that panics takes down every other request too.</li>
</ul>
<p>That is the main reason to keep <code>Panic</code> for real bugs only.</p>

<h2 id="option">Option: a value that may or may not be there</h2>
<p>Sometimes the answer from a function is "nothing": a search found no match, or a setting was never given. Returning minus one or an empty string for that is convenient, and later forgotten, and then it is a bug. <code>Option&lt;T&gt;</code> makes it explicit: either there is a value of type <code>T</code>, or there is not. <code>T?</code> is short for <code>core.Option&lt;T&gt;</code> and needs no import: a field written <code>timeout: int?</code> may be left out of a literal, plain values wrap on their own, and <code>null</code> means empty. See <a href="/learn/structs/#optional">optional fields</a>.</p>
<div class="note"><ul>
<li><code>Option</code> is a plain struct with two fields, <code>value</code> and <code>present</code>, not an enum: test it with <code>is_some()</code> or <code>.present</code>, not with <code>match</code>, and the <code>?</code> try-operator does not work on it.</li>
<li>Never read <code>.value</code> before checking. On an empty option it is the zero value of <code>T</code>: 0 for numbers, but for a <code>str</code> it is a null pointer, and printing or measuring it crashes the program.</li>
<li>Build options only with <code>Some</code> and <code>None</code> (or plain assignment and <code>null</code> through <code>T?</code>), so the two fields always agree.</li>
<li>The free functions <code>Some</code>, <code>None</code>, <code>IsSome</code>, <code>IsNone</code>, <code>UnwrapOr</code>, <code>Unwrap</code> and <code>Expect</code> need <code>import core</code> and the <code>core.</code> prefix; the methods <code>is_some()</code>, <code>is_none()</code>, <code>unwrap_or(x)</code> and <code>unwrap()</code> on a value already typed <code>T?</code> need neither.</li>
</ul></div>
<h3 id="option-lookup">A lookup that may find nothing</h3>
<p>Looking something up is the classic case for an option. Returning an empty string for a missing phone number would be ambiguous, since an empty value could also be stored on purpose. A function that returns <code>str?</code> says plainly in its signature that the answer may be missing, and every caller has to deal with that.</p>
{{example.core-guide-option-lookup}}
<p><code>is_some()</code> followed by <code>.value</code> suits code that does two different things. When there is a sensible default, <code>unwrap_or</code> does the check and the fallback in one call, as the last line shows.</p>
<h3 id="option-settings">Optional settings with defaults</h3>
<p>An optional field tells "not given" apart from a real zero or an empty string, which a plain <code>int</code> field cannot. Give each optional field <code>null</code> as its default, so a struct literal can leave it out, and apply the real default at the point of use.</p>
{{example.core-guide-option-settings}}
<p>The third line shows why this matters: a width of 0 was given on purpose and is kept, while the first two fall back to 80.</p>
<h3 id="option-first">Searching a list of structs</h3>
<p>A search over a vector returns the first match or nothing. Here the program knows an open task must exist at that moment, so it uses <code>core.Expect</code>: if the assumption is ever wrong, the program stops with that sentence rather than carrying on with an empty name.</p>
{{example.core-guide-option-first}}
<p><code>core.Unwrap</code> stops with a generic message when the option is empty. Prefer <code>core.Expect</code>, whose message tells the reader which assumption failed, and keep it for assumptions that would be a bug in your own program, the same rule as <code>Panic</code> above. When the caller needs to know <em>why</em> something failed rather than just that a value is missing, make the function <code>throws</code> instead, or declare your own enum with an <code>Err</code> case.</p>
>>
