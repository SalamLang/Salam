pkg.intro <<
<p>The <code>core</code> package has exactly one function, but an important one. Sometimes a program reaches a point where carrying on makes no sense: data is corrupt, or a condition that "can never happen" has happened. In that case it is better to stop right there with a clear message than to quietly hand back a wrong answer.</p>
<div class="note"><p>For ordinary errors, such as bad input from a user, use <a href="/std/result/">result</a> instead, so that the caller decides what to do. A panic is for when there is no correct way to continue.</p></div>
<h2 id="guide-invariant">Guarding an invariant</h2>
<p>An invariant is something your own code promises is always true: a balance never drops below zero, a list stays sorted, an index stays in range. Checks for ordinary, expected failures return a value the caller can act on. A check for a broken invariant calls <code>Panic</code>, because if it fails the bug is in the program itself and any result computed after that point would be wrong.</p>
{{example.core-guide-invariant}}
<p>Asking for more money than the account holds is an ordinary situation, so <code>withdraw</code> answers <code>false</code>. The <code>Panic</code> after the subtraction can only run if someone later changes the function and breaks it; it is there so that mistake shows up at once, with the owner's name in the message, instead of as a strange number weeks later.</p>

<h2 id="guide-unreachable">Marking code that should never run</h2>
<p>A function that must return a value for every input still needs something at the end, after all the known cases. When the remaining inputs are impossible by design, a <code>Panic</code> with the bad value in the message is the honest way to finish it. A made up return value, such as an empty string, would hide the bug and let it travel further.</p>
{{example.core-guide-unreachable}}
<p>Because <code>Panic</code> never returns, the compiler accepts it as the last statement of a function with a result type. Put the unexpected value into the message: <code>unknown light: blue</code> tells you far more than <code>unreachable</code>.</p>
<p>When the cases are the members of an enum, prefer <code>match</code>: it must cover every member, so the compiler finds the missing case for you and no <code>Panic</code> is needed.</p>

<h2 id="guide-panic-or-result">Panic or Result?</h2>
<p>The two work together. Anything that comes from outside the program, such as user input, files, the network or another service, can be wrong in normal operation, so it goes through <a href="/std/result/">result</a> and the caller decides what to do. Once the value has been checked, inner functions may treat a bad value as a programming error and panic.</p>
{{example.core-guide-vs-result}}
<div class="table-wrap"><table>
<thead><tr><th>Situation</th><th>Use</th></tr></thead>
<tbody>
<tr><td>The user typed something invalid</td><td><code>Result</code> with an error message</td></tr>
<tr><td>A file or server is missing</td><td><code>Result</code>, or the <code>Error</code> out-parameter of that package</td></tr>
<tr><td>A value may be absent</td><td><a href="/std/option/">option</a></td></tr>
<tr><td>Your own code broke a rule it promised to keep</td><td><code>Panic</code></td></tr>
<tr><td>A case that cannot happen by design</td><td><code>Panic</code>, or <code>match</code> on an enum</td></tr>
</tbody>
</table></div>
<h2 id="guide-what-happens">What a panic does</h2>
<ul>
<li>It writes <code>salam panic: </code> and your message to standard error, then calls the C <code>abort</code>. The process ends with signal <code>SIGABRT</code>, which a shell reports as exit status 134, and the system may write a core dump.</li>
<li><code>defer</code> statements do not run, so open files are not flushed and temporary files stay behind.</li>
<li>Text the program printed shortly before the panic can be lost when standard output is a pipe or a file, because <code>println</code> keeps it in a buffer that the panic does not write out. In a terminal every line appears. If the last lines matter, for example in a log a CI job reads, print them with <code>printerrln</code>, which is not buffered.</li>
<li>In a server, one bad request that panics takes down every other request too.</li>
</ul>
<p>That is the main reason to keep <code>Panic</code> for real bugs only.</p>
