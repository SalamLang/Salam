pkg.intro <<
<p>Sometimes the answer from a function is "nothing": a search found no match, or a setting was never given. Returning minus one or an empty string for that is convenient, and later forgotten, and then it is a bug. <code>Option&lt;T&gt;</code> makes it explicit: either there is a value of type <code>T</code>, or there is not.</p>
<p>If the reason for the failure matters as well as its absence, <a href="/std/result/">result</a> is the better fit.</p>
<p>Unlike <code>Result</code>, <code>Option</code> is a plain struct with two fields, <code>value</code> and <code>present</code>, not an enum. That shapes how you use it:</p>
<div class="note"><ul>
<li>You test it with <code>IsSome</code> or <code>.present</code>, not with <code>match</code>, and the <code>?</code> operator does not work on it.</li>
<li>Never read <code>.value</code> before checking. On an empty option it is the zero value of <code>T</code>: 0 for numbers, but for a <code>str</code> it is a null pointer, and printing or measuring it crashes the program.</li>
<li>Build options only with <code>Some</code> and <code>None</code>, so the two fields always agree.</li>
</ul></div>
<h2 id="guide-lookup">A lookup that may find nothing</h2>
<p>Looking something up is the classic case for an option. Returning an empty string for a missing phone number would be ambiguous, since an empty value could also be stored on purpose. A function that returns <code>Option&lt;str&gt;</code> says plainly in its signature that the answer may be missing, and every caller has to deal with that.</p>
{{example.option-guide-lookup}}
<p><code>IsSome</code> followed by <code>.value</code> suits code that does two different things. When there is a sensible default, <code>UnwrapOr</code> does the check and the fallback in one call, as the last line shows.</p>

<h2 id="guide-settings">Optional settings with defaults</h2>
<p>An option field tells "not given" apart from a real zero or an empty string, which a plain <code>int</code> field cannot. Give each option field the empty option as its default, so a struct literal can leave it out, and apply the default at the point of use.</p>
{{example.option-guide-settings}}
<p>The third line shows why this matters: a width of 0 was given on purpose and is kept, while the first two fall back to 80. The field default needs the type written out, <code>option.None() as option.Option&lt;int&gt;</code>, because a struct field gives <code>None</code> nothing to infer its type from. In a function body the return type does that job, so a plain <code>option.None()</code> is enough there.</p>

<h2 id="guide-first">Searching a list of structs</h2>
<p>A search over a vector returns the first match or nothing. Here the program knows an open task must exist at that moment, so it uses <code>Expect</code>: if the assumption is ever wrong, the program stops with that sentence rather than carrying on with an empty name.</p>
{{example.option-guide-first}}
<p>The option here holds the task's name. To change the task itself, return its index as <code>Option&lt;int&gt;</code> instead and write through <code>tasks.set</code>.</p>

<h2 id="guide-option-or-result">Option or Result?</h2>
<div class="table-wrap"><table>
<thead><tr><th>Situation</th><th>Use</th></tr></thead>
<tbody>
<tr><td>The value is missing, and that is normal</td><td><code>Option</code></td></tr>
<tr><td>Something went wrong and the caller needs to know what</td><td><a href="/std/result/">result</a></td></tr>
<tr><td>Missing would be a bug in your program</td><td><code>Expect</code> with a clear message</td></tr>

</tbody>
</table></div>
<p><code>Unwrap</code> stops with a generic message when the option is empty. Prefer <code>Expect</code>, whose message tells the reader which assumption failed.</p>

doc.Option = A struct that keeps a value and a "present or not" flag side by side. Build one with <code>Some</code> or <code>None</code>, so that the two fields always agree.
doc.Option.value = The value itself. When <code>present</code> is false this is the zero value of <code>T</code>; for a <code>str</code> that is a null pointer that crashes when used, so check <code>present</code> first.
doc.Option.present = True when there is a value.
doc.Some = Builds an option that holds a value.
doc.None = Builds an empty option. The type <code>T</code> comes from where the value is used, such as the return type of the function.
doc.IsSome = Returns true when the option holds a value.
doc.IsNone = Returns true when the option is empty.
doc.UnwrapOr = Returns the value, or the default you supplied when the option is empty.
doc.Unwrap = Returns the value. If the option is empty, the program stops with the panic <code>called Unwrap on a None value</code>.
doc.Expect = Like <code>Unwrap</code>, but stops with a message of your own when the option is empty; a good message makes the problem easy to find.
