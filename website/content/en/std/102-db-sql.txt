pkg.intro <<
<p>A query is a string, so a typo in it is found by the database, at run time, on the one code path nobody tested. This package reads the string instead: it lexes and parses SQL for one of four dialects, and when you hand it your schema it also resolves every table and column, names the ones that do not exist, and tells you the type of every placeholder and every column that comes back. Nothing here connects to a database; it is all static, so it belongs in a test or in a build step.</p>
<p>It is the same idea as sqlc in Go, with the schema taken from the SQL you already write: the <code>CREATE TABLE</code> statements in your migrations are the catalog, so there is no second file to keep in step.</p>
<div class="note"><p>Things that catch people out:</p>
<ul>
<li>The dialect is not advice. <code>?</code> is a placeholder in SQLite and MySQL and a plain operator in PostgreSQL, which numbers its own as <code>$1</code>; <code>"name"</code> is a quoted name everywhere except MySQL, where it is a string; <code>AUTOINCREMENT</code>, <code>AUTO_INCREMENT</code> and <code>GENERATED ... AS IDENTITY</code> belong to one engine each. Pass the dialect you will really run against.</li>
<li><code>Check</code> only resolves names when the statement parses. A report with a syntax error in it says nothing about the columns, so fix the syntax first and run it again.</li>
<li>A table whose columns are not known, from <code>CREATE TABLE ... AS SELECT</code> or a view the package could not read, is left open: columns on it are never reported as missing. No news is not always good news.</li>
<li><code>Apply</code> reads the DDL in order, so a view has to come after the tables it selects from, exactly as it does in the database.</li>
<li>Diagnostic messages are English in both language modes; the codes are the same, so a Persian program can match on <code>code</code>.</li>
<li><code>Placeholders</code> hands back a <code>Vector&lt;str&gt;</code> you own: free the vector, and the strings in it, when you are done.</li>
<li>Salam lets a name contain spaces; SQL does not. <code>SELECT family name FROM t</code> is a column and an alias, not one name, and it is accepted without complaint - which is worth knowing when the names are Persian, since those are often two words. Quote them: <code>SELECT "family name" FROM t</code>.</li>
</ul></div>
<h2 id="guide-walk">Start here: one walk from a schema to checked queries</h2>
<p>The six sections after this one take the package apart piece by piece. This one puts it together, in the order you would actually meet it on a project that already has a database and a pile of query strings. The program below is the whole arc, and you can run it as it stands - no server, no connection, nothing to set up.</p>
{{example.db-sql-tutorial}}
<p><strong>Step 1 is the only setup there is.</strong> You do not write a schema description for this package; you hand it the <code>CREATE TABLE</code> statements you already have. Point <code>Apply</code> at your migration files in order and the catalog is the schema your program really runs against.</p>
<p><strong>Step 2 is why you came.</strong> Five queries of the kind that live in every codebase, and five different ways of being wrong: a column name remembered in the plural, a column that belongs to the other table in the join, an INSERT that leaves out a NOT NULL column with no default, a number compared against a quoted word, and a DELETE with no WHERE. Each one is found without a database, and each one names what to do about it. The last is a warning rather than an error, because sometimes clearing a table is the intent - the point is that you decide, in a review, rather than at two in the morning.</p>
<p><strong>Step 3 is the same five, put right</strong>, and it is worth running your own queries through this pair of steps once before reading any further. The quickest way is the command: <code>salam sql check src --schema=db</code> reads the SQL out of your <code>.salam</code> files as well as your <code>.sql</code> ones.</p>
<p><strong>Step 4 is where it stops being a linter.</strong> Once the names resolve, the types follow: the placeholder is an <code>option.Option&lt;i64&gt;</code> because <code>year</code> can be null, <code>title</code> is a plain <code>str</code> because the column is NOT NULL. That is the signature your code should have, derived from the schema instead of remembered.</p>
<p><strong>Step 5 is the one that prevents the oldest bug in the book.</strong> <code>Fill</code> writes the values into the query with the quoting the engine wants - note what happens to the apostrophe in <code>O'Brien</code> - and because the query was lexed first, a <code>?</code> that lives inside a string is left alone.</p>
<p><strong>Step 6 is the part you can stop writing by hand.</strong> Annotate a query with a name and a kind and the generated function has the parameters and the row struct that step 4 worked out. Run it with <code>salam sql generate queries --schema=db --output=gen/store.salam</code>.</p>
<p>Two things to carry away. The schema is the DDL you already have, so nothing can drift out of step with it. And every one of these checks happens before the program runs, which is the only time a query mistake is cheap.</p>

<h2 id="guide-lint">Reading a query without a database</h2>
<p><code>Lint</code> parses one statement, or a whole script of them separated by <code>;</code>, and returns a <code>Report</code>. <code>r.ok</code> is false as soon as there is an error; <code>ReportText</code> renders the whole list the way a compiler would, with the line, the column, the message and a help line. Most of the dialect rules are in here: the same string is fine for SQLite and wrong for PostgreSQL, and the report says which part of it to change.</p>
{{example.db-sql-guide-lint}}
<p>The compiler ships the same checks as a command, so a whole project can be
checked without writing a program for it: <code>salam sql check src --schema=db</code>
reads the <code>.sql</code> files under <code>src</code>, and the SQL string literals out of
its <code>.salam</code> files, and reports them with the position in the Salam source. Without
<code>--dialect</code> each Salam file is read with the engine it imports, so a tree that mixes
<code>db/sqlite</code> and <code>db/mysql</code> is checked correctly with no flags at all. A
query assembled from pieces - glued with <code>+</code> or <code>.concat</code>, or any literal whose
only fault is that it stops in the middle - is a fragment rather than a statement, so it is
counted and skipped instead of being reported as a syntax error. The count is in the summary,
so nothing is checked silently; a fragment is also the reason to bind values as placeholders
instead of pasting them in.</p>
<p>Every diagnostic carries a code. <code>SQL0xx</code> is lexical, <code>SQL1xx</code> is syntax, <code>SQL2xx</code> is a dialect rule, <code>SQL3xx</code> is a name or a count that does not match the schema. Match on the code when you want to allow one particular thing; never match on the message.</p>

<h2 id="guide-catalog">Your migrations are the schema</h2>
<p><code>Apply</code> runs DDL into a <code>Catalog</code>: <code>CREATE TABLE</code> adds a table with its columns, their types, their NOT NULL and PRIMARY KEY, <code>ALTER TABLE</code> adds, drops and renames, <code>DROP</code> removes, and <code>CREATE VIEW</code> records the view's columns. Feed it the same strings you give <code>db.AddMigration</code> and the catalog is the schema the program really has.</p>
{{example.db-sql-guide-catalog}}
<p>With a catalog, <code>Check</code> resolves names: an unknown column or table is an error with the closest real name offered, a column that two joined tables both have is an error until you qualify it, an INSERT is checked against the column list and against the columns that are NOT NULL with no default, and an UPDATE or DELETE with no WHERE is a warning, because that is almost never what was meant.</p>
<p>It also reads the types it has: comparing a numeric column with a quoted value that is not a number is a warning on SQLite and MySQL, where it silently never matches or silently becomes zero, and an error on PostgreSQL, which refuses it; a column in the result list of a GROUP BY query that is neither grouped nor aggregated is an error on PostgreSQL and a warning elsewhere, with the same exception those engines make - grouping by a table's whole primary key determines the rest of that table's columns, so they are allowed unqualified; and <code>USING (col)</code> is checked on both sides of the join. A subquery that returns
the wrong number of columns for the comparison it sits in, an <code>ORDER BY 3</code> when the
statement returns two columns, a <code>LIMIT</code> that is not a number, an aggregate in
<code>WHERE</code> rather than <code>HAVING</code>, the same column assigned twice in one
<code>SET</code>, and two result columns given the same alias are all reported too.</p>

<h2 id="guide-fill">Putting the values in safely</h2>
<p>The three SQL drivers do not all offer prepared statements - only <a href="/std/db/sqlite/">db/sqlite</a> has <code>Prepare</code> and <code>Bind*</code> - so code that has to run on MySQL or PostgreSQL ends up gluing values into the SQL by hand, which is where quoting mistakes become injections. <code>Fill</code> does that one job properly: it lexes the query, so it knows which <code>?</code> is a placeholder and which one is a character inside a string, checks that the number of values matches, and writes each value the way the dialect wants it.</p>
{{example.db-sql-guide-fill}}
<p>A text value is wrapped in single quotes with every quote doubled, and on MySQL a backslash is doubled as well, because MySQL reads backslashes as escapes and the other two do not. A boolean is <code>1</code> or <code>0</code> on SQLite and MySQL and <code>TRUE</code> or <code>FALSE</code> on PostgreSQL; a null is <code>NULL</code>; numbers are written plainly. The <code>'?'</code> in the fourth query stays as it was, which a search-and-replace over the string would have got wrong.</p>
<p>This is substitution, not a prepared statement: the database still parses one complete statement, and there is no plan reuse. Where the driver can prepare and bind, as sqlite can, that is still the better tool. Where it cannot, this is the safe way to get the values in, and it is one audited function rather than a quoting rule repeated at every call site.</p>

<h2 id="guide-analyze">The type of every placeholder</h2>
<p><code>Analyze</code> does everything <code>Check</code> does and also hands back what the query takes and what it returns. Each <code>Param</code> says which column it was compared with, in which table, and the type that column has; each <code>ResultCol</code> says the name the column comes back under, its type, and whether it can be null. <code>SalamType</code> turns that into the Salam type to read it into, so a LEFT JOIN gives you <code>option.Option&lt;i64&gt;</code> where an inner join gives you <code>i64</code>.</p>
{{example.db-sql-guide-analyze}}
<p>That is enough to generate the binding code for a query, or to assert in a test that a query still takes and returns what the code around it believes. Placeholders are numbered in the order they appear, which is the order the driver binds them; for PostgreSQL the ordinal is the number in the <code>$n</code> itself, and a gap in those numbers is an error of its own.</p>

<h2 id="guide-generate">Generating the query functions</h2>
<p>With the schema and the analysis in place, the last step is mechanical, so the package does it: annotate a <code>.sql</code> file the way sqlc does and <code>Generate</code> writes the Salam for it - a row struct per query, a typed function per query, each one checked against the schema as it is generated.</p>
{{example.db-sql-guide-generate}}
<p>The kinds are <code>:one</code> (the first row, with an <code>ok &amp;: bool</code> out parameter), <code>:many</code> (a <code>Vector</code> of rows), <code>:exec</code> (a bool) and <code>:execrows</code> (the number of rows changed). Parameters are named after the column each placeholder is compared with and typed from it; a column that can be null comes back as <code>option.Option&lt;T&gt;</code> and is read through <code>IsNull</code>. A query that does not resolve against the schema stops the generation with the query's name in the message, so a typo never reaches the generated file.</p>
<p>The command is <code>salam sql generate queries --schema=db --output=gen/store.salam --package=store</code>. The generated file takes a <code>dyn db.Connection</code>, so one set of functions serves SQLite, MySQL and PostgreSQL, and it picks each dialect's quoting from <code>c.Kind()</code> at run time.</p>
