pkg.intro <<
<p>A target triple, such as <code>x86_64-unknown-linux-gnu</code>, names the architecture, the vendor, the operating system and the environment. Without linking against LLVM, this package gives from it what a compiler needs before it generates code, such as the pointer size and the data layout.</p>
<p>The parts are separated by dashes and the later ones may be missing: <code>x86_64-linux-musl</code> has no vendor, and <code>aarch64-apple-darwin</code> no environment. The functions here only read the text, so they work the same on every machine and for targets you cannot run, which is what a cross compiler needs. Salam's own LLVM backend uses them to pick the data layout and the C library of the target. To create a real LLVM target machine for a triple, use <a href="/std/llvm/"><code>llvm</code></a>.</p>
<h3>Things to know</h3>
<ul>
<li>The functions look for known words anywhere in the triple, such as <code>x86_64</code>, <code>windows</code> or <code>musl</code>. They do not validate it: a misspelled triple quietly gets the wrong answer.</li>
<li>An empty triple means the host machine. So does an architecture <code>PointerBits</code> does not know: it falls back to the host's pointer size instead of reporting an error.</li>
<li><code>Datalayout</code> knows x86-64 (Linux, Windows and macOS), 32 bit x86 outside Windows and macOS, AArch64, RISC-V 64 and 32 bit ARM. For anything else, WebAssembly included, it returns an empty string. Windows on ARM gets the Linux AArch64 layout.</li>
<li><code>IsGlibc</code> means "Linux and not musl". An Android triple such as <code>aarch64-linux-android</code> contains <code>linux</code>, so it counts as glibc although Android uses Bionic.</li>
</ul>

<h2 id="guide-sizes">Laying out a struct for another target</h2>
<p>The size of a pointer decides the size of every struct that holds one, and therefore every offset a code generator writes. <code>PointerBits</code> gives it for any triple. The program below lays out a list node with a name pointer, a 32 bit age and a next pointer, aligning each field to its own size as C does.</p>
{{example.llvm-triple-guide-sizes}}
<p>The node is twice as big on 64 bit targets: two eight byte pointers plus a four byte integer padded to eight. On a 32 bit target, WebAssembly included, every field is four bytes and nothing is padded. For an exact answer for every type, give the string from <code>Datalayout</code> to LLVM, as the <a href="/std/llvm/"><code>llvm</code></a> package does.</p>

<h2 id="guide-output">Choosing the file name and libc</h2>
<p>A build tool makes a few decisions straight from the triple: Windows programs end in <code>.exe</code>, a glibc program needs a compatible glibc wherever it runs, and a musl program can be linked fully static and copied to any Linux machine. <code>IsWindows</code> and <code>IsGlibc</code> answer the first two; anything else can be read from the triple with <a href="/std/str/"><code>str</code></a>.</p>
{{example.llvm-triple-guide-output}}
<p>When <code>Datalayout</code> returns an empty string the target is one this package does not know. That is not an error: leave the data layout out of the module and LLVM fills in its own default for the triple.</p>

<h2 id="guide-layout">What the package knows about a target</h2>
<p>This program asks every function about six targets. The first letter of a data layout string is the byte order: <code>e</code> for little endian, <code>E</code> for big endian. The rest lists the size and alignment of pointers and integer types, in LLVM's own format.</p>
{{example.llvm-triple-guide-layout}}
<p>Two answers deserve a second look. WebAssembly has no built-in layout, so its byte order is unknown here even though WebAssembly is little endian. Android reports <code>glibc: true</code>; a build tool that ships Android binaries should test for <code>android</code> itself before it trusts <code>IsGlibc</code>.</p>
>>

doc.HostDatalayout = The data layout of the host machine.
doc.Datalayout = The LLVM data layout string for the triple: the byte order, the pointer size and the alignment of the types; empty for a target it does not know, such as WebAssembly. An empty triple gives the host layout.
doc.PointerBits = The pointer size of the target in bits: 64, 32, or 16 for AVR and MSP430. An empty or unknown triple gives the host's size.
doc.IsWindows = The triple names Windows, MinGW or Win32; an empty triple asks about the host.
doc.IsGlibc = The target is Linux and not musl, macOS, Windows or WebAssembly. Android triples also count as glibc. False for an empty triple.
