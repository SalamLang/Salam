pkg.intro <<
<p>This package opens a native desktop window around HTML, and builds a whole desktop application on top of it, the kind you would build with Tauri or Electron, with no Rust and no second language. There are two levels in one package. The low level is a small window: you create it, show a page with <code>SetHTML</code> or <code>Navigate</code>, and <code>Run</code> keeps it open until the user closes it. The application level starts with <code>Init</code> and adds commands the page can call, events in both directions, packaged files, dialogs, notifications, the keychain, tray icons, menus, a single-instance lock and installers made by <code>salam bundle</code>.</p>
<p>The interface is HTML, CSS and JavaScript. By default it runs in the web view the operating system already has, like Tauri: WebView2 on Windows, WKWebView on macOS and WebKitGTK on Linux, so the program stays one small native executable. The engine is chosen when the program is built; see <a href="#guide-engine">choosing the web engine</a> for the Chromium option.</p>
<p>A page calls your Salam code with <code>salam.invoke</code>, which returns a promise. Pages can come from three places: files packed inside the executable, so nothing sits in a folder for users to edit; a remote site; or an HTML string. Use it for a small desktop tool, a viewer for data your program computed, or a native window around a web interface your program serves. For pages that run in the user's own browser, see <a href="/std/dom/">dom</a>; to generate the HTML, see <a href="/std/template/">template</a>.</p>
<h3>How data moves, and what does not work</h3>
<ul>
<li><strong>Put the data in the page.</strong> The reliable way to give the page your data is to write it into the HTML you pass to <code>SetHTML</code>, as JSON inside a <code>&lt;script&gt;</code>.</li>
<li><code>Init</code> installs a script for every page loaded later, before the page's own scripts run. <code>Eval</code> runs once, on whatever page is loaded at that moment.</li>
<li>Pages load in the background, so code sent with <code>Eval</code> right after <code>SetHTML</code> or <code>Navigate</code> can run before the new page exists. Use <code>Init</code>, or wait for <code>OnLoad</code>.</li>
<li>The page can talk back with <code>OnMessage</code>. For a whole application, with commands, events, packaged files and installers, use the application functions such as <code>Init</code>, <code>Command</code> and <code>Open</code>, described in the guides further down.</li>
<li><code>Create</code> reports failure by returning a window that is already closed; check <code>IsClosed()</code> right after it, for example on a Linux server with no display.</li>
</ul>
<h3>What pages may do</h3>
<ul>
<li><strong>Local pages may run every command.</strong> Remote sites get nothing until you name them with <code>Allow</code>, command by command if you like.</li>
<li>The bridge exists only in the top frame of an allowed origin, and every message carries a secret made for this run, so a frame or another site cannot call you. Answers carry the origin they belong to, so they never reach a page that replaced it.</li>
<li>A link to any other site opens in the system browser. On Linux the engine cannot tell a frame from the page, so a cross-origin frame there needs its origin in <code>allow_navigation</code>.</li>
<li>Files inside the executable are compressed and scrambled, which keeps them out of sight. They are not secret: anything a page can read, a determined user can extract. Keep real secrets on your server.</li>
</ul>
<p>A window needs a desktop session, so the site only compiles these programs; run them on your own machine with <code>salam run</code>. On Linux install <code>libgtk-3-dev</code> and <code>libwebkit2gtk-4.1-dev</code> (WebKitGTK 4.1) first. Windows 10 and 11 already ship WebView2, and macOS ships WKWebView. Building for another system needs nothing extra: <code>--target</code> works from any machine.</p>

<h2 id="guide-report">Showing data your program computed</h2>
<p>The simplest desktop program builds an HTML string and shows it. Everything the page needs, the style sheet included, can travel in that one string, so there are no files to ship next to the executable. <code>HINT_FIXED</code> keeps the window at the size you chose, which suits a small dialog like this order summary.</p>
{{example.gui-webview-guide-report}}
<p>The item names go into the HTML as they are. When the text comes from a user or a file, pass it through <code>EscapeHTML</code> from <a href="/std/template/"><code>template</code></a> first, or a name with a <code>&lt;</code> in it breaks the page.</p>

<h2 id="guide-data">Handing structured data to the page</h2>
<p>For anything bigger than a table, let JavaScript draw the page and give it the data as JSON. <code>Marshal</code> from <a href="/std/encoding/json/"><code>encoding.json</code></a> turns a vector of structs into a JSON array whose keys are the field names, and that text goes straight into a <code>&lt;script&gt;</code> in the page. The script runs as the page loads, so the data is there before anything is drawn.</p>
{{example.gui-webview-guide-data}}
<p>JSON is valid JavaScript, so no parsing step is needed. One caution: if a value could contain the text <code>&lt;/script&gt;</code>, it would end the script early; replace <code>&lt;/</code> with <code>&lt;\/</code> in the JSON first when the data comes from users.</p>

<h2 id="guide-launch">Opening a site or a local server</h2>
<p><code>Navigate</code> loads an address instead of a string, so the window can show a remote site or a web interface your own program serves on <code>127.0.0.1</code>. This one takes the address from the command line, so <code>salam run webview-guide-launch.salam http://127.0.0.1:8000</code> wraps a local development server in a native window.</p>
{{example.gui-webview-guide-launch}}
<p><code>Run</code> blocks until the user closes the window; the lines after it are where you save state and clean up. Call <code>Destroy</code> once at the end in every case. <code>Terminate</code> makes <code>Run</code> return at its next turn; on Linux and Windows that turn only comes with the next window event, such as a mouse move. On macOS it quits the whole application instead, so the lines after <code>Run</code> do not run there.</p>

<h2 id="guide-start">An application with a page and a command</h2>
<p>While developing, <code>assets_dir</code> serves your folder directly, so a reload shows your edits. Without it the files inside the executable are used.</p>
{{example.gui-webview-guide-start}}
<p>The page calls it like any other async function:</p>
<pre><code>const text = await salam.invoke("greet", { name: "Sara" });
const stop = salam.listen("saved", (data) =&gt; console.log(data));
salam.emit("ready", {});</code></pre>
<p>A command normally runs on the UI thread, so keep it short. Register slow work with <code>CommandAsync</code>; the page stays responsive and <code>Resolve</code> is safe from the worker.</p>

<h2 id="guide-commands">Commands, errors and slow work</h2>
<p>Arguments arrive as JSON. <code>Str</code>, <code>Int</code> and <code>Bool</code> read one by name and <code>Has</code> tells you whether the page sent it. Finish every call exactly once: with one <code>Resolve</code> method, or with <code>Reject</code>, which makes the page's promise throw an error carrying your message. A second answer is ignored.</p>
<p>A <code>Command</code> runs on the UI thread, so a slow one freezes the window. Register it with <code>CommandAsync</code> and it runs on a worker, where <code>Resolve</code> is safe to call later. Every window call belongs on the UI thread, so a worker hands such work to <code>Dispatch</code>.</p>
{{example.gui-webview-guide-commands}}
<pre><code>try {
  const sum = await salam.invoke("add", { a: 40, b: 2 });
  const report = await salam.invoke("report", { name: "March" });
} catch (e) {
  console.log(e.message);
}</code></pre>

<h2 id="guide-windows">Windows, events and menus</h2>
<p><code>Open</code> can be called many times. Give each window a <code>label</code> and find it again with <code>GetWindow</code>. <code>Emit</code> on a window reaches only that window, and <code>desktop.Emit</code> reaches all of them. <code>OnClose</code> runs when the user closes a window: return false and the window stays, which is the place to ask about unsaved work.</p>
{{example.gui-webview-guide-windows}}
<p>A menu is a list of items made with <code>Item</code>, <code>Separator</code> and <code>Submenu</code>. Every click arrives in <code>OnMenu</code> with the item's id, whichever menu it came from.</p>

<h2 id="guide-services">Dialogs, notifications, secrets and the tray</h2>
<p>These calls use whatever the system provides, so the same program behaves natively on each system. File dialogs return an empty string when the user cancels. <code>SecretSet</code> and <code>SecretGet</code> keep a small value, such as a login token, in the keychain instead of a file in your data folder. <code>SingleInstance</code> returns false when the program is already running, and the running copy gets the new arguments in its callback.</p>
{{example.gui-webview-guide-services}}
<p>Keep in mind that a page can call a command only if it is allowed to. Local pages may call all of them. If you load a remote site, list the dangerous commands, such as <code>choose_folder</code> above, only for origins you trust.</p>

<h2 id="guide-remote">A window around a website</h2>
<p>Give <code>url</code> an address to wrap a site you already run, and use <code>Allow</code> to give that one site access to chosen commands. Your local error page can stay in the assets.</p>
{{example.gui-webview-guide-remote}}

<h2 id="guide-bundle">Making installers</h2>
<p>Describe the application in <code>salam.toml</code> and run <code>salam bundle</code>. The same command works from any system with <code>--target</code>, and the assets folder goes inside the application.</p>
<pre><code>[app]
id = "com.example.notes"
name = "Notes"
version = "1.0.0"
assets = "www"
icon = "icon.png"
description = "Take notes"

$ salam bundle
$ salam bundle --target=x86_64-w64-windows-gnu
$ salam bundle --target=arm64-apple-macos</code></pre>
<p>On Linux you get a tar archive and a deb package, on Windows a zip with a windowed executable, on macOS an <code>.app</code>. <code>--format</code> also offers rpm, AppImage, NSIS and dmg, which need <code>rpmbuild</code>, <code>appimagetool</code>, <code>makensis</code> and <code>hdiutil</code>. Code signing is up to you.</p>

<h2 id="guide-debug">When something does not work</h2>
<ul>
<li>If <code>Open</code> gives a closed window, <code>LastError</code> says why. A missing WebKitGTK or WebView2 runtime shows up here.</li>
<li>A window that opens blank: set <code>SALAM_WEBVIEW_TRACE</code> to a file name and run again. Each line is one step: how the engine started, each navigation, resource and message, and every message the bridge refused. It also works in a program with no console.</li>
<li>Set <code>debug = true</code> in <code>Config</code> and call <code>OpenDevTools</code> on the window to use the developer tools of the engine.</li>
<li>A command that never answers leaves the page's promise pending forever. Make sure every path ends in a <code>Resolve</code> method or <code>Reject</code>.</li>
</ul>

<h2 id="guide-engine">Choosing the web engine</h2>
<p>The engine is chosen when your program is <strong>built</strong>, not when it runs. By default a program uses the web view of the operating system: WebView2 on Windows, WKWebView on macOS and WebKitGTK on Linux. That is what keeps the executable small, and it is the engine every guide above assumes. Because the web view comes with the system, the same page can look slightly different from one system to another.</p>
<p>For the same engine everywhere you can build against Chromium Embedded Framework (CEF) instead. Build the program with the <code>-DSALAM_WEBVIEW_CEF</code> flag, or let <code>salam bundle</code> do it: set <code>engine = "chromium"</code> and <code>runtime = "dir"</code> in the <code>[app]</code> table of <code>salam.toml</code>, or pass <code>--engine=chromium</code> and <code>--runtime=DIR</code> (the <code>SALAM_CEF_DIR</code> environment variable works too). The runtime folder holds the built <code>salam_webview_cef</code> library, <code>salam_cef_helper</code> and the CEF runtime files (see <code>std/gui/webview/native/CMakeLists.txt</code> in the Salam repository for how to build them). It is copied next to the program, and only for tar on Linux and zip on Windows.</p>
<p>A program can ask which engine it got. <code>Engine</code> returns <code>ENGINE_SYSTEM</code> (<code>"system"</code>) or <code>ENGINE_CHROMIUM</code> (<code>"chromium"</code>), <code>EngineName</code> returns a name for people to read (WebKitGTK, WebView2, WKWebView or Chromium Embedded Framework), and <code>SupportsCommands</code> says whether commands work.</p>
{{example.gui-webview-guide-engine}}
<p><strong>Be aware of the limits.</strong> With the Chromium engine today, windows open and pages load, but commands, events, custom schemes and the system services (dialogs, notifications, keychain, tray) are not available yet, and <code>SupportsCommands()</code> returns false. Full parity with the system engine is planned. If your program depends on <code>salam.invoke</code>, build it with the default engine for now, or check <code>SupportsCommands()</code> and fall back.</p>
