pkg.intro <<
<p>A regular expression is a small language for describing the shape of text; <code>[0-9]+</code> means "one or more digits". With one you can ask whether text matches a pattern, find every place it matches, and pull pieces out or replace them.</p>
<p>Every function comes in two forms: one takes a <code>Regex</code> made with <code>Compile</code>, and its twin whose name ends in <code>Str</code> takes the pattern as text. They do the same work. <code>Compile</code> only stores the pattern, and every call parses it again, so a <code>Regex</code> value is about naming the pattern once, not about speed.</p>
<p>Use it for patterns: validation, pulling fields out of log lines, rewriting. For a fixed piece of text, the plain functions of <a href="/std/str/">str</a> (<code>Contains</code>, <code>Index</code>, <code>Replace</code>, <code>Split</code>) are simpler and faster. For whole-word, Unicode-aware work on Persian text, see <a href="/std/unicode/">unicode</a>.</p>
<p>Parentheses in a pattern make a "group", and <code>(?P&lt;name&gt;...)</code> makes a named one. Group zero is the whole match. In a replacement, <code>$1</code> and <code>$2</code> stand for the groups.</p>
<h3>Limits that cause surprises</h3>
<ul>
<li><strong>The engine works on bytes.</strong> <code>.</code> and every class match one byte, so <code>\w</code> never matches a Persian letter, a range such as <code>[آ-ی]</code> does not work, and <code>ب+</code> repeats only the last byte of <code>ب</code>. Put a Persian letter in a group to repeat it, <code>(ب)+</code>, or use a negated class such as <code>[^ ]+</code>. Literal Persian words and alternatives such as <code>(تهران|شیراز)</code> work.</li>
<li>No <code>\b</code> (it means the letter <code>b</code>), no <code>(?i)</code>, no lookahead and no back references (<code>\1</code> means the digit 1). <code>^</code> and <code>$</code> are the start and end of the whole text, never of a line.</li>
<li>At most 16 groups, and a repeat count of at most 64: <code>a{100}</code> is an invalid pattern.</li>
<li>An invalid pattern does not stop the program; it just never matches. Check patterns you did not write with <code>IsValid</code>.</li>
<li>A match that would take more than 400000 steps is given up and reported as no match. Nested repetition such as <code>(a+)+</code> on long input can hit that limit.</li>
<li>The functions keep state in globals, so do not use this package from several threads at once.</li>
</ul>
<h2 id="guide-validate">Checking input</h2>
<p>The most common job is deciding whether a value has the right shape: an email address, a phone number, a postal code. <code>Match</code> is true when the pattern matches <em>anywhere</em> in the text, so a pattern used for validation must start with <code>^</code> and end with <code>$</code>; otherwise <code>"abc 09121234567 xyz"</code> would pass as a phone number. Giving each pattern a name with <code>Compile</code>, outside the loop or the request handler, keeps them in one place.</p>
{{example.regex-guide-validate}}
<p>A pattern like this checks shape, not truth: an address that passes may still not exist. For an email the only real test is sending a message to it.</p>

<h2 id="guide-logs">Pulling fields out of lines</h2>
<p>Named groups turn a line of text into fields. <code>FindMatch</code> returns a <code>MatchResult</code>; its <code>ok</code> field says whether the line matched at all, and <code>GroupByName</code> reads one field by its name. Checking <code>ok</code> first matters: a line in an unexpected format should be skipped or reported, not read as empty fields.</p>
{{example.regex-guide-logs}}

<h2 id="guide-rewrite">Rewriting text</h2>
<p><code>ReplaceAll</code> puts the same text in place of every match, which is enough for collapsing runs of spaces. When the replacement depends on what was matched, use <code>ReplaceAllExpand</code>: in its template <code>$1</code>, <code>$2</code> and so on are the groups and <code>$0</code> is the whole match. Here a date written year first is turned around, and only the first date is marked. <code>Split</code> with a character class breaks text on any mix of separators.</p>
{{example.regex-guide-rewrite}}

<h2 id="guide-user-patterns">Patterns that come from users</h2>
<p>When the pattern itself is typed by a user, for a search box or a filter rule, check it with <code>IsValid</code> before calling <code>Compile</code>. <code>FindAllMatches</code> then gives the position of each match in bytes, which is what you need to highlight the matched words.</p>
{{example.regex-guide-user}}
<p>The engine supports the common syntax: classes such as <code>[a-z]</code>, the shorthands <code>\d</code>, <code>\w</code> and <code>\s</code> with their capital opposites, repetition with <code>*</code>, <code>+</code>, <code>?</code> and <code>{n,m}</code>, alternation with <code>|</code>, and plain and named groups. There is no <code>(?i)</code> flag; for a case-insensitive search, lower-case the text with <a href="/std/str/"><code>str</code></a> first and write the pattern in lower case. Positions are in bytes, so a Persian letter takes two of them.</p>

<h2 id="guide-persian">Persian text</h2>
<p>Because the engine matches bytes, a pattern for Persian text needs a little care. This program pulls hashtags out of a post, shortens a stretched word and finds a city name.</p>
{{example.regex-guide-persian}}
<p><code>\w</code> only knows ASCII letters, digits and <code>_</code>, so <code>#\w+</code> finds nothing; "anything up to a space" with <code>[^ ]+</code> works for any script. <code>هه+</code> finds two pieces because the <code>+</code> applies to the second byte of <code>ه</code> only; the group in <code>ه(ه)+</code> repeats the whole letter. The position 13 is in bytes: the five Persian letters before the city name take two bytes each, and the two spaces and the <code>#</code> one each.</p>

doc.FindStr = Like <code>Find</code>, with the pattern as text.
doc.ReplaceStr = Like <code>Replace</code>, with the pattern as text.
doc.ReplaceAllStr = Like <code>ReplaceAll</code>, with the pattern as text.
