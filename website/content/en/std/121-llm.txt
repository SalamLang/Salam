pkg.intro <<
<p>This package runs large language models of the Llama family on the processor, in pure Salam with no outside library. Download a model in <a href="/std/gguf/">GGUF</a> form, read it with <code>LoadGgufModel</code> and make text with <code>Generate</code>, or drive the loop yourself with <code>Forward</code> and a <code>Sampler</code> (temperature, top-k, top-p and a repetition penalty).</p>
<p>It is meant for small models running inside your own program: classifying or rewriting short texts offline, a local assistant in a tool, or learning how a transformer works step by step. For large models or high speed, call a server such as llama.cpp or an API over <a href="/std/net/http/#guide-raw">net/http</a> instead.</p>
<h3>What runs, and what it costs</h3>
<ul>
<li>The layer layout is Llama's: RMSNorm, rotary positions, grouped-query attention and a SwiGLU feed forward block, with the optional attention biases that Qwen2 uses. Qwen2.5 Instruct is tested; Llama and Mistral use the same layout. Architectures with other layouts, such as Phi, fail to load or produce nonsense.</li>
<li>The file limits of <a href="/std/gguf/">gguf</a> apply: under 2 GB, and only <code>F32</code>, <code>F16</code>, <code>Q8_0</code>, <code>Q4_0</code> and <code>Q4_1</code> weights, not the K-quants.</li>
<li>Every weight is expanded to <code>f32</code> when the model loads, so Qwen2.5 0.5B, a 0.7 GB file, needs about 3 GB of memory. The key/value cache is sized for <code>cfg.ctx</code>, which starts as the model's full context (32768 for Qwen); lower it before <code>NewKVCache</code> to save memory.</li>
<li><code>encode</code> does not recognise special tokens such as <code>&lt;|im_start|&gt;</code> in text: it splits them into ordinary pieces, which the model does not understand. Look their ids up in <code>tok.index</code> and insert them yourself, as the chat example does.</li>
</ul>
<p>The tokenizer, sampling and generation also work on a small random model built with <code>RandomModel</code>, which is how the reference example at the bottom of this page runs without a download.</p>
<h2 id="guide-chat">A chat answer, streamed</h2>
<p>Instruction tuned models expect the conversation in the exact format they were trained on. Qwen uses <code>&lt;|im_start|&gt;</code> and <code>&lt;|im_end|&gt;</code> around each turn, and the prompt ends by opening the assistant's turn so the model writes the reply. The format of any model is in its GGUF file under <code>tokenizer.chat_template</code>; see <a href="/std/gguf/"><code>gguf</code></a> for reading it. Those markers are single special tokens, so <code>add_turn</code> pushes their ids from <code>tok.index</code> and only encodes the text between them.</p>
<p>Instead of <code>Generate</code>, which returns the whole text at the end, this program runs the loop itself so every token is printed as soon as it is chosen. The first <code>Forward</code> call reads the whole prompt; after that each call feeds only the newest token, because the <code>KVCache</code> remembers everything before it. The loop stops at the end of turn token, after 80 tokens, or when the context is full. <code>cfg.ctx</code> is lowered to 4096 first, which keeps the cache at about 100 MB instead of 800.</p>
<pre class="code" dir="ltr"><code>mkdir -p models
curl -L -o models/qwen2.5-0.5b-instruct-q8_0.gguf \
  https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct-GGUF/resolve/main/qwen2.5-0.5b-instruct-q8_0.gguf
salam run llm-guide-chat.salam</code></pre>
{{example.llm-guide-chat}}
<pre class="code" dir="ltr"><code>The sky appears blue because of the scattering of sunlight by tiny water droplets in the atmosphere, which causes them to bounce off each other and scatter into our eyes.
tokens in prompt: 30 answer: 33</code></pre>
<p>A half billion weight model writes fluent sentences but gets facts wrong, as here: the real cause is scattering by air molecules, not water droplets. Use such a model for form, not for knowledge. Build with <code>salam build --release</code> for real use: the model runs on the processor, and a release build drops the bounds checks from the inner loops. Even so, expect a few seconds per token on an ordinary machine.</p>

<h2 id="guide-tokens">How text becomes tokens</h2>
<p>A model never sees letters, only token ids. A BPE tokenizer starts from single characters and applies its list of merges in order, so frequent pieces such as <code>lower</code> become one token while rare words fall apart into many. Byte level BPE, the kind GPT 2, Llama 3 and Qwen use, writes a space as <code>&#288;</code>, so the space before a word is part of a token. This tokenizer is built by hand with five merges to make the steps visible.</p>
{{example.llm-guide-tokens}}
<p><code>tower</code> is not merged into <code>ow</code> pieces because the merges only know <code>lo</code> and <code>low</code>. Counting tokens this way is also how you check that a prompt fits in the model's context before sending it.</p>

<h2 id="guide-sampling">Temperature and top-k</h2>
<p>The model gives a score, a logit, for every token in the vocabulary, and the sampler turns the scores into a choice. <code>Greedy</code> always takes the highest. A <code>Sampler</code> draws at random in proportion to the probabilities: a temperature below one sharpens them toward the favourite, above one flattens them, and <code>top_k</code> drops all but the best <code>k</code> before drawing. The program draws 1000 times from four fixed scores with each setting and counts how often each token wins.</p>
{{example.llm-guide-sampling}}
<p>The seed passed to <code>NewSampler</code> makes the draws repeatable, which is why this output never changes. For factual answers use a low temperature; for varied writing, around 0.7 to 1.0 with <code>top_p</code> 0.9. <code>repeat_penalty</code> above 1 lowers the scores of recently used tokens and stops small models from looping.</p>
