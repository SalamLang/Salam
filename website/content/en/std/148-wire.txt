pkg.intro <<
<p><code>wire</code> wires the layers of a program together: a repository, a service that uses it, a handler that uses the service. You register one provider per component, name what each one needs, and ask for the top of the graph. Each component is built once, and <code>Close</code> runs the cleanups in the reverse of the order they were built.</p>
<p>Salam has no runtime type information, so providers are identified by a name you choose, usually the type name. A provider is a function that takes the container and returns the component; it reads its own dependencies with <code>Get</code>. The second string of <code>Provide</code> lists those dependencies so that <code>Build</code> can check the whole graph before anything runs.</p>

<h2 id="guide-provide">Providers and the graph check</h2>
<p><code>Provide(c, name, needs, witness, factory)</code> registers a provider. <code>needs</code> is a comma separated list of provider names, empty when there are none. <code>witness</code> is any value of the component's type; it only tells the compiler which type the factory returns. <code>Build</code> returns an empty string when the graph is sound and otherwise a message that names the problem: a missing dependency, a duplicate provider or a dependency cycle with the full path.</p>
{{example.wire-quickstart}}
<p><code>Get(c, name, out)</code> builds the component if it does not exist yet and copies it into <code>out</code>. It returns false and sets <code>Error</code> when the name is unknown or a cycle is hit at run time.</p>

<h2 id="guide-bind">Interfaces, values and cleanups</h2>
<p><code>Bind(c, "Store", "MemStore")</code> makes the name <code>Store</code> resolve to the provider <code>MemStore</code>, which is how a service asks for an interface and gets the implementation chosen at the wiring site. <code>Value</code> registers a ready made value such as a configuration struct. <code>OnClose</code> attaches a cleanup to a provider; <code>Close</code> runs the cleanups of the components that were actually built, last built first, and frees the container.</p>
<p><code>Built</code> lists the names in the order they were built and <code>Count</code> the number of registered names.</p>

<h2 id="guide-errors">Reading the errors</h2>
<p><code>Build</code> only looks at the registered names and their <code>needs</code> lists, it never runs a factory. A sound graph gives an empty string; the other three messages are <code>missing dependency: Service needs Repo</code>, <code>duplicate provider: Repo</code> and <code>dependency cycle: A -&gt; B -&gt; C -&gt; A</code>. Call it once at startup and stop there if the text is not empty. <code>Get</code> with a name nobody registered returns false and leaves <code>missing provider: Nope</code> in <code>Error</code>.</p>
{{example.wire-guide-errors}}

<h2 id="guide-swap">Choosing an implementation at the wiring site</h2>
<p>Put the choice in one function that builds the container. Here <code>Value</code> stores the configuration, two providers make a <code>Store</code> in different ways, and <code>Bind</code> points the name <code>Store</code> at one of them depending on the environment. Code that asks for <code>Store</code> does not change. Only the components that something actually asked for are built: <code>Built</code> lists 1 name in the test container and 2 in the production one, out of 4 registered.</p>
{{example.wire-guide-swap}}

<h2 id="guide-lifecycle">Build once, close in reverse</h2>
<p>Every provider is a singleton: asking twice for <code>Cache</code> runs its factory once and hands out copies of the same value. The cleanups registered with <code>OnClose</code> run from the last built component to the first, so the cache is closed before the database it holds. A second <code>Close</code> does nothing.</p>
{{example.wire-guide-lifecycle}}
