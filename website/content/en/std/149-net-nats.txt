pkg.intro <<
<p>NATS is a small, fast message bus. Programs publish messages to <em>subjects</em> such as <code>orders.eu.new</code>, other programs subscribe to subjects or patterns, and the server delivers. This package is a client for the core protocol, request and reply, queue groups, headers, JetStream streams and consumers, and a simple key value helper. It speaks the text protocol over TCP or TLS and needs nothing but the standard library.</p>
<p>The model: <code>Connect</code> opens a connection and you pass it by reference to every call. Nothing runs in the background. Messages are read, handlers are called and PINGs are answered only while you call <code>Pump</code>, <code>NextMsg</code>, <code>Flush</code>, <code>Request</code> or <code>Fetch</code>, so a program that stops calling them stops answering the server. Failures are values: a call returns false, or a message whose <code>ok</code> is false with the reason in <code>err</code>.</p>
<ul>
<li><strong>Subjects</strong> are tokens joined by dots. <code>*</code> matches one token and a final <code>&gt;</code> matches the rest, in subscriptions only.</li>
<li><strong>Queue groups</strong> split a subject among workers: each message goes to one member.</li>
<li><strong>Payloads are text.</strong> A <code>str</code> stops at its first NUL byte, so send binary data encoded, for example with Base64.</li>
</ul>

<h2 id="guide-connect">Connecting</h2>
<p><code>Connect</code> takes a URL such as <code>nats://127.0.0.1:4222</code>; <code>tls://</code> turns TLS on, and <code>nats://user:password@host</code> or <code>nats://token@host</code> carries credentials. <code>ConnectWith</code> takes an <code>Options</code> value for the rest. A failed connection is a connection with <code>ok</code> false, so check <code>IsConnected</code> and read <code>LastError</code>.</p>
<pre class="code"><code>mut nc := nats.Connect("nats://127.0.0.1:4222")
if not nats.IsConnected(nc):
    println nats.LastError(nc)
end</code></pre>

<h2 id="guide-pubsub">Publishing and subscribing</h2>
<p><code>Subscribe</code> returns a handle; <code>NextMsg</code> waits for its next message. Or give <code>SubscribeHandler</code> a function and let <code>Pump</code> call it. <code>Flush</code> sends a PING and waits for the PONG, which proves the server has received everything you published before it.</p>
<pre class="code"><code>sub := nats.Subscribe(nc, "greet.*")
nats.Publish(nc, "greet.bob", "hello")
m := nats.NextMsg(nc, sub, 1000)
println m.subject, m.data</code></pre>

<h2 id="guide-request">Request and reply</h2>
<p><code>Request</code> publishes with a private reply subject and waits for one answer. A responder is a <code>SubscribeReplier</code> or a handler that calls <code>Respond</code>. When nobody is subscribed, a server with headers support answers at once with <code>no responders</code> instead of making you wait for the timeout.</p>
<pre class="code"><code>nats.SubscribeReplier(nc, "svc.up", "", (m: nats.Msg): ret str.Upper(m.data) end)
r := nats.Request(nc, "svc.up", "quiet", 1000)</code></pre>

<h2 id="guide-reconnect">Reconnecting</h2>
<p>By default a lost connection is closed for good. Set <code>max_reconnects</code> to a positive number, or a negative one to never give up, and the client reconnects by itself. It walks the list made of the URL and <code>servers</code>, waits <code>reconnect_wait_ms</code> between attempts, sends all subscriptions again (an <code>AutoUnsubscribe</code> limit counts only what is left) and then sends the publishes that were held while the link was down, up to <code>reconnect_buffer</code> bytes. Reconnecting happens inside <code>Pump</code>, <code>NextMsg</code>, <code>Flush</code> and <code>Request</code>, since nothing runs in the background. A request that was already on its way when the link broke gets no answer and times out. Errors such as a refused login close the connection instead of retrying.</p>
<pre class="code"><code>mut opts := nats.DefaultOptions()
opts.servers.push("nats://10.0.0.2:4222")
opts.max_reconnects = 20
opts.reconnect_wait_ms = 500</code></pre>

<h2 id="guide-jetstream">JetStream</h2>
<p>JetStream stores messages in streams and hands them to consumers. <code>AddStream</code> makes a stream for some subjects, <code>JSPublish</code> publishes and returns the receipt with the stored sequence number, and a pull consumer made with <code>AddConsumer</code> is read with <code>Fetch</code>. Acknowledge every message with <code>Ack</code>; <code>Nak</code> asks for a redelivery and <code>Term</code> gives up on a message.</p>
<p>A push consumer made with <code>AddPushConsumer</code> has the server send messages to a subject you subscribed to. Read them with <code>NextPush</code>, which also answers flow control and skips heartbeats. Any other JetStream call is available through <code>JSRequest</code>.</p>

<h2 id="guide-kv">Key value buckets</h2>
<p>A bucket is a stream called <code>KV_</code> followed by its name, with one subject for each key. <code>KVCreate</code>, <code>KVPut</code>, <code>KVGet</code> and <code>KVDelete</code> cover the common cases. A delete writes a marker, so <code>KVGet</code> then reports <code>found</code> false and <code>deleted</code> true. Watching keys, compare-and-set updates and purging are not provided; use <code>JSRequest</code> or the stream calls for those.</p>

<h2 id="guide-limits">What to know</h2>
<ul>
<li>Nothing runs in the background. Call <code>Pump</code> or a waiting function regularly, or the server drops you as a slow consumer or a stale connection.</li>
<li>A connection is not safe to use from two threads at once.</li>
<li>Payloads stop at the first NUL byte. Binary data needs encoding.</li>
<li>The default is no reconnecting. Turn it on with <code>max_reconnects</code>.</li>
<li>Authentication is user and password or a token. NKeys, JWT credentials and client certificates are not supported.</li>
<li>JetStream calls need a server started with JetStream. Without it they return <code>jetstream not enabled</code> or <code>no responders</code>.</li>
</ul>
