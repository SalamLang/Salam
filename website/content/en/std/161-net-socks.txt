pkg.intro <<
<p>SOCKS is the plain, widely supported proxy protocol: a program asks a proxy to connect somewhere on its behalf and then talks through the connection as if it were direct. This package has both sides. <code>Connect</code> is the client; <code>Start</code> runs a server. It also plugs into <a href="/std/net/tunnel/">net.tunnel</a>, as a <code>Socks5Inbound</code> or <code>Socks4Inbound</code> that can share one port with an HTTP proxy, and as a <code>SocksConnector</code> that is one hop of a proxy chain. To see how the pieces fit together in an app, read <a href="/std/net/tunnel/#guide-vpn-app">Building a v2ray style or VPN app</a>.</p>
<p>Core ideas:</p>
<ul>
<li>A client is a value: <code>NewClient</code> or <code>NewClientAuth</code> fills a <code>Client</code>, and <code>Connect</code> returns a <code>ConnectResult</code> with a stream. Failure is a value too: <code>ok</code> is false and <code>code</code> and <code>err</code> say why.</li>
<li>SOCKS5 is the default. Set <code>version</code> to <code>Socks4</code> or <code>Socks4a</code> for older servers. SOCKS4 sends an IPv4 address; SOCKS4a lets the server resolve a name.</li>
<li>A name sent to a SOCKS5 or SOCKS4a proxy is resolved <em>by the proxy</em>, so the lookup does not happen on your machine.</li>
<li>A server is a <code>ServerConfig</code> given to <code>Start</code>. How it reaches targets is a callback (<code>SetConnector</code>) or a <code>tunnel.Dialer</code> (<code>SetDialer</code>), which is how it is joined to routing rules and proxy chains.</li>
<li><code>Associate</code> opens a UDP relay and <code>Bind</code> waits for an incoming connection. Both are SOCKS5 features the server can switch off.</li>
</ul>
<p>Things that catch people out:</p>
<ul>
<li><strong>A server listens on <code>bind_host</code>, which is <code>127.0.0.1</code> by default.</strong> Set it to <code>0.0.0.0</code> (or an address) only on purpose. A SOCKS server without a login that is reachable from outside is an open proxy anyone can abuse. Require a user (<code>AddUser</code>), restrict it with a firewall, or put it behind a tunnel.</li>
<li><strong>The login is not encrypted.</strong> SOCKS5 user name and password travel in clear text. Use it on a local port or through an encrypted tunnel, or set <code>tls</code> when the proxy is reachable over TLS. The server side of this package speaks plain TCP only.</li>
<li><strong>SOCKS4 has no passwords.</strong> A server that requires logins refuses SOCKS4 clients, and <code>allow_v4</code> can switch SOCKS4 off.</li>
<li><strong><code>allow_bind</code> is off by default</strong> because BIND makes the proxy open a listening port for the client, and a UDP relay does the same with a UDP port. Those sockets are bound to <code>bind_host</code> too, and that is the address reported to the client.</li>
<li><strong>UDP has no fragments.</strong> Only fragment 0 is supported, and there is no UDP over SOCKS4.</li>
<li><strong>IPv6 works end to end.</strong> TCP CONNECT, BIND and the UDP relay carry IPv6 targets (address type 4), and the server can listen on <code>::1</code> or on <code>::</code> for both families. A UDP relay bound to an IPv4 address still reaches IPv6 targets through a second outbound socket. SOCKS4 stays IPv4.</li>
<li><strong>Close streams.</strong> A <code>stream</code> is an open connection. Close it when you are done.</li>
</ul>

<h2 id="guide-client">Using a SOCKS proxy from a program</h2>
<p>Make a client for the proxy, connect to a target, and use the stream. The proxy here is a local server so the example runs anywhere; in real use it is the address of the proxy you trust.</p>
{{example.net-socks-guide-client}}
<p><code>DialConn</code> does the same but returns a plain TCP connection for code that already uses <code>net.tcp</code>. Through a proxy that needs a login use <code>NewClientAuth</code>. To go through two proxies in a row, see <code>tunnel.Chain</code> and the chain example below.</p>

<h2 id="guide-server">Running a SOCKS server</h2>
<p><code>NewServerConfig</code> gives a config for a port; <code>AddUser</code> turns the login on; <code>Start</code> binds and returns at once, and <code>Stop</code> ends it. How the server reaches a target is the part you usually change: leave <code>DirectConnect</code> for a plain proxy, set a callback with <code>SetConnector</code> to route by name, or give it a <code>tunnel.Dialer</code> with <code>SetDialer</code> to use rules, chains and block lists from <a href="/std/net/tunnel/">net.tunnel</a>. <code>allow</code> can refuse commands, hosts or ports before any connection is made.</p>
<p>To put SOCKS on the same port as an HTTP proxy, give a <code>Socks5Inbound</code> to a <code>tunnel.MixedProtocol</code> instead of calling <code>Start</code>. <code>Handle</code> serves a single stream you accepted yourself.</p>
<pre class="code"><code>mut config := socks.NewServerConfig(1080)
socks.AddUser(config, "alice", "a long random password")
server := socks.Start(config)
if not server.ok:
    println "port 1080 is busy"
end</code></pre>

<h2 id="guide-limits">What to know</h2>
<ul>
<li>The server listens on <code>bind_host</code> (loopback by default). Use a login or a firewall, never an open proxy.</li>
<li>The login is plain text. SOCKS4 has no login at all.</li>
<li>Names are resolved by the proxy for SOCKS5 and SOCKS4a, and by the client for SOCKS4.</li>
<li><code>Start</code> runs the accept loop on its own thread; connections run on further threads. <code>Stop</code> stops new clients only.</li>
<li>The decoders (<code>DecodeRequest</code>, <code>DecodeReply</code>, <code>Decode4Request</code>, <code>DecodeAddress</code>) return the bytes used, 0 for "need more data" and -1 for invalid, so they work on a growing buffer.</li>
<li>No logging happens by itself.</li>
</ul>
>>
