pkg.intro <<
<p>VLESS is a very small proxy protocol from the Xray and V2Ray family. A client opens a connection to the server and sends one header that says who it is (a UUID), what it wants (a TCP connection, or UDP datagrams) and where to (a host and a port). The server checks the UUID, answers with two bytes and from then on the connection carries the payload unchanged. That is all: <strong>VLESS does no encryption of its own.</strong> The protection has to come from what carries it, which is why it is used over TLS (<code>transport.Settings.tls</code>), usually inside a WebSocket behind a CDN.</p>
<p>This package is both halves. <code>Dial</code> connects a client through <a href="/std/net/transport/">net.transport</a> and sends the header; <code>Accept</code> reads the header on a server and checks it against a list of users. <code>Read</code> and <code>Write</code> then move the payload, <code>ReadPacket</code> and <code>WritePacket</code> move UDP datagrams, and <code>ParseLink</code> reads the <code>vless://</code> share links that apps exchange. <code>AsStream</code>, <code>DialOver</code> and <code>AcceptOver</code> connect it to the <a href="/std/net/tunnel/">net.tunnel</a> streams, so it can be one hop of a chain or run inside another protocol. Importing this package pulls in <code>net.transport</code>, and you need that import yourself to build a <code>Settings</code> value and a target <code>Addr</code>.</p>

<h3 id="wire">What goes on the wire</h3>
<div class="table-wrap"><table>
<thead><tr><th>Direction</th><th>Bytes</th></tr></thead>
<tbody>
<tr><td>Client to server, once</td><td>version <code>0</code>, the 16 byte user id, the length of the addon block (0, or the flow name wrapped in a small protobuf message), the command (<code>1</code> TCP, <code>2</code> UDP, <code>3</code> mux), the port, the address kind, the address. The mux command has no address.</td></tr>
<tr><td>Server to client, once</td><td>version <code>0</code> and the addon length (this package skips any addon).</td></tr>
<tr><td>Afterwards, TCP</td><td>the payload in both directions.</td></tr>
<tr><td>Afterwards, UDP</td><td>each datagram prefixed by its length in two bytes.</td></tr>
</tbody></table></div>
<p>The client does not wait for the server's reply before it sends data. The two byte reply is read by the first <code>Read</code>, and a server that refuses the user simply closes the connection, so the client learns about it there and not from <code>Dial</code>.</p>

<h3 id="pitfalls">What trips people up</h3>
<ul>
<li><strong>Without TLS the user id is visible and nothing is encrypted.</strong> A plain TCP VLESS connection is a plain text tunnel with a password in front. Use TLS, or put VLESS inside something that encrypts.</li>
<li><strong>A rejected client sees success.</strong> <code>Dial</code> only sends the header. A wrong UUID shows up as the first <code>Read</code> failing, on the server as <code>unknown user</code>.</li>
<li><strong>The flow must match.</strong> A server user created with <code>NewUser(id, "")</code> accepts requests without a flow. A request that names a flow different from the user's is refused.</li>
<li><strong>UDP is length prefixed datagrams on the one connection.</strong> It is the simple form; Xray's XUDP packet format is not implemented.</li>
<li><strong>Close frees the request.</strong> Call <code>Close</code> once when you are done, on both sides; it also closes the transport underneath.</li>
</ul>

<h2 id="guide-header">The request header</h2>
<p><code>EncodeRequest</code> and <code>DecodeRequest</code> are the header on its own, with no connection. They are what the tests compare with known bytes, and they are handy to see exactly what a server will receive. <code>DecodeRequest</code> returns how many bytes it consumed, or -1 when the bytes are cut short, have a wrong version or carry an unknown command.</p>
{{example.net-vless-guide-header}}

<h2 id="guide-link">Share links</h2>
<p>Apps share a server as one <code>vless://uuid@host:port?query#name</code> text. <code>ParseLink</code> reads it into a <code>Link</code>: check <code>ok</code> first, and read <code>err</code> when it is false. <code>LinkSettings</code> turns the link into the <code>Settings</code> for <code>net.transport</code> (the path's <code>?ed=2048</code> suffix becomes <code>early_data</code>), <code>FormatLink</code> goes back to text and <code>DialLink</code> does the whole connect. The parser refuses what the package cannot do, with a message that says why: <code>security=reality</code>, <code>type=grpc</code>, <code>type=h2</code>, <code>type=xhttp</code>, an <code>encryption</code> other than <code>none</code>, and a bad UUID.</p>
{{example.net-vless-guide-link}}

<h2 id="guide-quickstart">Quick start: a client and a server over TCP</h2>
<p>The server listens with <code>transport.Listen</code>, accepts with <code>transport.Accept</code> and hands the connection to <code>vless.Accept</code> with its list of users. The client dials with <code>vless.Dial</code>. The target address in the header is what the server would connect onward to; this echo server just prints it. In a real server you would dial that target (with <a href="/std/net/tcp/">net.tcp</a> or a <a href="/std/net/tunnel/">tunnel</a> dialer) and copy bytes both ways.</p>
{{example.net-vless-guide-loopback}}

<h2 id="guide-wrong-user">A user the server does not know</h2>
<p>The client cannot tell by itself. The server sees <code>unknown user</code>, closes the connection and the client's first read fails.</p>
{{example.net-vless-guide-wrong-user}}

<h2 id="guide-udp">UDP datagrams</h2>
<p>Dial with <code>CmdUDP</code> and the datagram target (a DNS server here). Each <code>WritePacket</code> sends one datagram and each <code>ReadPacket</code> returns one, whole, in the buffer; a datagram can be at most 65535 bytes. A zero length datagram reads as an empty one.</p>
{{example.net-vless-guide-udp}}

<h2 id="guide-over-stream">Inside another stream</h2>
<p><code>DialOver</code> and <code>AcceptOver</code> run the protocol on any <code>tunnel.Stream</code> instead of a network connection, and <code>AsStream</code> turns the result back into a stream. This is how a chain is built: the output of one protocol is the carrier of the next. The example runs both ends over an in-memory pipe.</p>
{{example.net-vless-guide-over-stream}}

<h2 id="guide-cdn">VLESS over WebSocket and TLS behind a CDN</h2>
<p>The most common deployment. Do the CDN steps from the <a href="/std/net/transport/#guide-cdn">net.transport</a> page: a proxied domain, a secret WebSocket path, TLS to the CDN with the front name as <code>sni</code> and your own domain as <code>host</code>. Then the share link carries all of it, and one call connects:</p>
{{example.net-vless-guide-cdn}}
<p>On the server, listen with <code>network = "ws"</code>, the same <code>path</code> and <code>host</code>, with <code>tls</code> off when the CDN or your reverse proxy terminates TLS (and on, with a certificate and key, when it does not). Accept connections with <code>transport.AcceptRaw</code>, run <code>transport.Upgrade</code> and then <code>vless.Accept</code> in a worker thread for each of them.</p>
<p>Two things to know. First, VLESS has no encryption (<code>encryption=none</code>), so the CDN can read the traffic between its two TLS legs. For hostile CDNs use <a href="/std/net/vmess/">VMess</a> with <code>SecAES128GCM</code>, which encrypts the payload itself. Second, set the <code>fragment</code> options of <code>net.transport</code> if the first hop is blocked by its TLS server name; they apply to this dial like any other.</p>

<h2 id="guide-limits">Limits</h2>
<ul>
<li><strong>Vision is the padding layer only.</strong> With the flow <code>xtls-rprx-vision</code> the first 8 writes in each direction are wrapped in Vision frames (user id, command, content and random padding, as Xray does), and the last of them tells the peer padding ended. Our client and server interoperate and the framing follows Xray; the "direct copy" step that skips the outer TLS after the inner TLS 1.3 handshake is not implemented, so the data stays inside the outer connection. A peer that sends the direct command is treated as ending its padding. Vision applies to <code>CmdTCP</code> only, and it has not been run against a real Xray server.</li>
<li><strong>XHTTP and QUIC are not supported,</strong> and <code>ParseLink</code> refuses their links. The transports are <code>tcp</code>, <code>ws</code>, <code>httpupgrade</code> and <code>grpc</code> (<code>serviceName</code> and <code>mode=gun|multi</code> in the link), with <code>none</code>, <code>tls</code> or <code>reality</code> security (<code>pbk</code>, <code>sid</code>, <code>spx</code>, <code>fp</code>).</li>
<li><strong>Multiplexing is Mux.Cool.</strong> Dial with <code>CmdMux</code> and call <code>MuxClient</code>; on the server check that <code>Accept</code> gave a request with <code>CmdMux</code> and call <code>MuxServer</code>. Sessions then come from <code>net.transport</code> (<code>MuxOpen</code>, <code>MuxAccept</code>).</li>
<li><strong>The <code>fingerprint</code> of a link is informational.</strong> It is stored and written back, but the TLS handshake is not changed by it.</li>
<li><strong>No live interoperability test against Xray or V2Ray was run.</strong> The header is checked against fixed byte vectors, and client and server are tested against each other over TCP, TLS, WebSocket and HTTP upgrade, but not against a real Xray build.</li>
<li><strong>There are no server fallbacks.</strong> A connection that is not VLESS, or has an unknown user, is closed; it is not handed to a web server as Xray's fallbacks do.</li>
<li><strong>Early data needs <code>DialEarly</code>.</strong> <code>LinkSettings</code> sets <code>early_data</code> from <code>?ed=</code>, but <code>Dial</code> and <code>DialLink</code> do not send any early payload.</li>
</ul>
