pkg.intro <<
<p>VMess is the older protocol of the V2Ray family, and unlike <a href="/std/net/vless/">VLESS</a> it encrypts for itself. The client proves it holds a user's UUID with an authentication id that contains the current time, sends the request (the target address and the session keys) encrypted under keys derived from the UUID, and then sends the payload in encrypted chunks. The server answers with its own encrypted header and its own chunks. Anyone watching sees random bytes, whatever carries them.</p>
<p>This package implements <strong>only the AEAD form</strong>, the one used since V2Ray 4.28 and the only one current clients still produce: the user is identified by the encrypted authentication id and the header is sealed with AES-128-GCM. The older MD5 based form, the one that needs <code>alterId</code> to be above 0, is not implemented. Set <code>alterId</code> to 0 on both sides (it is the default in current clients).</p>
<p>The package is both halves. <code>Dial</code> connects a client through <a href="/std/net/transport/">net.transport</a> and sends the header, <code>Accept</code> reads it on a server, <code>Read</code> and <code>Write</code> move the payload and <code>ReadPacket</code> reads one chunk as a UDP datagram. <code>AsStream</code>, <code>DialOver</code> and <code>AcceptOver</code> connect it to <a href="/std/net/tunnel/">net.tunnel</a> streams. The lower level functions (key derivation, the sealed header, the chunk encoder) are public, because the protocol is easiest to understand, and to test, one piece at a time.</p>

<h3 id="security">The body encryptions</h3>
<div class="table-wrap"><table>
<thead><tr><th>Constant</th><th>What it does</th></tr></thead>
<tbody>
<tr><td><code>SecAES128GCM</code></td><td>Each chunk is sealed with AES-128-GCM. The default choice.</td></tr>
<tr><td><code>SecChaCha20Poly1305</code></td><td>Each chunk is sealed with ChaCha20-Poly1305. A good choice on a processor without AES instructions.</td></tr>
<tr><td><code>SecNone</code></td><td>The chunks are framed but not encrypted. The header is still sealed.</td></tr>
<tr><td><code>SecZero</code></td><td>No chunks and no encryption: the payload follows the header as it is. Only for use inside TLS.</td></tr>
</tbody></table></div>
<p>The header is always sealed with AES-128-GCM under keys derived from the UUID, whichever body type is chosen. The options in <code>Request.option</code> are bits: <code>OptChunkStream</code> frames the body in chunks, <code>OptChunkMask</code> hides the chunk lengths with a SHAKE-128 stream, <code>OptPadding</code> adds random padding to each chunk, <code>OptAuthLength</code> authenticates the lengths with the body cipher. <code>Dial</code> uses <code>DefaultOption</code> for the security type; to choose the bits yourself, call <code>Client</code> on a connection you opened.</p>

<h3 id="pitfalls">What trips people up</h3>
<ul>
<li><strong>The two clocks must agree.</strong> The authentication id contains the time and a server accepts only ids within <code>TimeWindow</code> seconds, 120, of its own clock. A phone or a server with a wrong clock gets <code>unknown user or stale timestamp</code> and nothing else. This is the first thing to check when a correct UUID is refused.</li>
<li><strong>Share one replay filter.</strong> <code>Accept</code> remembers the authentication ids it has seen and refuses a repeat. Make one with <code>NewReplayFilter</code> and pass the same one to every <code>Accept</code> call of a server; it is safe to use from several threads. Once it holds more than 4096 ids it drops the ones older than four minutes.</li>
<li><strong>A refused client is not told.</strong> <code>Dial</code> only sends the header. A wrong UUID, a stale clock or a replayed id makes the server close the connection, and the client sees that as a failed read.</li>
<li><strong>The server must support the security type.</strong> An <code>Accept</code> that reads a type other than the four above fails with <code>unsupported security type</code>.</li>
<li><strong>There are no vmess:// links.</strong> The base64 JSON share format of V2RayN and others is not parsed here. Take the fields from it yourself.</li>
<li><strong>Close frees the keys.</strong> Call <code>Close</code> once on each side when you are done.</li>
</ul>

<h2 id="guide-primitives">The building blocks</h2>
<p>This program derives a user's command key from a UUID, makes an authentication id for a given time, opens it again (which also gives back the time), shows that another user's key cannot open it, and seals a small header. The numbers that come out are fixed, so they can be compared with another implementation.</p>
{{example.net-vmess-guide-primitives}}

<h2 id="guide-quickstart">Quick start: a client and a server over TCP</h2>
<p>The server listens with <code>transport.Listen</code>, accepts with <code>transport.Accept</code> and hands each connection to <code>vmess.Accept</code> with its list of users and the shared replay filter. The client dials with <code>vmess.Dial</code> and picks the body encryption. The target in the header is what a real server would connect onward to; this echo server just reports it.</p>
{{example.net-vmess-guide-loopback}}

<h2 id="guide-wrong-user">A user the server does not know</h2>
<p>The client cannot tell by itself. The server finds no matching key, says <code>unknown user or stale timestamp</code>, and closes the connection. A real server should do nothing else: sending an error would tell a scanner that it found a proxy.</p>
{{example.net-vmess-guide-wrong-user}}

<h2 id="guide-over-stream">VLESS carrying VMess</h2>
<p>A stream wrapper turns any protocol into the carrier of another. Here an outer VLESS connection runs over an in-memory pipe and an inner VMess connection runs inside it, with different users and different targets. On a real network the outer one would be VLESS over WebSocket and TLS and the inner one VMess, which encrypts the payload end to end even when a CDN terminates the outer TLS.</p>
{{example.net-vmess-guide-over-stream}}

<h2 id="guide-cdn">VMess over WebSocket and TLS behind a CDN</h2>
<p>Do the CDN steps from the <a href="/std/net/transport/#guide-cdn">net.transport</a> page: a proxied domain, a secret WebSocket path, TLS to the CDN with the front name as <code>sni</code>, your domain as <code>host</code>. VMess does the encryption, so it also protects the payload from the CDN.</p>
{{example.net-vmess-guide-cdn}}
<p>On the server, listen with <code>network = "ws"</code>, the same <code>path</code> and <code>host</code> and with <code>tls</code> off when the CDN or your reverse proxy terminates TLS. For each connection, in a worker thread, call <code>transport.AcceptRaw</code>, <code>transport.Upgrade</code> and then <code>vmess.Accept</code>. Keep the server's clock right (the time window is 120 seconds), and tell your users to do the same.</p>

<h2 id="guide-link">Share links</h2>
<p>Apps share a VMess server as <code>vmess://</code> followed by base64 of a JSON object (the v2rayN form, the same one <code>tunnel.ParseLink</code> reads). <code>ParseLink</code> reads it into a <code>Link</code>: check <code>ok</code> and read <code>err</code> when it is false. <code>FormatLink</code> writes one back, <code>LinkSettings</code> turns it into the <code>net.transport</code> settings (WebSocket path and <code>?ed=</code> early data, gRPC service name, TLS name) and <code>DialLink</code> dials it. <code>SecurityByName</code> and <code>SecurityName</code> convert between names such as <code>chacha20-poly1305</code> and the security numbers; <code>auto</code> means AES-128-GCM. The legacy <code>aid</code> is parsed and kept but only 0 is meaningful.</p>

<h2 id="guide-limits">Limits</h2>
<ul>
<li><strong>AEAD only.</strong> There is no legacy (<code>alterId</code> above 0) mode, and no compatibility with servers or clients that need it.</li>
<li><strong>The authenticated length option follows Xray.</strong> <code>OptAuthLength</code> derives its length key and nonce from the request key and IV in both directions, seals the length with AES-128-GCM (also for ChaCha20-Poly1305 bodies) and was checked against Xray and sing-box in the interop run (see <code>docs/VPN_INTEROP.md</code> for the matrix). <code>Dial</code> never sets it; choose the bits with <code>Client</code>.</li>
<li><strong>Interoperability was tested separately.</strong> The header, the authentication id, the key derivation and the chunk formats are checked in this repository against fixed byte vectors and the two halves of this package against each other (over TCP, TLS, WebSocket and a pipe). The interop harness runs the package against real Xray and sing-box builds; its results are in <code>docs/VPN_INTEROP.md</code>.</li>
<li><strong>Multiplexing is Mux.Cool.</strong> Dial with <code>CmdMux</code> and call <code>MuxClient</code>; on the server, when the accepted request has <code>CmdMux</code>, call <code>MuxServer</code>. Sessions come from <code>net.transport</code> (<code>MuxOpen</code>, <code>MuxAccept</code>).</li>
<li><strong>Weak primitives by design.</strong> VMess uses MD5 for the command key and AES in ECB mode for one block of the authentication id; these are the protocol's, not choices of this package. The payload ciphers are authenticated (AES-GCM, ChaCha20-Poly1305).</li>
<li><strong><code>SecNone</code> and <code>SecZero</code> do not encrypt the payload.</strong> Use them only inside TLS you trust.</li>
<li><strong>Replay protection is per process.</strong> The filter lives in memory, so a restart forgets it, but the time window still limits what can be replayed.</li>
</ul>
>>
