pkg.intro <<
<p><code>gui.reactive</code> is the state runtime of Salam's native user interface, modelled on the property system of Slint. Every value that can change is a property. A property either holds a value or has a <em>binding</em>, a function that computes it from other properties. Reading a property inside a binding records a dependency by itself, so there is nothing to declare.</p>
<p>The work is split in two halves. A <code>Set</code> only compares, stores and marks the dependents dirty, stopping at nodes that are already dirty. Nothing is computed then: a dirty binding runs the next time somebody reads it, and it forgets its old dependencies and records new ones, so a binding with an <code>if</code> depends only on the branch it took.</p>
<p>Things to know:</p>
<ul>
<li><strong>Handles are small values.</strong> <code>IntProp</code>, <code>StrProp</code> and the others hold an index into the runtime, so a lambda that captures one by value still sees the live property. A constant made with <code>ConstInt</code> and friends holds its value in the handle and costs nothing in the runtime.</li>
<li><strong>Setting a bound property removes the binding</strong>, as an assignment does in Slint. Use <code>Link</code> for a value that two places edit.</li>
<li><strong>Text has ownership rules.</strong> <code>StrProp.Get</code> returns a string owned by the property, valid until the value changes. <code>Bind</code> takes ownership of the new string its function returns; <code>BindCopy</code> copies it, for literals and other properties' text.</li>
<li><strong>Change handlers never run inside a set.</strong> <code>OnChange</code> queues them, the event loop calls <code>RunPendingHandlers</code>, and many changes give one call.</li>
<li><strong>Binding loops are reported</strong> with the property names, for example <code>binding loop: 'min width' -> 'preferred width' -> 'min width'</code>, instead of overflowing the stack. Name properties with <code>Name</code> to get readable reports.</li>
<li><strong>The runtime is for one thread</strong>, the user interface thread. A capturing lambda keeps its environment until the program ends, so bindings made per row of a long list should read package-level state rather than capture.</li>
</ul>

<h2 id="guide-counter">A counter component</h2>
<p>This is what a component with <code>state count</code> turns into. The label and the <code>wide</code> flag are bindings on <code>count</code>. A tracker stands for the screen: it runs the paint function, and its callback only notes that a repaint is needed. The loop plays the event loop: it handles a click, runs the change handlers, and repaints when asked. Clicking three times with one jump to 10 gives four paints and three saves.</p>
{{example.gui-reactive-guide-counter}}

<h2 id="guide-transition">A CSS transition on hover</h2>
<p>An animated property moves to each new value over time. Here the background is a binding on <code>hovered</code>, animated with <code>ease-in-out</code> over 300 ms and interpolated per colour channel. Each frame sets the clock with <code>SetTime</code>; the animated property depends on the clock only while it moves, and <code>AnimationsRunning</code> tells the loop when it can stop drawing.</p>
{{example.gui-reactive-guide-transition}}
