pkg.intro <<
<p>This package holds Salam's data structures. <code>Vector</code> and <code>HashMap</code>, which turn up in every program, are defined here but built in: you can use them without an import. The rest (<code>Stack</code>, <code>Queue</code>, <code>Deque</code>, <code>Set</code>, <code>Counter</code>, <code>PriorityQueue</code>, <code>OrderedMap</code>, <code>LinkedList</code>, <code>CircularList</code>, <code>Pair</code>) and the vector helpers such as <code>clone</code> and <code>index_of</code> need <code>import collections</code>. To sort or search a vector use <a href="/std/sort/">sort</a>; to share a structure between threads, guard it with <a href="/std/sync/">sync</a>, because none of these types locks.</p>
<p>All of them are generic: you set the element type with <code>&lt;...&gt;</code>, as in <code>collections.Stack&lt;str&gt;</code>, and build an empty one with <code>collections.Stack {} as collections.Stack&lt;str&gt;</code>. All of them allocate, so write <code>defer x.free()</code> right after creating one. <code>free</code> releases the structure itself, not heap strings or other objects stored in it.</p>
<p>Which should you pick? For an ordinary list, <code>Vector</code>; for "last in, first out", <code>Stack</code>; for "first in, first out", <code>Queue</code>; for adding and removing at both ends, <code>Deque</code>; for fast lookup by a key, <code>HashMap</code>; for removing duplicates, <code>Set</code>; for "always give me the smallest", <code>PriorityQueue</code>; and for string settings that must keep their order, <code>OrderedMap</code>. Most of them are thin layers over <code>Vector</code>: a stack is one vector, a queue and a deque are two.</p>
<p>What people get wrong:</p>
<ul>
<li>Copying with <code>=</code>. <code>b := a</code> copies only the vector's header, so both names see the same elements: <code>b.set(0, x)</code> changes <code>a</code> too, and a <code>push</code> on one can move the memory under the other. Take a real copy with the built-in <code>v.copy()</code> or with <code>collections.clone(v)</code>. The same goes for a <code>HashMap</code> (<code>m.copy()</code>) and for any struct holding one.</li>
<li>Changing a struct you got from a map. <code>m.get(k)</code> returns a copy; change it and <code>put</code> it back.</li>
<li>Reading from an empty structure. <code>pop</code>, <code>peek</code>, <code>dequeue</code>, <code>first</code>, <code>last</code> and an index past the end stop the program with a message such as <code>Vector.pop: empty</code>. Check <code>is_empty()</code> first. A <code>--release</code> build leaves the check out, and the same mistake then reads garbage.</li>
<li>Printing a map in its own order. <code>each key, value in m</code> visits the slots in hash order, which changes as the map grows. Collect and sort the keys when the order shows.</li>
</ul>

<h2 id="guide-vector">Vector: insert, remove, copy</h2>
<p><code>push</code> and <code>pop</code> work at the end in constant time. <code>insert</code> and <code>remove_at</code> shift every later element, so they are fine for short lists and slow inside a loop over a long one. <code>index_of</code> and <code>contains</code> scan from the front. The example also shows the copy trap from the list above: <code>alias</code> writes straight into <code>line</code>, while the clone keeps its own elements.</p>
{{example.collections-guide-vector}}
<p><code>slice</code> returns a new vector and clamps a range that runs past the end, so it never fails. Printing a vector with <code>println</code> shows its elements, which is handy while debugging.</p>

<h2 id="guide-hashmap">HashMap: stock by product code</h2>
<p>A <code>HashMap</code> finds a value by its key in constant time. <code>get</code> on a missing key returns the zero value of the type (0, empty text, a struct of zeros) and never fails, so ask <code>has</code> first when a missing key is an error, or use <code>get_or</code> when a default is right. Struct values come back as copies: change the copy and <code>put</code> it again.</p>
{{example.collections-guide-inventory}}
<p>Do not <code>put</code> or <code>remove</code> while an <code>each</code> loop walks the same map: a <code>put</code> can grow the table and move every entry. Collect the keys first, as the example does, then change the map.</p>

<h2 id="guide-stack">Stack: matching brackets</h2>
<p>A stack is the tool when the most recent thing must be dealt with first. Checking brackets is the classic case: push every opening bracket, and on a closing bracket the top of the stack must be its partner. <code>peek</code> looks at the top without removing it, and whatever is left at the end was never closed.</p>
{{example.collections-guide-brackets}}

<h2 id="guide-queue">Queue: shortest path in a grid</h2>
<p>A queue hands items out in the order they arrived, which is exactly what a breadth first search needs: every cell at distance 1 is handled before any cell at distance 2, so the first time the search reaches the exit, it has found a shortest path. <code>enqueue</code> adds at the back and <code>dequeue</code> takes from the front.</p>
{{example.collections-guide-maze}}

<h2 id="guide-deque">Deque and Stack together: undo with a limit</h2>
<p>An undo history adds at one end and, once it is full, drops the oldest step at the other end, so it needs a <code>Deque</code>. Undone steps go onto a <code>Stack</code> for redo, and any new edit clears that stack, as editors do.</p>
{{example.collections-guide-history}}

<h2 id="guide-counter">Counter and Set: counting words</h2>
<p><code>Counter</code> keeps a count for each value it has seen; <code>count</code> answers 0 for a value it never saw, so no check is needed first. A <code>Set</code> answers "have I seen this?" quickly and here keeps the words in order of first use. A stable sort by count then keeps that order among words with the same count.</p>
{{example.collections-guide-wordcount}}

<h2 id="guide-priority">PriorityQueue: the most urgent job first</h2>
<p><code>PriorityQueue</code> is a binary min-heap: <code>push</code> and <code>pop</code> take log n steps, and <code>pop</code> always returns the smallest element. It compares elements with <code>&lt;</code>, so it holds numbers or strings, not structs. To queue records, pack the priority and a position into one number, here <code>urgency * 1000 + index</code>, and keep the records in a vector. The position also breaks ties in arrival order, which a heap would not do by itself. For the largest first, push negative numbers.</p>
{{example.collections-guide-scheduler}}

<h2 id="guide-orderedmap">OrderedMap: settings that keep their order</h2>
<p>A <code>HashMap</code> gives its keys back in no particular order, which is a nuisance when you write a configuration file back to disk. <code>OrderedMap</code> keeps keys in the order they were first set; changing a value keeps its position, and <code>set</code> returns that position. <code>get_or</code> supplies a default for a missing key.</p>
{{example.collections-guide-config}}
