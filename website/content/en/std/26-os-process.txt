pkg.intro <<
<p>The <code>os.process</code> package runs another program directly, with no shell in between. The program's path and its arguments are given separately, so nothing has to be quoted and spaces or special characters in an argument cause no trouble. Use it to call tools such as <code>git</code>, <code>ffmpeg</code> or a compiler with file names that came from a user. For a quick one-line shell command use <a href="/std/os/">os</a> (<code>Run</code>, <code>RunCapture</code>) or <a href="/std/os/shell/">os.shell</a>; when a program cannot start at all, the reason is recorded in <a href="/std/os/error/">os.error</a>.</p>
<p>A run has up to four steps: <code>Start</code> or <code>StartCaptured</code> launches the program and returns at once, <code>Wait</code> blocks until it exits and returns the exit code, <code>ReadStdout</code> and <code>ReadStderr</code> read what a captured run printed, and <code>Cleanup</code> deletes the two temporary files that held it. A captured program gets an empty standard input.</p>
<p>For a program you talk to while it runs, with pipes, time limits and exit codes or signals, use <code>Command</code>, <code>Launch</code> and <code>Child</code>, described in the sections below. For a program that must see a terminal, use <a href="/std/os/pty/">os.pty</a>.</p>
<p>What people get wrong:</p>
<ul>
<li>Treating <code>IsRunning</code> as a live check. It reports a flag that <code>Start</code> sets and only <code>Wait</code>, <code>Kill</code> or <code>Terminate</code> clear; it stays true after the program has exited on its own.</li>
<li>Killing without waiting. <code>Kill</code> and <code>Terminate</code> only send the signal. Call <code>Wait</code> afterwards, or the finished process stays in the process table as a zombie.</li>
<li>Expecting a timeout from <code>Wait</code>. <code>Wait</code> on a <code>Process</code> waits as long as the program runs. To give up after a while use a <code>Child</code> (see below), whose <code>Wait</code> takes a time limit.</li>
<li>Forgetting <code>Cleanup</code>. Each captured run leaves two files in the temporary folder until you call it.</li>
</ul>
<div class="note"><p>On Windows the arguments are joined into one command line with quotes around those that contain spaces, and the ANSI <code>CreateProcessA</code> starts the program. An argument that itself contains a <code>"</code>, or text outside the system code page such as Persian, does not arrive intact there; <code>Fork</code> and <code>WaitPid</code> return -1.</p></div>
<h2 id="guide-args">Pass arguments exactly as they are</h2>
<p>Each element of the argument vector reaches the program as one argument, byte for byte. Spaces, quotes, a <code>$</code> or a <code>;</code> mean nothing special, because no shell reads them. That makes this package the safe way to pass file names and other text that came from a user.</p>
{{example.os-process-guide-args}}
<p>The program name is looked up on the <code>PATH</code> like in a terminal, so <code>printf</code> works without a full path. The vector does not include the program name itself; the package adds it. This exactness holds on Linux and macOS; see the note above for Windows.</p>

<h2 id="guide-exitcode">Exit code, output and error output</h2>
<p>A program reports success with exit code zero and anything else on failure, and it writes its complaints to the error output. After <code>Wait</code>, read both: <code>ReadStdout</code> for the results and <code>ReadStderr</code> for the reason it failed. Call <code>Cleanup</code> after reading, because the captured output is kept in temporary files until then.</p>
{{example.os-process-guide-exitcode}}

<h2 id="guide-parallel">Run several programs at once</h2>
<p><code>StartCaptured</code> returns as soon as the program has started, so you can start several and wait for them afterwards. The total time is about that of the slowest one rather than the sum of all. Waiting in the order you started them keeps the output in a fixed order, even when a later job finished first.</p>
{{example.os-process-guide-parallel}}
<p>Keep the number of programs you run at once reasonable; <a href="/std/os/platform/">os.platform</a>'s <code>CpuCount</code> is a good limit for work that keeps the processor busy.</p>

<h2 id="guide-helper">A helper that runs a program and returns its output</h2>
<p>Most programs need the same few lines every time: start, check that it started, wait, read, clean up. Put them in one function. A <code>defer</code> right after the start makes sure <code>Cleanup</code> runs on every way out of the function, and an out-parameter tells the caller whether the program succeeded.</p>
{{example.os-process-guide-helper}}

<h2 id="guide-stop">Stop a program</h2>
<p><code>Terminate</code> sends <code>SIGTERM</code>, which a well-behaved program catches to save its work and exit; <code>Kill</code> sends <code>SIGKILL</code>, which cannot be caught. Either way, <code>Wait</code> collects the program afterwards. A program ended by a signal reports 128 plus the signal number as its exit code, so 143 means <code>SIGTERM</code> and 137 means <code>SIGKILL</code>, the same numbers a shell shows.</p>
{{example.os-process-guide-stop}}
<h2 id="guide-launch">Talk to a running child</h2>
<p><code>Start</code> and <code>StartCaptured</code> run a program to the end. When you need to talk to it while it runs, describe it with a <code>Command</code> (<code>NewCommand</code> gives one for a program), pass it to <code>Launch</code>, and use the <code>Child</code> it returns. Set <code>stdin_mode</code>, <code>stdout_mode</code> and <code>stderr_mode</code> to <code>Pipe</code> (or call <code>Piped</code>) to connect a stream to your program, to <code>Null</code> to throw it away, or leave <code>Inherit</code> to share your own. <code>Merge</code> on the error stream puts it into the output pipe in the order it was written. <code>Arg</code>, <code>Env</code>, <code>Unset</code> and the <code>cwd</code> and <code>clear_env</code> fields set the arguments, the environment and the folder. Writing to a child that has already gone returns false and never kills your program.</p>
{{example.os-process-guide-launch}}

<h2 id="guide-read">Read with a time limit</h2>
<p>Every read takes a time in milliseconds: 0 only looks, a positive number waits that long, a negative number waits for ever. <code>ReadAvailable</code> returns whatever has arrived, <code>ReadLine</code> one complete line, <code>Read</code> an exact number of bytes, <code>ReadUntil</code> everything up to a given text (the way to wait for a prompt) and <code>ReadFor</code> everything that arrives in a period. A read returns a <code>Chunk</code>: check <code>timed_out</code> (nothing came, and the child may still be working) and <code>eof</code> (the stream ended) before using <code>data</code>, and <code>Free</code> it. Bytes that were read but not yet returned stay in the child, so a timed-out call loses nothing. The <code>ReadErr</code> methods do the same for the error pipe, and <code>ReadBytes</code> reads binary data into a buffer.</p>
{{example.os-process-guide-read}}

<h2 id="guide-status">Exit code or signal</h2>
<p><code>Child.Wait</code> takes a time limit and returns a <code>Status</code>. A child that ended by itself has <code>exited</code> set and its code in <code>code</code>; one that a signal ended has <code>signaled</code> set and the number in <code>signal</code>. This differs from <code>Process.Wait</code>, which folds a signal into 128 plus the number. <code>ReturnCode</code> gives the Python-style number (the code, or the negative signal), and <code>Success</code> is true for code 0. When the limit passes first, <code>timed_out</code> is set and the child keeps running; <code>Poll</code> asks whether it is still running without waiting.</p>
{{example.os-process-guide-status}}

<h2 id="guide-timeout">Run with a timeout</h2>
<p><code>RunTimeout</code> is the one-call version: it writes the input text, collects the whole output and error output, and kills the child when the time runs out. It reads both pipes while it writes, so a child that prints a megabyte on each stream cannot deadlock it. <code>RunCommand</code> does the same for a <code>Command</code> with an environment or folder. The result is a <code>RunResult</code>: <code>started</code>, <code>status</code>, <code>stdout</code>, <code>stderr</code> and <code>timed_out</code>; call <code>Free</code> on it.</p>
{{example.os-process-guide-timeout}}

<h2 id="guide-group">Stop a child and everything it started</h2>
<p>Kill a shell and the programs it started keep running. Start the child with <code>new_group</code> and <code>KillGroup</code> (or <code>SignalGroup</code> with any signal) stops the whole group. <code>RunTimeout</code> does this for you. <code>Signal</code>, <code>Kill</code> and <code>Terminate</code> reach only the child itself.</p>
{{example.os-process-guide-group}}
<p>On Unix a program that cannot be found, or a folder that cannot be entered, makes <code>Launch</code> return a child whose <code>ok</code> is false and whose <code>error</code> says why; the check happens before <code>Launch</code> returns, so there is no need to wait for an exit code 127.</p>
<div class="note"><p>On Windows <code>Launch</code> uses <code>CreateProcessW</code> and anonymous pipes. Every signal ends the child at once and is reported as a signal, <code>RunCommand</code> writes all of its input before it starts reading, and the pseudo terminal of <a href="/std/os/pty/">os.pty</a> is not available. The tests that start real children run on Linux and macOS.</p></div>

doc.Fork = Splits the current process in two: it returns zero in the child and the child's id in the parent. On Unix systems only; its example is not run here.
doc.ExitNow = Ends the process immediately with no cleanup at all, for finishing a child after <code>Fork</code>.
doc.Kill = Kills the process at once (SIGKILL); 0 when the signal was sent. Call <code>Wait</code> afterwards to collect it.
doc.Terminate = Asks the process to finish gracefully (SIGTERM) so it has a chance to clean up; call <code>Wait</code> afterwards. On Windows it is the same as <code>Kill</code>.
doc.ReadStdout = Reads the captured output once the process has finished; empty for a process started with <code>Start</code>. The text stops at the first zero byte.
doc.ReadStderr = Reads the captured error output; empty for a process started with <code>Start</code>.

doc.ExitCode = The process's exit code.

doc.Child.ReadBytes = Reads up to <code>max</code> bytes into a buffer you own. Returns the count, 0 on a timeout and -1 at the end of the stream.

doc.Child.ReadErrUntil = Like <code>ReadUntil</code>, for the error pipe.
doc.Child.ReadErrFor = Like <code>ReadFor</code>, for the error pipe.

doc.Child.Signal = Sends a signal to the child. On Windows every signal ends the child.

doc.Child.Terminate = Sends <code>SigTerm</code>, asking the child to finish.

doc.Launch = Starts a child as the command describes and returns at once. Check <code>ok</code>; when it is false, <code>error</code> and <code>os.error</code> say why.
doc.NewCommand = A command for a program, with every stream inherited and no arguments yet.

doc.RunTimeout = Runs a program with the given arguments and input text, collects its output and error output, and kills it, and everything it started, when the time in milliseconds runs out. The result tells whether it timed out.
