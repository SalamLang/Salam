pkg.intro <<
<p>For data that is only needed while the program runs, make a temporary file or directory. The names are unique, so several copies of the program running at once do not collide. Removing them is up to you.</p>
<h2 id="guide-scratch">A scratch directory for one job</h2>
<p>The usual pattern is three lines: make a directory with <code>Directory</code>, put <code>defer temp.RemoveDir(work)</code> right under it, and build every path inside it with <a href="/std/fs-path/">path.Join</a>. The deferred call runs on every way out of the function, an early <code>ret</code> included, so the directory is gone however the job ends. <code>Directory</code> returns an empty string when it cannot make the directory, so check for that before you use it.</p>
{{example.os-temp-scratch}}

<h2 id="guide-staging">Build a file in steps, then publish it</h2>
<p>When a file is written in several steps, write it to a temporary file first and copy it to its real name only when it is complete. Whoever reads <code>people.csv</code> then never sees half of it. Use <code>file.Copy</code> here, not <code>file.Move</code>: the temporary directory is often on another disk (a <code>tmpfs</code> in memory on many Linux systems), and a rename cannot cross disks.</p>
{{example.os-temp-staging}}
<p>When the whole content is ready in one string, <a href="/std/fs-file/">fs.file.AtomicWrite</a> is simpler: it writes the temporary copy next to the target, on the same disk, and renames it in one step.</p>

<h2 id="guide-permissions">Who can read a temporary file</h2>
<p>The system temporary directory is shared by every account on the machine. That is why <code>File</code> makes its file readable and writable by you alone (<code>600</code>) and <code>Directory</code> makes its directory open to you alone (<code>700</code>). A token or a downloaded document you put there stays out of reach of other users. Leave it like that, and widen the permissions with <a href="/std/fs/">fs.Chmod</a> only when another account really has to read the file.</p>
{{example.os-temp-permissions}}

<h2 id="guide-errors">Errors, and where the files go</h2>
<p><code>Remove</code> and <code>RemoveDir</code> return <code>0</code> on success and <code>-1</code> on failure, and they record the reason in <a href="/std/os-error/">os.error</a>. The usual failure is removing the same file twice:</p>
{{example.os-temp-errors}}
<p>The files go into the directory that <a href="/std/os/">os.TempDir</a> names: the <code>TEMP</code>, <code>TMP</code> or <code>TMPDIR</code> environment variable, checked in that order, and <code>/tmp</code> when none is set. Nothing removes them when the program exits, and a program that crashes leaves them behind, so a long running service should give each job its own directory and remove it when the job is done. The names are random (<code>salam-</code> and hex digits), so never compare them or show them in output that someone reads later.</p>
>>
