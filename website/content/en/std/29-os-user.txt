pkg.intro <<
<p>Programs usually keep their settings in the user config directory and throwaway data in the user cache directory. This package gives the right path on every operating system; the config directory, for instance, is <code>~/.config</code> on Linux and macOS and <code>%APPDATA%</code> on Windows.</p>
<h2 id="guide-resolve">How the directories are found</h2>
<p>These functions do not ask the operating system for a list of folders. They read environment variables, the same way most command line tools do, which also means that whoever starts the program can point them somewhere else:</p>
<div class="table-wrap"><table>
<thead><tr><th>Function</th><th>Linux, macOS and BSD</th><th>Windows</th></tr></thead>
<tbody>
<tr><td><code>HomeDir</code></td><td><code>$HOME</code></td><td><code>%USERPROFILE%</code></td></tr>
<tr><td><code>ConfigDir</code></td><td><code>$XDG_CONFIG_HOME</code>, else <code>~/.config</code></td><td><code>%APPDATA%</code></td></tr>
<tr><td><code>CacheDir</code></td><td><code>$XDG_CACHE_HOME</code>, else <code>~/.cache</code></td><td><code>%LOCALAPPDATA%</code></td></tr>
<tr><td><code>Username</code></td><td><code>$USER</code>, else <code>$LOGNAME</code>, else the user database</td><td><code>%USERNAME%</code></td></tr>
</tbody>
</table></div>
<p>The example sets the variables itself with <a href="/std/env/">env.Set</a>, so it prints the same on every Unix machine:</p>
{{example.os-user-resolve}}

<h2 id="guide-app-dirs">Settings and cache for your own program</h2>
<p>Give your program its own folder inside each of these directories, named after the program, and create it with <a href="/std/fs-dir/">dir.MkdirAll</a> before the first write: on a fresh account even <code>~/.config</code> may not exist yet. Settings belong in the config folder. Anything you can rebuild, such as downloads or a search index, belongs in the cache folder, which the user or a cleanup tool may empty at any time.</p>
<p>The first line of this example points <code>HOME</code> at a folder in the current directory so that running it does not touch your real settings. A real program leaves that line out.</p>
{{example.os-user-app-dirs}}

<h2 id="guide-expand-home">Expanding ~ in paths from users</h2>
<p>The shell turns <code>~/notes</code> into a full path before your program sees it, but a path read from a settings file or typed at a prompt still starts with <code>~</code>. Neither <a href="/std/fs-file/">fs.file</a> nor <a href="/std/fs-path/">fs.path</a> expands it, so replace it yourself with <code>HomeDir</code>:</p>
{{example.os-user-expand-home}}

<h2 id="guide-pitfalls">Things to watch for</h2>
<ul>
<li><code>Username</code> is fine for a greeting or a log line, but it comes from environment variables that anyone starting the program can change. Never use it to decide what someone is allowed to do.</li>
<li><code>Uid</code> and <code>Gid</code> are <code>-1</code> on Windows. On Unix a <code>Uid</code> of <code>0</code> means the program runs as root, which is worth a warning in a tool that should not.</li>
<li>Each function returns an empty string when its variable is not set, for example in a service started with an empty environment. Check the length before you join a path onto it; otherwise the path silently becomes relative to the current directory.</li>
</ul>
>>
