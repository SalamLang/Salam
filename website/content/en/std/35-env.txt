pkg.intro <<
<p>Settings such as a server port, a database address and API keys belong in environment variables rather than in the code. The <code>env</code> package reads them with the right type and gives you a default when they are not set. It can load them from a <code>.env</code> file too.</p>
<p>The "profile" is read from <code>SALAM_ENV</code> and says whether the program is running in development, test or production. When <code>SALAM_ENV</code> is not set, <code>APP_ENV</code> and then <code>ENV</code> are tried, and the default is <code>development</code>. The value is lower-cased, and <code>prod</code>, <code>dev</code> and <code>testing</code> count as the long names.</p>

<h2 id="guide-config">Reading the whole configuration at start-up</h2>
<p>Read every setting once, in one function, into a struct. The rest of the program then takes the struct and never calls <code>env</code> itself, which keeps the list of variables in one place and makes the code easy to test. Print the configuration at start-up, but pass secrets through <code>Mask</code> first.</p>
{{example.env-guide-config}}

<h2 id="guide-dotenv">What a .env file can contain</h2>
<p>A <code>.env</code> file has one <code>NAME=value</code> per line. Lines starting with <code>#</code> are comments, a leading <code>export</code> is allowed so the same file works with a shell, and values may be in double or single quotes. Inside double quotes and unquoted values, <code>${NAME}</code> is replaced; single quotes keep the text exactly as written.</p>
{{example.env-guide-dotenv}}
<p>Three things to notice. <code>Load</code> never replaces a variable that is already set, so <code>APP_PORT</code> stays <code>3000</code>, and the number it returns counts only the variables it actually set. A <code>${APP_PORT}</code> inside the file uses the file's own value. And an empty value is set but empty: <code>Has</code> says true while <code>GetOr</code> gives the default.</p>

<h2 id="guide-profiles">One set of files per environment</h2>
<p><code>LoadProfile</code> reads up to four files from a folder, later ones winning over earlier ones: <code>.env</code>, <code>.env.local</code>, <code>.env.&lt;profile&gt;</code> and <code>.env.&lt;profile&gt;.local</code>. Commit the first and third, and keep the <code>.local</code> files, which hold each developer's own values and secrets, out of version control. A variable that is already set in the real environment still wins over every file.</p>
{{example.env-guide-profiles}}
<p>Here <code>DB_HOST</code> comes from <code>.env.production</code>, <code>LOG_LEVEL</code> from <code>.env.production.local</code>, and <code>CACHE</code> stays <code>on</code> because it was set before loading. Missing files are skipped without an error.</p>

<h2 id="guide-expand">Filling a template with variables</h2>
<p><code>Expand</code> replaces <code>${NAME}</code> in any text, and <code>${NAME:-default}</code> uses the default when the variable is unset or empty. It suits connection strings and paths that are partly configured. An unknown name without a default becomes an empty string, so check the important variables with <code>Has</code> first.</p>
{{example.env-guide-expand}}

<h2 id="guide-pitfalls">Pitfalls</h2>
<ul>
<li><code>GetInt</code> and <code>GetFloat</code> return the default only when the variable is unset or empty. A value that is not a number is not rejected: <code>abc</code> gives <code>0</code> and <code>12px</code> gives <code>12</code>. Check the value yourself when a wrong setting must stop the program.</li>
<li><code>GetBool</code> treats anything it does not recognise as <code>false</code>, whatever the default.</li>
<li><code>Load</code> keeps existing values, <code>Overload</code> replaces them, and <code>LoadDotEnv</code> replaces them too. Use <code>Load</code> when the real environment should win, which is what you want in production.</li>
<li><code>Set</code> changes the environment of this program and of the processes it starts afterwards, never the shell that started it.</li>
</ul>
>>

doc.Get = The value of a variable, or an empty string.
doc.GetOr = The value of a variable, or the default when it is not set.
doc.Has = True when the variable is set.
doc.GetInt = The value as a whole number, or the default when it is not set or is empty. A value that is not a number is not rejected: <code>abc</code> gives 0 and <code>12px</code> gives 12.
doc.GetFloat = The value as a decimal number, or the default when it is not set or is empty.
doc.GetBool = The value as a boolean; <code>true</code>, <code>1</code> and <code>yes</code> count as true.
doc.Set = Sets a variable for this program and for the processes it starts afterwards.
doc.Unset = Removes a variable.
doc.Mask = Masks a sensitive value for a log, showing only the first and last two characters.
doc.GetMasked = Returns a variable's value masked.
doc.Profile = The name of the run profile, from <code>SALAM_ENV</code>.
doc.IsProduction = True in the <code>production</code> profile.
doc.IsDevelopment = True in the <code>development</code> profile.
doc.IsTest = True in the <code>test</code> profile.
doc.IsStaging = True in the <code>staging</code> profile.
doc.Load = Loads a <code>KEY=VALUE</code> file without changing variables that are already set. It returns how many variables it set.
doc.Overload = Like <code>Load</code>, but it replaces existing variables with the file's values too.
doc.LoadText = Does the same from text instead of a file.
doc.LoadDotEnv = Loads the <code>.env</code> file and, like <code>Overload</code>, replaces variables that are already set.
doc.LoadProfile = Loads the <code>.env.&lt;profile&gt;</code> file from the given directory, such as <code>.env.test</code> in the test profile.
doc.Expand = Replaces <code>${name}</code> and <code>${name:-default}</code> in text with the values of the variables.
