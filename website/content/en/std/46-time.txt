pkg.intro <<
<p>The <code>time</code> package reads the clock, turns dates into text and back, does date arithmetic, measures how long code takes and waits. It works with two kinds of value:</p>
<ul>
<li>An <strong>instant</strong> is an <code>i64</code> count of seconds since the start of 1970 in UTC, the Unix epoch. <code>Now</code> returns one, and dates are stored, compared and sent as instants.</li>
<li>A <strong>duration</strong> is a <code>Duration</code>, a span with nanosecond precision such as <code>1h30m</code>, which you can add up, compare and print.</li>
</ul>
<p>There are also two clocks. The <strong>wall clock</strong> (<code>Now</code>, <code>NowMillis</code>) tells the date and can jump when the system time is set. The <strong>monotonic clock</strong> (<code>MonoNanos</code>) only moves forward and is the one to measure spans and deadlines with; timers and tickers use it.</p>
<p>For the Persian and Hijri calendars and for named time zones such as <code>Asia/Tehran</code>, see <a href="/std/calendar/">calendar</a>. For timing parts of a program while you debug it, <a href="/std/debug/">debug</a> has named timers.</p>
<p>The things people get wrong:</p>
<ul>
<li><code>Year</code>, <code>FormatDate</code>, <code>Format</code>, <code>FormatISO</code> and <code>Weekday</code> use the machine's local time zone, so the same instant prints differently on a server set to UTC and a laptop in Tehran. Use the <code>...UTC</code> functions and <code>FormatISOUTC</code> for anything stored or compared.</li>
<li><code>FormatISO</code> has no offset, so the text cannot be read back to the same instant on another machine. Send <code>FormatISOUTC</code> or <code>FormatRFC3339</code>.</li>
<li><code>Days(30)</code> is 30 times 24 hours, not a month. There is no month arithmetic; build the date with <code>FromUTCParts</code> and a month one higher (it rolls 13 over into January).</li>
<li><code>FromUTCParts</code> and <code>FromLocalParts</code> accept any numbers and roll over: 30 February becomes 1 March. The parse functions, by contrast, reject a day that the month does not have.</li>
<li>Timing code with <code>Now</code>. It has whole seconds and follows clock changes; use <code>MonoNanos</code>.</li>
</ul>

<h2 id="guide-dates">Dates from text, and date arithmetic</h2>
<p>Dates usually arrive as text: from JSON, a database or a form. <code>ParseISO</code> reads the ISO 8601 form and returns a <code>TimeResult</code>; check <code>ok</code> before using <code>epoch</code>, because bad input is common. Once you have an instant, arithmetic is plain integer arithmetic: <code>AddDuration</code> moves it, and <code>DiffSeconds</code> gives the distance between two instants.</p>
{{example.time-guide-expiry}}
<p>The example fixes "today" with <code>FromUTCParts</code> so its output never changes; a real program would use <code>Now()</code>. Adding <code>Days(30)</code> adds exactly 30 times 24 hours. In UTC that is always 30 calendar days, but in a zone with daylight saving the local clock time can move by an hour, so keep stored instants in UTC and convert only for display.</p>

<h2 id="guide-durations">Timeouts from settings</h2>
<p>A setting such as <code>timeout = 1m30s</code> is easier to read than a number of milliseconds. <code>ParseDuration</code> understands <code>h</code>, <code>m</code>, <code>s</code>, <code>ms</code>, <code>us</code> and <code>ns</code>, in any combination and with fractions. Check the value against sensible limits too: a parse that worked is not yet a value that makes sense.</p>
{{example.time-guide-timeouts}}
<p>Durations add, subtract, multiply and compare without any unit conversions, and <code>to_str</code> prints them in the same short form that <code>ParseDuration</code> reads. When a quick default is enough, <code>ParseDurationOr</code> does the parse and the fallback in one call.</p>

<h2 id="guide-schedule">The next run of a daily job</h2>
<p>An instant is seconds since 1970 in UTC, so the start of its UTC day is <code>t - t % SecondsPerDay</code>, and the time of day is the rest. That is enough to work out when a job that runs every night at 02:30 UTC should run next.</p>
{{example.time-guide-schedule}}
<p>1 January 1970 was a Thursday, which is why the weekday table starts there. <code>Weekday</code> gives the same answer for the machine's local time. <code>FormatHTTPDate</code> is the form HTTP headers such as <code>Last-Modified</code> and <code>Expires</code> need.</p>

<h2 id="guide-ticker">Heartbeats, deadlines and waiting for a condition</h2>
<p>A <code>Ticker</code> fires at a fixed interval: <code>wait</code> sleeps until the next tick, and if the program comes back late it skips the missed ticks instead of firing them all at once, counting them in <code>dropped</code>. A <code>Timer</code> is a single deadline you check with <code>expired</code>, here an upper limit for the whole loop. <code>WaitUntil</code> checks a condition every <code>poll</code> until it holds or <code>limit</code> runs out, which is the usual way to wait for a server or a file to appear.</p>
{{example.time-guide-ticker}}
<p>All of these run on the calling thread and block it. To do other work between ticks, call <code>fired</code> in your loop instead of <code>wait</code>; to run something truly in the background, start a <a href="/std/thread/">thread</a>.</p>

<h2 id="guide-measure">Measuring how long code takes</h2>
<p>Take <code>MonoNanos</code> before the work and pass it to <code>SinceDuration</code> after. The monotonic clock only moves forward, so the result is right even if the system clock is changed while the code runs; <code>Now</code> is for dates, not for timing.</p>
{{example.time-guide-measure}}
<p>The example prints only comparisons, because the measured time is different on every run. To find the slow part of a larger program, the <a href="/std/debug/">debug</a> package has named timers that build on the same clock.</p>
