<p>MessagePack holds the same data as JSON in a shorter binary form that is quicker to read, which suits messages between services, cache entries and RPC. This package turns a <a href="/std/encoding/value/">Value</a> into a <code>compress.ByteBuf</code> with <code>Marshal</code> and reads one back with <code>Unmarshal</code> (or <code>UnmarshalBytes</code> for raw memory). Errors arrive in an <a href="/std/encoding/encerr/">EncodingError</a>.</p>
<p>Pick it over <a href="/std/encoding/json/">encoding/json</a> when both ends are programs and size or speed matters; keep JSON when people read the data or a browser consumes it. For a fixed binary layout of your own, such as a file header, write the fields directly with <a href="/std/encoding/binary/">encoding/binary</a>; for schemas shared across languages, <a href="/std/encoding/protobuf/">encoding/protobuf</a>.</p>

<h3 id="pitfalls">What trips people up</h3>
<ul>
<li><strong>No <code>bin</code> or <code>ext</code> types.</strong> Data from another library that stores bytes as <code>bin</code>, or timestamps as <code>ext</code>, fails with <code>KindCustom</code>. Strings stop at the first zero byte, so binary data cannot ride in a string either; Base64 it first.</li>
<li><strong>Map keys must be strings.</strong> A map with integer keys, as some other libraries write, is read with every key turned into <code>""</code>, so the entries overwrite each other.</li>
<li><strong>Trailing bytes are ignored.</strong> <code>Unmarshal</code> reads one value and does not report what follows it or how many bytes it used, so you cannot read several messages from one buffer. Frame each message yourself, for example with a 4-byte length in front.</li>
<li><strong>Reset the error between calls.</strong> <code>Unmarshal</code> returns null at once if the <code>EncodingError</code> you pass already holds an error.</li>
<li><strong>Integers above <code>i64</code></strong> (a <code>uint64</code> over 9223372036854775807) wrap around to negative numbers.</li>
</ul>

<h2 id="guide-size">Guide: how much smaller is it?</h2>
<p>MessagePack drops the quotes, colons and commas of JSON, and stores numbers and lengths in as few bytes as it can. For records with short keys and small numbers it usually comes to a half or two thirds of compact JSON. Decode JSON into a <a href="/std/encoding/value/">Value</a> once, and <code>Marshal</code> writes it as MessagePack.</p>
{{example.encoding-msgpack-guide-size}}
<p>The keys are still written in full in every record, so long key names cost as much as in JSON. If size matters more than that, compress the buffer as well with <a href="/std/compress/">compress</a>.</p>

<h2 id="guide-bytes">Guide: what the bytes look like</h2>
<p>Each value starts with a type byte. Small integers from 0 to 127 are a single byte, larger ones get a marker such as <code>cc</code> (one byte follows) or <code>ce</code> (four bytes follow). Short strings, arrays and maps carry their length in the first byte: <code>a2</code> is a string of 2 bytes, <code>92</code> an array of 2 items, <code>81</code> a map with one pair.</p>
{{example.encoding-msgpack-guide-bytes}}
<p>The program reads the buffer byte by byte with <code>compress.BufGet</code>. Turning the buffer into a <code>str</code> first would not work: <code>70000</code> contains a zero byte, and a <code>str</code> ends at the first zero. Keep MessagePack data in its <code>ByteBuf</code>, or use <code>BufToBase64</code> when you need text.</p>

<h2 id="guide-cache">Guide: structs in a cache</h2>
<p>A cache such as Redis stores bytes, and MessagePack bytes are quicker to read back than JSON. For a struct, go through JSON on the way in and out: <code>json.Marshal</code> and <code>json.Decode</code> give a Value to pack, and <code>json.Unmarshal</code> fills the struct from the unpacked Value. Here a <code>HashMap</code> stands in for the cache.</p>
{{example.encoding-msgpack-guide-cache}}
<p>For a real cache, send <code>b.data</code> and <code>b.len</code> to the client library as a binary value, and decode what comes back with <code>UnmarshalBytes</code>.</p>

<h2 id="guide-errors">Guide: broken, cut and foreign buffers</h2>
<p>Network reads can stop halfway, and other programs may use parts of MessagePack this package does not read. Both <code>Unmarshal</code> and <code>UnmarshalBytes</code> report a buffer that ends in the middle of a value as <code>KindUnexpectedEOF</code>, so you can tell "wait for more bytes" apart from data that is simply wrong.</p>
{{example.encoding-msgpack-guide-errors}}
<p>The third case is a <code>bin</code> value, type byte <code>c4</code>, as written by libraries that keep bytes apart from strings; it fails with <code>KindCustom</code>. Ask the sender to use strings, or Base64 the bytes, when it has to talk to Salam. The last case shows that one stray byte after a complete value is not noticed, which is why a stream of messages needs its own framing.</p>
>>
