pkg.intro <<
<p>Binary file formats and network protocols store a number as several bytes in a row. <strong>Big-endian</strong> writes the most significant byte first and is the usual order in network protocols; <strong>little-endian</strong> is the other way round and is what most processors use, and formats such as ZIP.</p>
<p>The writing functions take a <code>ByteBuf</code> and the reading functions take a <code>ByteReader</code>, both from the <a href="../compress/">compress</a> package.</p>

<h2 id="guide-header">Guide: your own file format</h2>
<p>A binary format usually starts with a few magic bytes that identify it, then a version number and a count, then the records. Write each field with the function for its size and byte order, and read them back in exactly the same order. <code>compress.BufPushBytes</code> writes a fixed text such as the magic, and <code>compress.RdBytes</code> reads it back.</p>
{{example.encoding-binary-guide-header}}
<p>Check the magic and the version before trusting the rest; an old or foreign file then fails with a clear message instead of nonsense numbers. Keep one byte order for the whole format and write it down in its description.</p>

<h2 id="guide-png">Guide: read a header of a real format</h2>
<p>PNG is a good example of a big-endian format. A file starts with an 8 byte signature, then chunks, each with a 4 byte length, a 4 letter type and the data. The first chunk, <code>IHDR</code>, holds the width and height as big-endian 32 bit numbers. The program builds those first bytes itself so it runs without a file; with a real image, read the file into a buffer first and the parsing is the same.</p>
{{example.encoding-binary-guide-png}}

<h2 id="guide-frames">Guide: length-prefixed messages</h2>
<p>A TCP connection delivers a stream of bytes, not separate messages. The usual fix is to send each message with its length in front, here as a 16 bit big-endian number. The reader takes the length, checks that the whole message has arrived with <code>RdLeft</code>, and only then reads it.</p>
{{example.encoding-binary-guide-frames}}
<p>The length counts bytes, so <code>سلام</code> is 8, not 4. The last frame says 10 bytes but only 3 have arrived; a real server keeps those bytes and tries again when more data comes in.</p>

<h2 id="guide-endian">Guide: byte order and sign mistakes</h2>
<p>Reading with the wrong byte order does not fail, it just gives a wrong number, so these bugs are easy to miss. Unsigned 32 bit values are another trap: they come back in an <code>int</code>, so anything at or above 2,147,483,648 looks negative. Widen it to <code>i64</code> and mask it to get the unsigned value.</p>
{{example.encoding-binary-guide-endian}}
<p>Reading past the end does not stop the program either; the missing bytes simply read as zero. When the input comes from outside, check <code>compress.RdLeft</code> before each read, as the framing example does.</p>
>>
