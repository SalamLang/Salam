pkg.intro <<
<p>Binary file formats and network protocols store each number as a fixed number of bytes in a fixed order. This package writes and reads such fields: 8, 16, 32 and 64 bit integers, signed or unsigned, and 32 or 64 bit IEEE 754 floats. <strong>Big-endian</strong> (<code>BE</code>) puts the most significant byte first and is the usual order on the network and in PNG; <strong>little-endian</strong> (<code>LE</code>) is the other way round and is what x86 and ARM processors use, and formats such as ZIP and WAV.</p>
<p>Writers append to a <code>ByteBuf</code> and readers advance a <code>ByteReader</code>, both from <a href="/std/compress/">compress</a>; that package also has <code>BufPushBytes</code> and <code>RdBytes</code> for raw byte runs such as magic numbers. Use this package when the layout is fixed by a specification or by you. For self-describing data use <a href="/std/encoding/msgpack/">encoding.msgpack</a> or <a href="/std/encoding/protobuf/">encoding.protobuf</a>; for hex or Base64 text, <a href="/std/encoding/">encoding</a>.</p>
<p>For random access into bytes you already have, such as a file read whole or a memory-mapped binary, use a <code>View</code>: <code>GetU32LE(view, offset)</code> and its relatives read a number at any offset, <code>PutU32LE</code> and its relatives write one, and <code>CStringAt</code> and <code>FixedStringAt</code> read the names that executable formats store. A view checks every access against its length: a getter returns 0 outside it and a setter returns false, so a damaged header cannot read beyond the buffer; call <code>Has</code> first when 0 is a legal value.</p>
<h3 id="pitfalls">What trips people up</h3>
<ul>
<li><strong>Every <code>Read...</code> function is <code>throws</code>.</strong> When fewer bytes are left than the value needs, it throws a core <code>Error</code> of kind <code>UnexpectedEnd</code> with the code <code>binary.unexpected_end</code> and the reader's position in <code>offset</code>, and the reader does not move. Call it with <code>try</code> inside a decoder that is itself <code>throws</code>, so a truncated file stops with an error instead of decoding zeros. The check costs one comparison per value; a loop of 10 million <code>ReadU32LE</code> calls took about 3 ms with the LLVM backend and about 100 ms with the C backend (gcc or tcc) on a busy 6 core x86-64 machine.</li>
<li><strong>32-bit unsigned values come back in an <code>int</code></strong>, which is signed, so values from 2,147,483,648 up look negative. <code>ReadU32BE</code> and <code>ReadI32BE</code> return the same bits. Widen with <code>(v as i64) &amp; 4294967295</code>.</li>
<li><strong>64-bit unsigned is an <code>i64</code></strong> too, so values above 9,223,372,036,854,775,807 are negative.</li>
<li><strong>Writers do not range check.</strong> <code>WriteU8(b, 300)</code> writes 44, the low 8 bits.</li>
<li><strong><code>BinaryOptions</code> is not used</strong> by any function yet; the float functions take a <code>big_endian</code> bool instead, and the integer functions carry the order in their names.</li>
</ul>

<h2 id="guide-header">Guide: your own file format</h2>
<p>A binary format usually starts with a few magic bytes that identify it, then a version number and a count, then the records. Write each field with the function for its size and byte order, and read them back in exactly the same order. <code>compress.BufPushBytes</code> writes a fixed text such as the magic, and <code>compress.RdBytes</code> reads it back.</p>
{{example.encoding-binary-guide-header}}
<p><code>read_file</code> checks the magic and the version before trusting the rest, and refuses a count that is too large to be real, so a damaged file cannot make it loop for a long time. It then reads every record with <code>try</code>, so the 18-byte copy, which has room for only two of the three scores, stops at the third with the offset where the data ran out. The checks of its own throw an <code>Error</code> too, so the caller handles every failure in one <code>catch</code>. Changing byte 4 turns the version into 9, which is refused. Keep one byte order for the whole format and write it down in its description.</p>

<h2 id="guide-png">Guide: read a header of a real format</h2>
<p>PNG is a good example of a big-endian format. A file starts with an 8 byte signature, then chunks, each with a 4 byte length, a 4 letter type and the data. The first chunk, <code>IHDR</code>, holds the width and height as big-endian 32 bit numbers. The program builds those first bytes itself so it runs without a file; with a real image, read the file into a buffer first and the parsing is the same.</p>
{{example.encoding-binary-guide-png}}

<h2 id="guide-frames">Guide: length-prefixed messages</h2>
<p>A TCP connection delivers a stream of bytes, not separate messages. The usual fix is to send each message with its length in front, here as a 16 bit big-endian number. The reader takes the length, checks that the whole message has arrived with <code>RdLeft</code>, and only then reads it.</p>
{{example.encoding-binary-guide-frames}}
<p>The length counts bytes, so <code>سلام</code> is 8, not 4. The last frame says 10 bytes but only 3 have arrived; a real server keeps those bytes and tries again when more data comes in.</p>

<h2 id="guide-endian">Guide: byte order and sign mistakes</h2>
<p>Reading with the wrong byte order does not fail, it just gives a wrong number, so these bugs are easy to miss. Unsigned 32 bit values are another trap: they come back in an <code>int</code>, so anything at or above 2,147,483,648 looks negative. Widen it to <code>i64</code> and mask it to get the unsigned value.</p>
{{example.encoding-binary-guide-endian}}
<p>Reading past the end, on the other hand, is never silent: the last read throws <code>binary.unexpected_end</code>. Check <code>compress.RdLeft</code> first when running out of data is normal rather than an error, as the framing example does for a frame that has not fully arrived.</p>
>>
