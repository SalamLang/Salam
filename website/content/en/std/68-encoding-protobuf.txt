pkg.intro <<
<p>Protocol Buffers is Google's binary format for structured messages. The shape of the messages is defined in a <code>.proto</code> file, and this package reads it, generates Salam code for the messages and services, and also carries the low level tools for writing and reading fields.</p>
<p>In the bytes, every field comes as a <strong>tag</strong>, the field number and the wire type, followed by its value. Numbers are usually written as a <strong>varint</strong>: each byte holds 7 bits of the number and its top bit says whether another byte follows.</p>

<p>The guide below works through the jobs you meet in practice: writing a message by hand, reading one back while skipping fields you do not know, nesting messages, choosing between <code>int64</code> and <code>sint64</code>, and generating the code from a <code>.proto</code> file instead of writing it. Every byte buffer here is a <code>compress.ByteBuf</code> from <a href="/std/compress/">compress</a>, so programs import both packages.</p>

<h2 id="guide-encode">Writing a message by hand</h2>
<p>A message is nothing more than its fields one after another. For each field call <code>WriteTag</code> with the field number from the <code>.proto</code> file and the wire type, then the writer for the value: <code>WriteVarint</code> for integers, enums and booleans, <code>WriteLenPrefixedStr</code> for strings and <code>WriteLenPrefixedBytes</code> for bytes and nested messages. The program below writes <code>User { id: 42, name: "Sara", admin: true }</code> and prints the bytes in hex.</p>
{{example.encoding-protobuf-encode-user}}
<p>Read the output in pairs: <code>08</code> is field 1 with wire type 0, <code>2a</code> is 42; <code>12</code> is field 2 with wire type 2, <code>04</code> the length and then the four letters; <code>18 01</code> is field 3 set to true. Proto3 leaves out fields that hold their default value (0, an empty string, false), so a sender usually checks the value before it writes the tag.</p>

<h2 id="guide-decode">Reading a message and skipping unknown fields</h2>
<p>Decoding is a loop: read a tag, look at the field number, read the value with the reader that matches, and repeat until the reader is empty. A field number you do not know must still be stepped over, which is what <code>SkipField</code> does with the wire type. That is how an old program keeps reading messages from a newer one that added fields. Every reader takes the same <code>ok</code> flag, so one check after the loop catches a message that was cut short.</p>
{{example.encoding-protobuf-decode-loop}}
<p>The second call reads the same bytes minus the last two: the string length promises four bytes that are not there, <code>ReadLenPrefixedStr</code> clears <code>ok</code>, and the loop stops. Always test <code>ok</code> before you trust the struct you filled.</p>

<h2 id="guide-nested">Nested and repeated messages</h2>
<p>A field whose type is another message is written as bytes: encode the inner message into its own buffer, then write it with wire type <code>WT_LEN</code> and <code>WriteLenPrefixedBytes</code>. A <code>repeated</code> field is the same tag written once per element. On the reading side <code>ReadLenPrefixedBuf</code> hands you the inner bytes as a new buffer, which you decode with the same loop and then free.</p>
{{example.encoding-protobuf-nested}}

<h2 id="guide-zigzag">Negative numbers: int64 or sint64</h2>
<p>A plain <code>int32</code> or <code>int64</code> field writes a negative number as a huge unsigned value, which always takes ten bytes. The <code>sint32</code> and <code>sint64</code> types first map the number with ZigZag (0, -1, 1, -2 become 0, 1, 2, 3), so small negative numbers stay small. Use <code>ZigZagEncode64</code> before <code>WriteVarint</code> and <code>ZigZagDecode64</code> after <code>ReadVarint</code>, and pick <code>sint64</code> in the <code>.proto</code> file for fields such as offsets or temperature deltas that are often below zero.</p>
{{example.encoding-protobuf-zigzag}}

<h2 id="guide-generate">Generating the code from a .proto file</h2>
<p>For more than a couple of messages, let the package write the code. <code>GenerateSingle</code> turns a <code>.proto</code> source into a Salam package with one struct per message and a <code>Marshal</code> and <code>Unmarshal</code> function for each; <code>GenerateWithServices</code> adds gRPC client stubs for the services (see <a href="/std/grpc/">grpc</a>). The program below prints only the declarations of the generated code.</p>
{{example.encoding-protobuf-codegen}}
<p>Save the text to a file such as <code>point_pb.salam</code>, add <code>include pb "point_pb.salam"</code> to your program, and call <code>pb.MarshalPoint(p)</code> to get a <code>ByteBuf</code> and <code>pb.UnmarshalPoint(buf.data, buf.len, ok)</code> to read one back. The generator covers scalar fields, strings, bytes and repeated scalars. It leaves out fields whose type is another message or an enum, so write those few by hand as in the nested example above, or keep the enum as an <code>int32</code> in the <code>.proto</code> file.</p>
