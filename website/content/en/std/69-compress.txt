pkg.intro <<
<p>This package is the base of all binary data work in Salam. <code>ByteBuf</code>, a growable byte buffer, and <code>ByteReader</code>, a cursor over bytes, are what packages such as <a href="/std/encoding/binary/">encoding.binary</a>, <a href="/std/archive/">archive</a> and <a href="/std/encoding/msgpack/">encoding.msgpack</a> pass around. On top of them it has gzip, bzip2, raw DEFLATE, a few teaching compressors (RLE, LZ77, LZW, Huffman, BWT), bit-level reading and writing, and the CRC-32 and Adler-32 checksums.</p>
<p>To pack several files into one <code>.zip</code> or <code>.tar</code>, use <a href="/std/archive/">archive</a>, which calls this package for the compression. To write numbers in a fixed byte order, use <a href="/std/encoding/binary/">encoding.binary</a> on the same buffers.</p>
<p>For compression, reach for <strong>gzip</strong> when the data has to be read by other programs. Use <strong>bzip2</strong> when the result should be smaller than gzip and a slower pack is fine; it reads and writes standard <code>.bz2</code> data. The other methods are mostly there to learn from and experiment with, and their output format belongs to this package alone. The examples show that for small data the overhead of Huffman and DEFLATE comes to more than the data itself.</p>

<h3 id="pitfalls">What trips people up</h3>
<ul>
<li><strong>Gzip verifies its checksum.</strong> <code>GzipDecompress</code> checks the header, inflates the data, then compares both the CRC-32 and the uncompressed length in the trailer; a mismatch sets <code>ok</code> false and returns an empty buffer.</li>
<li><strong>Xz and LZMA writing is a fast match finder, not a tuned one.</strong> The packed size is within a few percent of <code>xz</code> at the same level, never smaller. The whole input and the whole result are held in memory, and level 9 asks for a 64 MiB window. The result of a decoder is kept whole in memory too, so use the <code>...Max</code> functions on data you did not make yourself.</li>
<li><strong>Zstandard output is valid, not the smallest.</strong> The writer is simple, so <code>ZstdCompressLevel</code> makes frames usually a quarter to a half larger than the <code>zstd</code> tool at the same level; every reader still accepts them. Reading is complete, but only <code>ZstdDecompressDict</code> and <code>ZstdDecompressEx</code> take a dictionary, and the decoder holds the whole result in memory, so use <code>ZstdDecompressMax</code> on data from outside.</li>
<li><strong>Bzip2 checks every checksum and can be capped.</strong> <code>Bzip2Decompress</code> verifies each block CRC and the whole stream CRC and rejects broken tables and indexes, and it accepts several streams one after another and nothing else after them. A tiny file can expand to a huge one, so use <code>Bzip2DecompressMax</code> on data from outside.</li>
<li><strong>The method is not stored.</strong> <code>Compress</code> output does not say which method made it; keep the method number next to the data.</li>
<li><strong>A <code>str</code> stops at the first zero byte.</strong> Keep binary data in a <code>ByteBuf</code>; <code>BufToStrUnsafe</code> is for bytes that are really text.</li>
<li><strong>Buffers are not freed for you.</strong> Call <code>BufFree</code> on buffers you are done with, especially in loops and servers.</li>
</ul>

<p>The guide below covers the jobs this package is used for day to day: gzipping and bzip2-ing text, laying out your own binary records in a <code>ByteBuf</code>, checking data with CRC-32, and choosing a compression method. Each section has a complete program with its output.</p>

<h2 id="guide-gzip">Gzip text for storage or transport</h2>
<p><code>GzipCompressStr</code> turns a string into a gzip stream that <code>gzip -d</code>, browsers and every other gzip reader understand, and <code>GzipDecompressBuf</code> turns it back. Gzip output is binary, so when it has to travel inside JSON, a URL or an environment variable, wrap it in Base64 with <code>BufToBase64</code>. On the receiving side <code>encoding.Base64DecodeBytes</code> writes the bytes into a buffer you have made big enough; set the buffer's <code>len</code> to the count it returns. It throws when the text is not Base64 or does not fit, so call it inside <code>try:</code>.</p>
{{example.compress-guide-gzip}}
<p>A log with the same line twenty times shrinks to a tenth of its size. Base64 costs a third back (64 characters for 48 bytes), which is still far smaller than the original. <code>BufToStrUnsafe</code> copies the bytes into a string, so use it only for data that is really text: a <code>str</code> ends at the first zero byte.</p>

<h2 id="guide-bzip2">Bzip2 for smaller files</h2>
<p><code>Bzip2CompressStr</code>, <code>Bzip2Compress</code> and <code>Bzip2CompressBuf</code> write a standard bzip2 stream (what <code>bzip2</code> and Python's <code>bz2</code> read), and <code>Bzip2CompressLevel</code> takes a level from 1 to 9: the block size in units of 100000 bytes, 9 by default. <code>Bzip2DecompressBuf</code> reads one or more streams, including old ones with randomised blocks, and checks all CRCs. The program packs the same text both ways and then shows the two safety nets: a cap on the unpacked size, and a flipped bit.</p>
{{example.compress-guide-bzip2}}
<p>On text with many repeated words bzip2 beats gzip by a good margin, while on short or already compressed data the two are close. Bzip2 needs more time and memory per megabyte than gzip, so it suits files that are written once and read rarely. To work with <code>.bz2</code> files on disk, use <code>Bzip2CompressFile</code> and <code>Bzip2DecompressFile</code> from <a href="/std/archive/">archive</a>.</p>

<h2 id="guide-record">Your own binary format with ByteBuf</h2>
<p>A <code>ByteBuf</code> grows as you push into it, and a <code>ByteReader</code> walks over the bytes from the start. That is all you need for a small file format: a few magic bytes so that a wrong file is rejected, a count, and then each record as a length and its bytes. <code>BufPushU32</code> and <code>RdU32</code> write and read a 32 bit number in big-endian order; for little-endian or 64 bit numbers use <a href="/std/encoding/binary/">encoding.binary</a>, which works on the same buffers.</p>
{{example.compress-guide-record}}
<p>The reader never reads past the end. When a read asks for more bytes than are left, the reader sets <code>bad</code>, returns zeros or an empty buffer, and stays bad, so it is enough to check <code>r.bad</code> once after a group of reads. The last call reads a copy cut to 20 bytes: the first name still fits, the second does not.</p>

<h2 id="guide-checksum">Checking data with CRC-32</h2>
<p>A checksum tells you whether bytes arrived unchanged. <code>CRC32Str</code> and <code>CRC32Buf</code> compute the same CRC-32 that zip, gzip and PNG use; <code>Adler32Str</code> and <code>Adler32Buf</code> are faster and weaker, the one zlib uses. The program seals a message by appending its CRC, then shows that changing a single byte is caught.</p>
{{example.compress-guide-checksum}}
<p><code>GzipDecompress</code> and <code>GzipDecompressBuf</code> check the header and the optional header CRC, inflate the data, and then compare the CRC-32 and the length in the last eight bytes of the stream. A flipped bit there, or a corruption that still decodes, is reported by <code>ok</code> being false, so you never see damaged data as a successful read.</p>

<h2 id="guide-choose">Choosing a method</h2>
<p><code>Compress</code>, <code>CompressBuf</code> and <code>CompressStr</code> take a method number, and <code>CompressBest</code> tries each one and keeps the smallest result. The best method depends on the shape of the data, as these output sizes show:</p>
{{example.compress-guide-choose}}
<p>RLE wins on long runs of one byte and makes ordinary text bigger. LZ77 does well on repeated phrases. <code>MethodDeflate</code> is left out of the list because it is this package's own container, which stores its Huffman tables in full and so starts at almost 300 bytes; gzip uses real DEFLATE with compact tables and is the better choice whenever the data leaves your program. Two rules follow: the output of <code>Compress</code> does not say which method made it, so store the method number next to the data (the value <code>CompressBest</code> wrote into its last argument), and very short inputs are best stored as they are (method 0, which <code>CompressBest</code> reports as none for the short line above).</p>

<h2 id="guide-xz">Read .xz and .lzma files</h2>
<p><code>XzDecompress</code> opens the <code>.xz</code> files that <code>xz</code>, <code>tar -J</code> and <code>7z a -txz</code> write, and <code>LzmaDecompress</code> the older <code>.lzma</code> format. An xz file is checked as it is read: the headers, the index and the CRC-32, CRC-64 or SHA-256 of every block, and any mismatch gives <code>ok</code> false with an empty result. The decoders hold the whole result in memory, so on data you did not make yourself call <code>XzDecompressMax</code> or <code>LzmaDecompressMax</code> with the biggest size you accept; a few hundred bytes of LZMA can describe gigabytes.</p>
{{example.compress-guide-xz}}
<h3 id="guide-xz-write">Write .xz and .lzma files</h3>
<p><code>XzCompressStr</code>, <code>XzCompress</code> and <code>XzCompressBuf</code> write a standard <code>.xz</code> file that <code>xz</code>, <code>unxz</code>, <code>tar -J</code> and 7-Zip open: one LZMA2 block, a CRC-64 check, and an index. <code>XzCompressLevel</code> takes a level from 0 (fastest, 256 KiB window) to 9 (64 MiB window, longest search), and <code>XzCompressCheck</code> also picks the check: <code>XzCheckNone</code>, <code>XzCheckCrc32</code>, <code>XzCheckCrc64</code> or <code>XzCheckSha256</code>. Data that does not shrink is stored in uncompressed chunks, so the result is only the container overhead over the input. <code>LzmaCompressStr</code>, <code>LzmaCompress</code>, <code>LzmaCompressBuf</code> and <code>LzmaCompressLevel</code> write the older <code>.lzma</code> format, which has no check; <code>archive.XzCompressFile</code> and <code>archive.LzmaCompressFile</code> do it for a file.</p>
{{example.compress-guide-xz-write}}
<p>Inside 7z archives and xz blocks the compressed data comes without a container. <code>LzmaRawDecompress</code> and <code>Lzma2RawDecompress</code> read that form when you know the properties and the unpacked size, and <code>BcjDecode</code> and <code>DeltaDecode</code> undo the filters that sit in front of it. Dictionaries above 1 GiB (<code>LzmaMaxDictSize</code>) are refused.</p>

<h2 id="guide-zstd">Read and write .zst files</h2>
<p><code>ZstdDecompress</code> opens the <code>.zst</code> files that <code>zstd</code>, <code>tar --zstd</code> and <code>7z a -tzstd</code> write: one frame or several in a row, any compression level, with or without a checksum, and frames written with long-distance matching or many threads. The decoder checks as it reads. A bad table, an offset that points before the data, a size that does not add up or a wrong XXH64 checksum gives <code>ok</code> false and an empty result; <code>ZstdDecompressEx</code> also says which of these it was, through the <code>ZstdErr...</code> codes. The whole result is kept in memory, so on data you did not make yourself call <code>ZstdDecompressMax</code> with the biggest size you accept.</p>
{{example.compress-guide-zstd}}
<p><code>ZstdCompressLevel</code> writes a standard frame at a level from 1 to 22 (0 stores the data as it is), with the content size and a checksum in the header. The writer is deliberately simple: it finds repeats with a greedy or lazy search over a hash chain and codes them with the predefined tables, so the result is usually a quarter to a half larger than the <code>zstd</code> tool's at the same level. Every reader accepts it. Dictionaries are supported for reading only (<code>ZstdDecompressDict</code>); the writer does not use one.</p>
<h2 id="guide-stream">Unpack a big file without holding it in memory</h2>
<p>Everything above works on a whole buffer. For a file that may not fit in memory, <code>NewFileBitReader</code> reads a part of a file in pieces of 64 KiB and <code>RawInflateToSink</code> writes the unpacked data into a <code>FileSink</code>, which counts the bytes, keeps a CRC-32 and stops at a cap you choose. The archive package uses exactly these calls to unpack zip, gzip and RAR entries to disk. <code>FileSeek</code>, <code>FileSize</code> and <code>FileReadAt</code> use 64 bit offsets, and <code>CRC32Update</code> lets you checksum data that arrives in parts.</p>
{{example.compress-guide-stream}}
<p>A sink that reaches its cap sets <code>over</code> and refuses the rest, so a small hostile file cannot fill the disk. Check the result of <code>SinkClose</code> too: a full disk shows up there as a failed write.</p>
