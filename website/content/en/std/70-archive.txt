pkg.intro <<
<p>An archive gathers several files into one. <strong>Zip</strong> compresses each file on its own; <strong>tar</strong> only puts the files one after another and is usually gzipped afterwards (<code>.tar.gz</code>).</p>
<p>The functions work both in memory and on files. They take the archive data as an address and a length, such as <code>b.data</code> and <code>b.len</code> of a byte buffer.</p>

<p>Multi-volume sets work for RAR through <code>RarOpenVolumes</code>, for 7z through <code>SevenZipOpenVolumes</code> and for zip through <code>ZipOpenFile</code> (pass the <code>.zip</code>, the <code>.z01</code> or the <code>.zip.001</code> piece; the other pieces are found next to it) and written with <code>ZipCreateFileSplit</code>. Passwords work for RAR through <code>RarOpen</code> and for 7z through <code>SevenZipOpen</code>. Zip entries with a password are read through <code>ZipOpenFile</code> and <code>ZipFileSetPassword</code> (ZipCrypto and WinZip AES) and written through <code>ZipFileInput.password</code>.</p>

<p>The compression itself comes from <a href="/std/compress/">compress</a>; use that package directly to gzip a single file or stream. For reading and writing the files on disk around an archive, see <a href="/std/fs/">fs</a>.</p>
<h3 id="limits">Limits to know about</h3>
<ul>
<li><strong>Zip:</strong> zip64 is read and written (64-bit sizes and offsets, the zip64 end record, more than 65535 entries), but the package counts bytes in an <code>int</code>, so in practice an archive and each entry must stay under 2 GB. A bigger entry is listed with its true size, and extracting it reports <code>ZIP_TOO_BIG</code>; <code>ZipCreate</code> returns an empty buffer (and <code>ZipCreateFile</code> false) for input it cannot hold: a negative length, a null address with a length, a name over 65535 bytes, or about 1.9 GB in total. <code>ZipCreate</code> switches to zip64 on its own only for 65535 entries or more; <code>ZipCreate64</code> always writes the zip64 form, which <code>unzip</code> and <code>7z</code> read. Methods 0 (stored), 8 (DEFLATE), 12 (bzip2), 14 (LZMA) and 93 (zstd) are read and written, and 9 (Deflate64, what 7-Zip writes with <code>-mm=Deflate64</code>) is read; any other method is reported as <code>ZIP_UNSUPPORTED</code>, and encrypted entries are written as ZipCrypto or WinZip AES-128, AES-192 or AES-256 (<code>ZipFileInput.password</code> and <code>encryption</code>); the in-memory readers refuse them, use <code>ZipOpenFile</code>. <code>ZipExtractByName</code> and <code>ZipExtractByNameMax</code> do not check the CRC-32; <code>ZipExtractVerified</code>, <code>ZipVerify</code> and <code>ZipExtractAll</code> do, and <code>ZipExtractAll</code> skips an entry that fails the check and returns false.</li>
<li><strong>Zip names and dates:</strong> a name with non-ASCII bytes is written with the UTF-8 flag (general purpose bit 11), so Windows Explorer, <code>unzip</code> and 7-Zip show Persian names correctly. When reading, a name is taken as it is (UTF-8) unless the Info-ZIP "Unicode path" field is present, which then wins. Names from other code pages are not converted. Dates are DOS dates: two second steps, between 1980 and 2107, with no time zone, read here as UTC. Set <code>ZipFileInput.mtime</code> (seconds since 1970) to date an entry; 0, or any time before 1980, writes 1 January 1980. The extra timestamp field is not written. <code>ZipExtractAll</code> sets the modification time of the files it writes from that date, except on Windows and 32 bit systems, and does not touch folders.</li>
<li><strong>Tar:</strong> names of any length round-trip: a long name is stored in the ustar prefix field when it splits at a slash, otherwise in a PAX <code>path</code> record, and reading understands ustar prefixes, PAX (<code>x</code> and <code>g</code>) and GNU long names and links. Symbolic and hard links are real entries (<code>Entry.kind</code> and <code>Entry.link</code>); devices, pipes and other special entries are listed with <code>kind</code> 4 and skipped by <code>TarExtractAll</code>. Times and modes you set are written (a time past the ustar range goes into a PAX record), and extraction applies the mode and the modification time of files and folders, but not their owner. On Windows symbolic links are not created (the call returns false), hard links become copies and times are not set; times are not set on 32 bit systems either. Entries that are not given a time get 0, and the mode you leave at 0 becomes 644 for files, 755 for folders and 777 for symbolic links.</li>
<li><strong>Tar extraction:</strong> <code>TarExtractAll</code> skips, and returns false for, a name that is absolute or climbs out with <code>..</code>, a name that passes through a symbolic link it created, a symbolic link whose target is absolute or leaves the target folder (a <code>..</code> after a name is refused too), and a hard link to a name outside the folder. Set-user-id and similar mode bits are never applied.</li>
<li><strong>RAR:</strong> RAR 5 archives are read completely: every compression level, solid archives and the built-in filters, with each entry's CRC-32 checked. Older archives (RAR 1.5 to 4.x) are read the same way, including PPMd text compression and the standard filters. Password-protected archives open with <code>RarOpen</code> and a password, including ones whose file names are encrypted; without it they report <code>RAR_ENCRYPTED</code>, and a wrong password reports <code>RAR_BAD_PASSWORD</code>. Multi-volume archives open from the list of volumes (<code>RarOpenVolumes</code>, or <code>RarReadVolumes</code> to load a set from disk); a set with a missing volume reports <code>RAR_MULTIVOLUME</code> for the files that cross it. A file that is both encrypted and split across volumes is read too (checked against the reference unrar on RAR 1.5, 2.0, 3 and 5 sets). The old RAR 1.5 and 2.x passwords work as well, tested with a real WinRAR 2.02 file. The RAR 7 format version 1 (dictionaries over 4 GB, fractional sizes) is read; only a match distance beyond 4 GB has never been run. The in-memory functions need the archive and each entry under 2 GB (a bigger entry reports <code>RAR_TOO_BIG</code>); for bigger RAR 5 files use <code>RarFileOpen</code>, which reads from disk and unpacks in pieces. Extraction restores the Unix permissions and the modification time (on 64-bit systems other than Windows), recreates symbolic links whose target stays inside the destination, and writes hard links and file copies as plain copies; a link that points outside is skipped and reported as <code>RAR_UNSAFE_PATH</code>. New archives are RAR 5 with the files stored, because only WinRAR itself can compress to RAR; any RAR tool opens them.</li>
<li><strong>7z:</strong> read, and written with stored data only. LZMA, LZMA2, PPMd, BZip2, Deflate, Deflate64, copy, BCJ2, the branch filters (x86, ARM, ARM64, RISC-V and others), byte swap and delta are supported, with AES-256 passwords (headers too); Multi-volume sets (<code>.7z.001</code>) and self-extracting archives (an executable stub before the archive) are read. Unix modes, times and symbolic links are restored on extraction, and a link that would point outside the target folder is refused. The calls that take a pointer and a length hold everything unpacked in memory, so a solid block is capped at about 1 GiB and the dictionary of an LZMA stream may not pass 1 GiB; <code>SevenZipOpenFile</code> has no such limit (see below). Names are UTF-8; the time is the last change.</li>
</ul>

<p>The guide below shows the usual jobs: zipping a set of files, making and reading a <code>.tar.gz</code>, telling formats apart by their first bytes, and extracting without letting an archive write outside the target folder.</p>

<h2 id="guide-zip">Zip a set of files</h2>
<p>Each file you put into a zip is a <code>ZipFileInput</code>: its path inside the archive, the address and length of its bytes, and the method: 8 for DEFLATE, 0 to store it as it is, or 12, 14 and 93 for bzip2, LZMA and zstd (the <code>ZipMethod...</code> constants). <code>MakeZipFileInputLevel</code> also sets a level for those compressors. Every unzip reads bzip2 entries; LZMA and zstd entries are read by 7-Zip and by Python's <code>zipfile</code> (zstd from Python 3.14), but not by older tools such as Info-ZIP <code>unzip</code>, so use them only when you know the reader. A name that ends with <code>/</code> is a folder. <code>ZipCreateFile</code> writes the archive to disk and returns false when it cannot; bzip2, LZMA and zstd entries are streamed through the encoders in std/compress, so an entry of any size needs only the encoder window in memory (about 1 MiB for zstd at the default level, a few MiB for LZMA, one block for bzip2); <code>ZipCreate</code> keeps it in memory, for example to send it as an HTTP response.</p>
{{example.archive-guide-bundle}}
<p>Text shrinks well. The logo is already compressed, so it uses method 0: running DEFLATE on it again would only cost time and could even make it bigger. The same rule holds for JPEG, PNG, MP4 and other zips.</p>

<h2 id="guide-targz">Make and read a .tar.gz</h2>
<p>Tar does not compress. It puts each file after a 512 byte header and pads its contents to a multiple of 512 bytes, so three small files already take 3.5 KB. The usual answer is to gzip the whole tar, and all that padding then nearly disappears. In memory that is <code>TarCreate</code> followed by <code>compress.GzipCompressBuf</code>; for a tar that is already on disk, <code>GzipCompressFile</code> and <code>GzipDecompressFile</code> do it file to file. <code>TarGzCreate</code> and <code>TarGzCreateFile</code> do both steps at once.</p>
{{example.archive-guide-targz}}
<p>Reading goes the other way: <code>TarGzList</code>, <code>TarGzExtractByName</code> and <code>TarGzExtractAll</code> gunzip and read in one call, and set <code>ok</code> to false when the data is not a valid gzip. They refuse to inflate past 1 GiB; give the <code>Max</code> forms a smaller limit for input you do not trust. Directory entries in a tar have size 0 and <code>is_dir</code> set.</p>

<p>Zstandard works the same way: <code>TarZstdCreate</code> builds the tar and compresses it, and <code>TarZstdList</code>, <code>TarZstdExtractByName</code> and <code>TarZstdExtractAll</code> decompress and read in one call, with <code>Max</code> forms to cap the unpacked size. A <code>.tar.zst</code> made with <code>tar --zstd</code> reads the same way. For a single file there is <code>ZstdCompressFile</code> and <code>ZstdDecompressFile</code>.</p>
<h2 id="guide-sevenzip">Read a 7z archive</h2>
<p>7z archives are read, and can be made with stored data (no compression). <code>SevenZipList</code> and <code>SevenZipListStatus</code> list the entries, <code>SevenZipExtractByName</code> unpacks one, and <code>SevenZipExtractAll</code> writes everything under a folder. The LZMA, LZMA2, PPMd, BZip2, Deflate and Deflate64 methods are understood, with BCJ2, the branch filters (x86, ARM, ARM64, RISC-V, PowerPC, SPARC, IA-64), byte swap and delta in front of them, solid blocks, empty files and folders, encrypted data and encrypted headers (AES-256). The signature header, the header, every solid block and every file are checked against their CRC-32. Anti items, which mean "delete this name" in an update archive, are left out.</p>
{{example.archive-guide-sevenzip}}
<p>A solid block is one compressed stream holding several files, so reading one file out of it unpacks the whole block; to get many files out of one archive use <code>SevenZipExtractAll</code>, which unpacks each block once. Every call returns a <code>SEVENZIP_...</code> status instead of guessing: a wrong password is <code>SEVENZIP_BAD_PASSWORD</code>, a missing password <code>SEVENZIP_ENCRYPTED</code>, a damaged file <code>SEVENZIP_BAD_CRC</code> or <code>SEVENZIP_CORRUPT</code>. Open an encrypted archive with <code>SevenZipOpen</code> and its password, then use <code>SevenZipEntries</code>, <code>SevenZipRead</code> and <code>SevenZipReadAll</code>:</p>

<h2 id="guide-extract">Extract safely</h2>
<p><code>ZipExtractAll</code> and <code>TarExtractAll</code> create the folders they need under the target directory. An archive from someone else can hold names like <code>../escape.txt</code> or <code>/etc/passwd</code> that would land outside it; both functions skip such entries, write the rest, and return false so you know something was left out. <code>ZipExtractByName</code> and <code>TarExtractByName</code> set <code>ok</code> to false when the name is not in the archive.</p>
{{example.archive-guide-extract}}
<p>A false result from an extract call is therefore not always a disk error: check the entry names with <code>ZipList</code> or <code>TarList</code> when you need to tell the two apart.</p>

<h2 id="guide-gzip">Gzip a single file (.gz)</h2>
<p>A <code>.gz</code> holds one file, not a folder. <code>GzipCompressFile</code> and <code>GzipDecompressFile</code> go from a path to a path and return false when they cannot read, write or decode; in memory, <code>compress.GzipCompressBuf</code> and <code>compress.GzipDecompressBuf</code> do the same on a buffer. Decompressing checks the trailer, so a damaged or cut file is refused instead of giving back wrong bytes. For data from someone else use <code>compress.GzipDecompressMax</code>, which stops at a size you choose, so a tiny file cannot expand into gigabytes.</p>
{{example.archive-guide-gzip}}
<p>To compress several files, put them in a tar first (the <code>.tar.gz</code> section above). To open a <code>.tar.gz</code> you do the same two steps backwards.</p>

<h2 id="guide-check">Check an archive</h2>
<p>"Check" means two different things. To see what is inside without unpacking, list it: <code>ZipList</code>, <code>TarList</code> and <code>RarList</code> (or <code>RarEntries</code>) give every name, size, folder flag and, for zip and RAR, the stored CRC-32; free the list with <code>FreeEntries</code>. To know the data is intact, you need a checksum, and formats differ:</p>
<ul>
<li><strong>gzip and RAR</strong> verify themselves. A gzip call returns <code>ok = false</code>; a RAR call sets the status to <code>RAR_BAD_CRC</code>, or <code>RAR_BAD_PASSWORD</code> when a password was wrong.</li>
<li><strong>zip</strong> stores a CRC-32 for each entry. <code>ZipExtractVerified</code> compares it with the data and sets <code>status</code> to <code>ZIP_OK</code>, <code>ZIP_BAD_CRC</code> and so on; <code>ZipVerify</code> checks every entry and returns how many failed; <code>ZipBadEntries</code> lists them. <code>ZipExtractByName</code> stays unchecked, for speed and for old code: compare <code>compress.CRC32Buf(data)</code> with <code>Entry.crc32</code> yourself, as the example below does.</li>
<li><strong>tar</strong> has no checksum for the contents. All you can check is that the listing is sane (names, sizes); for integrity gzip the tar and rely on the gzip trailer, or keep a hash next to the file.</li>
</ul>
{{example.archive-guide-check}}
<p>In the example one byte of the first zip entry was changed. Extraction still reports success for it, but its checksum no longer matches, while the second entry is fine. The RAR entry with the same damage is refused by the extractor itself.</p>
<p>The verified calls do that comparison for you. <code>ZipVerify</code> sets <code>checked</code> to the number of files it inflated and returns how many were bad, or -1 when the data is not a zip; <code>ZipStatusText</code> turns a status into a sentence.</p>
{{example.archive-guide-zipverify}}
<p>The next example covers dates and zip64: <code>ZipFileInput.mtime</code> sets an entry's date, <code>Entry.mtime</code> reads it back, and <code>ZipCreate64</code> writes the zip64 form.</p>

<h2 id="guide-rar">Read and write a RAR</h2>
<p>Reading goes through <code>RarList</code> and <code>RarExtract</code>, the same way as zip. The sample below is a small solid RAR 5 made by WinRAR: the second file is packed against the first, so <code>RarExtract</code> unpacks both to reach it. Every entry is checked against its CRC-32, and the <code>status</code> says what went wrong instead of returning silent garbage.</p>
{{example.archive-guide-rar}}
<p>Making a RAR is simpler: build <code>RarFileInput</code> values and call <code>RarCreate</code> or <code>RarCreateFile</code>. The result is a valid RAR 5 archive with the files stored uncompressed. If you need real compression, use zip, or <code>.tar.gz</code> as shown above. </p>
<h2 id="guide-rar-password">Open a password-protected RAR</h2>
<p>A <code>RarArchive</code> remembers the data and the password, so the list, a single read and a full extraction share them. With the wrong password the archive does not open (when the names are encrypted) or each read fails with <code>RAR_BAD_PASSWORD</code>; with none at all you get <code>RAR_ENCRYPTED</code>. RAR 5 checks the password up front. RAR 3 and 4 have no check value, so for them a wrong password shows up as a failed checksum, and it is reported the same way.</p>
{{example.archive-guide-rar-password}}

<h2 id="guide-rar-volumes">Read a multi-volume RAR</h2>
<p>A big archive is often cut into volumes: <code>name.part01.rar</code>, <code>name.part02.rar</code>, and so on, or the older <code>name.rar</code>, <code>name.r00</code>, <code>name.r01</code>. <code>RarReadVolumes</code> takes the first file name, finds the rest by that naming and loads them; <code>RarOpenVolumes</code> turns the list into a <code>RarArchive</code>, and the usual <code>RarEntries</code> and <code>RarRead</code> work across the cuts. Close the archive with <code>RarClose</code> and free the volumes with <code>RarFreeVolumes</code>.</p>
{{example.archive-guide-rar-volumes}}

<h2 id="guide-sevenzip-volumes">Read a split 7z archive</h2>
<p>7z cuts a big archive into plain pieces named <code>name.7z.001</code>, <code>name.7z.002</code> and so on. <code>SevenZipReadVolumes</code> takes the first file name and loads the rest by counting up; <code>SevenZipOpenVolumes</code> joins the pieces and opens them as one archive. A self-extracting 7z (an executable with the archive appended) opens with <code>SevenZipOpen</code> directly: the signature is searched for in the first 8 MiB.</p>
{{example.archive-guide-sevenzip-volumes}}

<h2 id="guide-open">One door for every format</h2>
<p><code>Open</code> reads the first bytes, finds the format and returns an <code>Archive</code>; <code>List</code>, <code>Read</code>, <code>Extract</code> and <code>ExtractAll</code> then work the same for every format and report one set of <code>ARCHIVE_</code> codes. <code>OpenFile</code>, <code>ListFile</code> and <code>ExtractFile</code> do the same from a path. Gzip, bzip2 and xz files are unpacked on opening, and a tar inside is recognized, so a <code>.tar.gz</code>, <code>.tar.bz2</code> and <code>.tar.xz</code> open like any other archive. The per-format functions below keep working unchanged.</p>

<p><code>ExtractAll</code> is the safe way to unpack data you do not trust. Before it writes anything it checks every entry against <code>Limits</code> (entry count, size of one entry, size of all, and the ratio of unpacked size to archive size, which catches compression bombs) and refuses names that are absolute or climb out with <code>..</code>, links that leave the folder, files written through a link, and device entries. If a check fails nothing is written and <code>status</code> says why. The limits use the sizes the archive declares; each format still verifies the real sizes while unpacking. Multi-volume RAR and 7z sets, and large-file streaming, stay with the per-format functions.</p>
<p>The same calls work from a path. <code>ListFile</code> and <code>ExtractFile</code> open the file, do the job and close it; <code>OpenFile</code> gives you an <code>Archive</code> to reuse, and <code>SetLimits</code> tightens the <code>Limits</code> of one archive. Every call reports a status code, and <code>ArchiveStatusText</code> turns it into words. The example makes a <code>.tar.gz</code>, lists and extracts it, hits a limit and a missing file on purpose, and prints all fifteen codes.</p>

<h2 id="guide-sevenzip-create">Make a 7z archive</h2>
<p>Build <code>SevenZipFileInput</code> values and call <code>SevenZipCreate</code> or <code>SevenZipCreateFile</code>. Files, folders, empty files and symbolic links (set <code>link</code>) are written, with modes and times when you give them. <code>SevenZipCreate</code> stores the data; <code>SevenZipCreateLevel</code> and <code>SevenZipCreateFileLevel</code> compress each file with LZMA at levels 1 to 9. The result opens in 7-Zip and in <code>SevenZipExtractAll</code>.</p>

<h2 id="guide-zipfile">Big zip files on disk</h2>
<p>The functions that take a pointer and a length hold the whole archive in memory, which stops at 2 GiB. For a zip of any size use <code>ZipOpenFile</code>: it reads only the end of the file and the list of entries, and <code>ZipFileExtractTo</code> and <code>ZipFileExtractAll</code> unpack straight to disk in 64 KiB pieces, checking the CRC-32 and the size as they go. Sizes and offsets are 64 bit, zip64 included, so an entry of several gigabytes works and memory use stays small. The only limit is the one you pass: <code>cap</code> is a number of bytes (0 for none), and an entry over it returns <code>ZIP_TOO_BIG</code> before anything is written.</p>
{{example.archive-guide-zipfile}}

<h2 id="guide-sevenzipfile">Big 7z files on disk</h2>
<p><code>SevenZipOpenFile</code> opens a 7z on disk and keeps only its header in memory. <code>SevenZipFileExtractTo</code> and <code>SevenZipFileExtractAll</code> unpack straight to disk: LZMA and LZMA2 data goes through a window as big as the dictionary and out in 64 KiB pieces, so an entry of several gigabytes needs only a few megabytes of memory. Every method streams the same way: PPMd needs only the model memory its properties ask for, bzip2 holds one block, the branch filters (BCJ, ARM, ARM64, RISC-V and the rest), delta, byte swap and BCJ2 are stages that pass each piece on, and AES-256 decrypts in pieces in front of the next coder, so AES then LZMA2 then BCJ reads straight from the file with no temporary file. Encrypted headers go through the same path. BCJ2 reads its range coder stream from the file; its call and jump streams are read from the file when stored and decoded into small buffers (at most <code>memcap</code>) when compressed. A solid block is read once for all of its files. <code>cap</code> limits the bytes of one entry and <code>memcap</code> the memory the decoder may use; both take 0 for no limit.</p>
{{example.archive-guide-sevenzipfile}}

<h2 id="guide-tarfile">Big tar files on disk</h2>
<p><code>TarFileOpen</code> reads a tar from disk one entry at a time: <code>TarFileNext</code> fills an <code>Entry</code> (sizes and offsets are 64 bit, so a 5 GB entry is just an entry), <code>TarFileExtractTo</code> copies its data to a file in 64 KiB pieces, and <code>TarFileExtractAll</code> unpacks the whole archive with the same safety rules as <code>TarExtractAll</code>. Nothing but one entry's header is ever in memory. <code>cap</code> is the only size limit and it is yours (0 for none): <code>TAR_TOO_BIG</code> means an entry is over it. <code>TarGzFileExtractAll</code> and <code>GzipDecompressFileCap</code> do the same for gzip, which is read as a stream. A compressed tar needs no temporary file: <code>TarGzFileExtractAll</code>, <code>TarBz2FileExtractAll</code>, <code>TarXzFileExtractAll</code> and <code>TarZstdFileExtractAll</code> (or <code>TarCompressedFileExtractAll</code>) feed the decoder's output into the tar reader piece by piece, and <code>TarCompressedFileEntries</code> lists one the same way.</p>
{{example.archive-guide-tarfile}}

<h2 id="guide-rarfile">Big RAR files on disk</h2>
<p><code>RarFileOpen</code> reads a RAR 5 file's headers only (offsets and sizes are 64 bit); <code>RarFileExtractTo</code> and <code>RarFileExtractAll</code> then unpack to disk, writing the result in pieces and checking the CRC-32 as they go. Compressed entries, solid archives and the built-in filters work. What is held in memory is the packed data of one entry and the decoder window, so the unpacked size can be anything: an entry of several gigabytes is unpacked from a file of a few megabytes in constant memory. The size limits are yours: <code>cap</code> for the unpacked bytes and <code>memcap</code> for that memory, and <code>RAR_TOO_BIG</code> means one of them was passed, and <code>RAR_WINDOW_TOO_BIG</code> that the data needs a window bigger than <code>memcap</code> or 1 GiB. Passwords and volumes work from disk too: <code>RarFileOpenWith</code> opens archives with encrypted files or file names, and <code>RarFileOpenVolumes</code> a set of volumes, decrypting and joining pieces as it unpacks. <code>RarFileExtractAll</code> restores permissions and times and creates safe symbolic links. Older RAR formats (1.5 to 4.x) work the same way, passwords, encrypted file names and volumes included: the packed data is read from the file in pieces and the unpacked data goes to disk in pieces (the VM filters are applied on the way), so an entry or a volume over 4 GiB works with a few megabytes of memory (sizes and offsets are 64 bit, including the high size fields of the headers). Only entries encrypted with the very old RAR 1.5 or 2.0 ciphers still need their packed data in memory, up to 256 MiB.</p>
