pkg.intro <<
<p>UDP sends separate packets, with no connection and no guarantee that they arrive or arrive in order; in exchange it is fast and simple. It is what DNS, games, live streaming and discovering devices on a local network use. Up to about 1500 bytes per packet is safe.</p>
<p>A UDP socket is not tied to one peer. The same socket can send to many addresses and receive from anyone, and every <code>Packet</code> carries <code>from_host</code> and <code>from_port</code> so you know where to answer. Each <code>Send</code> is one packet and each <code>Receive</code> returns one whole packet, so unlike TCP there is no need to find where a message ends.</p>
<p>Choose UDP when a late answer is worth nothing (game state, sensor readings, voice) or when one small question gets one small answer. When every byte must arrive, in order, use <a href="/std/net/tcp/">net/tcp</a>. To look up names, <a href="/std/net/dns/">net/dns</a> already speaks the DNS protocol over UDP for you.</p>
<h3 id="pitfalls">What trips people up</h3>
<ul>
<li><strong>A timeout looks like an empty packet.</strong> <code>Receive</code> returns empty <code>data</code> both when the timeout passed and when a peer really sent zero bytes, so never use empty packets as messages.</li>
<li><strong>Too small a buffer cuts the packet.</strong> The rest of a packet larger than <code>max</code> is thrown away, not kept for the next call. Pass the largest size your protocol allows (0 means 65536 for <code>Receive</code>).</li>
<li><strong>Text stops at a zero byte.</strong> <code>Receive</code> gives a <code>str</code>; binary packets need <code>ReceiveBytes</code>.</li>
<li><strong>IPv4 only.</strong> Sockets, addresses and multicast groups are all IPv4.</li>
<li><strong>Nothing is guaranteed.</strong> Packets can be lost, repeated or reordered; the retry guide shows the usual answer.</li>
</ul>

<h2 id="guide-request-reply">Answering a request</h2>
<p>A UDP server binds a port and answers each packet to the address it came from. The client uses <code>Open</code>, which picks a free port for it, sends a packet and waits for the reply on the same socket. Set a timeout on both sides, because a lost packet would otherwise leave <code>Receive</code> waiting forever.</p>
{{example.net-udp-guide-ping}}
<p>Binding to <code>127.0.0.1</code> with <code>BindOn</code> keeps the server private to this machine. <code>Bind</code> listens on every address, which is what a service on the network needs.</p>

<h2 id="guide-retry">Timeouts and retries</h2>
<p>UDP never tells you that a packet was lost, so a client that expects an answer has to wait a short time and send again. With <code>SetTimeout</code>, <code>Receive</code> returns a packet with empty <code>data</code> when nothing arrived in time. The server in this example ignores the first two requests, the way a busy network might drop them, and the client tries until it gets an answer or runs out of attempts.</p>
{{example.net-udp-guide-retry}}
<p>Because a request can arrive twice (the first copy was only slow, not lost), a request that changes something should carry an id, so the server can recognise a repeat and answer it without doing the work again. DNS works exactly like this.</p>

<h2 id="guide-binary">Binary packets</h2>
<p>Compact protocols put numbers in bytes instead of text. <code>SendBytes</code> sends a block of memory as one packet and <code>ReceiveBytes</code> fills a buffer and reports the sender through its last two arguments. The packet here has one byte for the kind of message, one for a sensor number and two for a value, high byte first, which is the usual network order.</p>
{{example.net-udp-guide-binary}}
<p>Keep packets below about 1500 bytes. Larger ones are split by the network and lost completely if one part goes missing. Use <code>ReceiveBytes</code> rather than <code>Receive</code> whenever the data may contain a zero byte, since a <code>str</code> ends at the first one.</p>

<h2 id="guide-discovery">Finding devices on the local network</h2>
<p>To find a printer, a game host or another copy of your program on the same network without knowing its address, send to a group instead of to one machine. With <code>JoinMulticast</code> a socket receives what anyone sends to the group address; <code>SetBroadcast</code> instead allows sending to the broadcast address of the whole network, such as <code>255.255.255.255</code>. This example depends on how the network is set up, so it is only compiled here. On most machines it prints <code>heard: printer at 192.168.1.50</code>, because the sender also receives its own multicast packets.</p>
{{example.net-udp-guide-discovery}}
<p>Multicast addresses from <code>239.0.0.0</code> to <code>239.255.255.255</code> are meant for private use inside an organisation. Every program that wants the announcements binds the same port and joins the same group.</p>
>>

doc.Packet.from_port = The port of the sender.
doc.Bind = Makes a socket that listens on the given port on every address; zero means a free port.
doc.BindOn = Like <code>Bind</code>, but on the given address only.
doc.Open = A socket with no particular port, for sending.
doc.Port = The port of the socket.
doc.Ok = True when the socket was created properly.
doc.Close = Closes the socket.
doc.Send = Sends one packet to a host and port and returns the number of bytes.
doc.SendTo = The same as <code>Send</code>.
doc.SendBytes = Sends <code>n</code> bytes from memory in one packet.
doc.Receive = Receives one packet of at most <code>max</code> bytes (65536 when <code>max</code> is 0); a longer packet is cut. When a timeout is set and nothing arrives, the packet comes back with empty <code>data</code>.
doc.ReceiveBytes = Reads one packet into memory, returns its length (negative on timeout or error) and gives back the address and port of the sender.
doc.SetBroadcast = Allows sending to the broadcast address of the network.
doc.SetTimeout = How many milliseconds a receive may wait at most.
doc.JoinMulticast = Joins a multicast group so its packets arrive.
doc.LeaveMulticast = Leaves a multicast group.
