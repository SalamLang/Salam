pkg.intro <<
<p>DNS turns names such as <code>salamlang.ir</code> into IP addresses. <code>Lookup</code> is the simplest way and does what a browser does. The <code>Lookup...</code> functions ask the DNS server for one particular kind of record and are what you want for building network tools or checking the configuration of a domain.</p>
<p>A lookup can fail for ordinary reasons: the name does not exist, the network is down or the server is slow. None of the functions stop the program. <code>Lookup</code> and <code>LookupCNAME</code> return an empty string, and the others return an empty list, so check the result before using it.</p>
<h3 id="resolvers">Two different resolvers</h3>
<ul>
<li><strong><code>Lookup</code></strong> asks the operating system, exactly as connecting by name does: the hosts file, <code>localhost</code>, search domains and the system cache all apply. It returns one IPv4 address.</li>
<li><strong>The <code>Lookup...</code> record functions</strong> send their own queries over UDP to the servers from <code>DefaultServers</code>: the <code>nameserver</code> lines of <code>/etc/resolv.conf</code> on Linux, macOS and BSD. The hosts file is not used. When there is no such file, which is always the case on Windows, they fall back to the public resolvers <code>8.8.8.8</code> and <code>1.1.1.1</code>, so the names you look up leave your network. Each server gets 3 seconds before the next one is tried.</li>
</ul>
<h3 id="pitfalls">What trips people up</h3>
<ul>
<li><strong>Large answers can be incomplete.</strong> An answer that does not fit in one UDP packet comes back with <code>tc</code> set and is not retried over TCP, so very long TXT records or long lists of addresses may be cut short.</li>
<li><strong><code>QueryServer</code> does not check the answer's id</strong> against the question's. On an untrusted network compare <code>Message.id</code> yourself, or prefer a resolver you trust.</li>
<li><strong>Everything is plain text on port 53.</strong> There is no DNSSEC validation and no DNS over TLS or HTTPS.</li>
<li><strong><code>LookupPTR</code> takes IPv4 addresses only.</strong></li>
</ul>

<h2 id="guide-connect">Resolve a name, then connect</h2>
<p><a href="/std/net/tcp/">net/tcp</a> and <a href="/std/net/udp/">net/udp</a> take a host name or an address, but resolving the name yourself first lets you report a clear error before you try to connect. <code>Lookup</code> uses the operating system resolver, so <code>localhost</code> and the names in the hosts file work too, offline.</p>
{{example.net-dns-guide-connect}}
<p>The <code>.invalid</code> top level domain is reserved and never exists, which makes it handy for testing the failure path.</p>

<h2 id="guide-mail">Checking the mail setup of a domain</h2>
<p>Mail for a domain goes to the servers in its MX records, lowest priority number first; the others are fallbacks. The domain's TXT records hold the SPF policy, which says which servers may send mail for it, and the DMARC policy lives in the TXT record of <code>_dmarc.</code> plus the domain. This program needs the internet, so it is only compiled here. Against the real DNS it printed:</p>
{{example.net-dns-guide-mail}}
<pre class="code" dir="ltr"><code>MX 10 alt1.gmail-smtp-in.l.google.com
MX 20 alt2.gmail-smtp-in.l.google.com
MX 40 alt4.gmail-smtp-in.l.google.com
MX 30 alt3.gmail-smtp-in.l.google.com
MX 5 gmail-smtp-in.l.google.com
deliver to: gmail-smtp-in.l.google.com first
SPF: v=spf1 redirect=_spf.google.com
DMARC: v=DMARC1; p=none; sp=quarantine; rua=mailto:mailauth-reports@google.com</code></pre>
<p>The records come back in whatever order the server chose, so sort or pick by <code>priority</code> yourself, as the loop does.</p>

<h2 id="guide-servers">Asking one server directly</h2>
<p><code>QueryServer</code> skips the system resolver and asks the server you name, which is how you compare what different resolvers say or test your own DNS server. It returns the whole <code>Message</code>: <code>rcode</code> 3 means the name does not exist, and an empty message (no <code>qr</code> flag, id 0) means no answer came back within the timeout. Each record has a <code>ttl</code>, the number of seconds a cache may keep it. A name that is an alias answers with a CNAME record before the address, which is why the loop looks at <code>rtype</code>. This one needs the internet too.</p>
{{example.net-dns-guide-servers}}
<p><code>192.0.2.1</code> belongs to a range reserved for documentation, so nothing answers there and the program shows the timeout case. The addresses and TTLs you see will differ from run to run.</p>

<h2 id="guide-toy-server">Speaking the protocol yourself</h2>
<p>DNS is just small binary packets over UDP, and <code>EncodeQuery</code> and <code>Decode</code> build and read them. That is enough for a test double: the program below runs a toy DNS server on <code>127.0.0.1</code> that answers every question with <em>no such name</em> by setting two flag bytes of the query and sending it back. The client sends a real query with <a href="/std/net/udp/">net/udp</a> and decodes the answer, all offline.</p>
{{example.net-dns-guide-toy-server}}
<p>The id of the answer matches the id of the question (7 here). A real client sends a random id and ignores any answer whose id does not match, so a stray or forged packet is not mistaken for the answer.</p>
