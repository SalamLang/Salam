pkg.intro <<
<p>A WebSocket is a connection that starts as one HTTP request and then stays open, and either side sends a message whenever it likes: live chat, notifications, dashboards, games. This package has both ends. The server takes connections with <code>Listen</code> and <code>Accept</code> on its own port, and a client connects with <code>Dial</code>; <code>AcceptWSS</code> and <code>DialWSS</code> do the same over TLS. It runs its own listener and does not plug into the <a href="/std/net/http/">net/http</a> server. For the Socket.IO protocol that many JavaScript apps use (events, acknowledgements, reconnection) use <a href="/std/net/socketio/">net/socketio</a> instead; a plain browser <code>WebSocket</code> talks to this package directly.</p>
<p>Core ideas:</p>
<ul>
<li><code>Receive</code> blocks until a whole message has arrived and returns a <code>Message</code>; check its kind with <code>IsText</code>, <code>IsBinary</code> and <code>IsClose</code>. Pings are answered for you. <code>Poll</code> waits at most a given time.</li>
<li>A <code>Hub</code> groups connections into rooms so one call sends to every member.</li>
<li>One connection is read by one thread. To serve many clients, give each connection its own thread.</li>
</ul>
<p>Things that catch people out:</p>
<ul>
<li><strong>A <code>Hub</code> has no lock.</strong> When several connection threads share it, wrap <code>Register</code>, <code>Unregister</code> and <code>Broadcast</code> in a <a href="/std/sync/">sync</a> mutex.</li>
<li><strong>Keep a copy of the connection for <code>Unregister</code>.</strong> When the other side closes, <code>Receive</code> clears <code>conn.fd</code>, and <code>Unregister</code> matches on that socket number, so unregistering with the closed connection removes nothing. Register a copy taken right after <code>Accept</code> and unregister with the same copy.</li>
<li><strong>Text stops at a zero byte</strong> and is not checked as UTF-8. Send binary data as binary and read it from <code>m.data</code> and <code>m.len</code>; that buffer belongs to the connection and is reused by the next binary message, so copy what you keep.</li>
<li>The server takes any origin and offers no subprotocols or compression; check <code>conn.hdr</code> yourself if you need an <code>Origin</code> rule. A frame larger than 100 MB closes the connection.</li>
</ul>
<p>Each example below runs a server and its clients in the same program, the server in a thread started with <code>spawn</code>, on a free port chosen by <code>Listen(0)</code>. That keeps them runnable offline; in a real program the clients are browsers using the JavaScript <code>WebSocket</code> API, which speaks the same protocol.</p>

<h2 id="guide-json">Typed JSON messages</h2>
<p>A WebSocket carries text or bytes; the structure is up to you. The common choice is one JSON object per message with a <code>type</code> field, and a server loop that reads a message, looks at the type and answers. <code>Receive</code> waits for the next message, <code>IsText</code> tells text from close or binary frames, and <code>json.Str</code> quotes user text safely when you build a reply by hand.</p>
{{example.net-websocket-json}}
<p>Always answer an unknown type with an error message instead of closing; clients built later may send types an older server does not know.</p>

<h2 id="guide-rooms">Rooms with a Hub</h2>
<p>A chat or a live score page sends one message to many connections. A <code>Hub</code> keeps connections by room name: <code>Register</code> adds a connection to a room, <code>Broadcast</code> sends text to every member and returns how many got it, and <code>RoomSize</code> counts the members. A natural room name is the path the client connected to, which the server sees in <code>conn.path</code>.</p>
{{example.net-websocket-rooms}}
<p>In a real server, read each connection in its own thread and call <code>Unregister</code> when it closes, so broadcasts do not go to connections that are gone. The next section shows that server.</p>

<h2 id="guide-chat-server">A chat server with a thread per connection</h2>
<p>Here every <code>member</code> thread accepts one connection, registers it in the <code>lobby</code> room, and then reads that connection until it closes, broadcasting each line to the room. Several threads may call <code>Accept</code> on the same server; each gets a different client. The hub is shared, so every hub call is wrapped in one mutex. The thread registers <code>entry</code>, a copy taken before any <code>Receive</code>, and unregisters with that same copy; with <code>conn</code> itself the room would still count two members at the end.</p>
{{example.net-websocket-chat-server}}
<p>A thread per client is fine for hundreds of connections. Start one <code>member</code> thread per expected client, or have each thread spawn the next one after its <code>Accept</code> returns, so there is always one waiting for the next visitor.</p>

<h2 id="guide-auth">Checking a token during the handshake</h2>
<p>A WebSocket starts as an HTTP request, and its headers are kept in <code>conn.hdr</code>, so the server can check a token before it trusts the connection; read it with <code>http.HeaderValue</code> from <a href="/std/net/http/#guide-raw">net/http</a>. On the client side <code>DialWith</code> adds extra header lines. A connection without a valid token gets a short message and is closed, which the client sees as a close message from <code>Poll</code>.</p>
{{example.net-websocket-auth}}
<p>Browsers cannot set an <code>Authorization</code> header on a WebSocket. For browser clients put a short lived token in the URL, such as <code>/live?token=...</code>, and check <code>conn.path</code> instead.</p>

<h2 id="guide-heartbeat">Waiting without blocking: Poll and ping</h2>
<p>A client that waits a long time for an answer should know the connection is still alive, and proxies close connections that stay silent. <code>Poll(conn, ms)</code> waits at most that many milliseconds and returns a message of kind <code>TIMEOUT</code> when nothing arrived, which is the moment to send a <code>Ping</code>. The loop below waits for a job report, pinging every 100 ms, and gives up after 50 quiet rounds.</p>
{{example.net-websocket-heartbeat}}
<p>The send functions return 0 on success and a negative number when the connection is gone, so check the result of <code>SendText</code> and <code>Ping</code> in long running loops.</p>
