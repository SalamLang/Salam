pkg.intro <<
<p>This package writes the documentation of an HTTP API as an OpenAPI 3.1 document and serves it with a viewer page where people can read each operation and try it. Use it with an API built on <a href="/std/net-http/">net/http</a> and <a href="/std/net-router/">net/router</a>: client generators, API gateways and your own front-end team read the same <code>openapi.json</code>. The viewer is built into the package, so it works offline and loads nothing from a CDN.</p>
<p>How it fits together:</p>
<ul>
<li>A <code>Doc</code> holds the whole document. <code>Route</code> adds an operation (or <code>At</code> picks one that exists), and the calls after it, such as <code>Summary</code>, <code>Query</code> and <code>Returns</code>, describe that operation.</li>
<li>Body and response schemas come from a sample value: pass an empty struct and its fields, under their <code>@json</code> names, become a schema under <code>components</code>.</li>
<li><code>Mount</code> adds the viewer and the spec to your router; <code>Problems</code>, <code>Missing</code> and <code>Undocumented</code> check the document in a test.</li>
</ul>
<p>Things that catch people out:</p>
<ul>
<li><strong><code>Mount</code> copies the spec when you call it, and adds routes to the router.</strong> Describe every route first, then <code>Mount</code>, then <code>http.Use</code>; a description added after <code>Mount</code> never reaches the page.</li>
<li><strong>After an <code>At</code> that finds nothing, the following calls do nothing.</strong> Check what <code>At</code> returns, or use <code>Route</code>, which creates the operation.</li>
<li><strong>The docs are public.</strong> Anyone who can reach the server can read <code>/docs</code>, and the spec is served with <code>Access-Control-Allow-Origin: *</code>. Leave <code>Mount</code> out of a production build if the API is private.</li>
</ul>
<h2 id="guide-api">Document an API next to its routes</h2>
<p>The simplest habit is to describe each route right after you register it, so the two never drift apart. <code>Route</code> starts an operation, and the calls after it fill it in. <code>Returns</code> takes a sample value: pass a struct, or an array of one struct for a list, and the schema appears under <code>components</code>. <code>Mount</code> then serves the spec at <code>/docs/openapi.json</code> and the viewer at <code>/docs</code>.</p>
{{example.net-http-swagger-api}}
<p><code>Mount</code> takes a copy of the spec when you call it, so document every route first and mount last. Path patterns are written the router's way, <code>/books/:id</code>, and appear in OpenAPI's form, <code>/books/{id}</code>.</p>

<h2 id="guide-auth">Security schemes and saving the spec</h2>
<p>Declare each way to sign in once, with <code>BearerAuth</code> for tokens in the <code>Authorization</code> header or <code>ApiKeyAuth</code> for a key in a header, query value or cookie. Then mark each operation that needs it with <code>Secure</code> and the scheme's name. <code>WriteSpec</code> saves the spec to a file, for a client generator or for publishing with the site, and <code>SpecFromFile</code> reads one back.</p>
{{example.net-http-swagger-auth}}

<h2 id="guide-check">Check the documentation in CI</h2>
<p>Documentation goes stale quietly. <code>Problems</code> finds mistakes in the spec itself: a security scheme that was never declared, a path parameter that does not match the path, a status code outside 100 to 599, a body on a GET, or a repeated operation id. <code>Missing</code> compares the spec with the router and lists the routes that have no operation. Print both in a test and fail the build when either is not empty.</p>
{{example.net-http-swagger-check}}
<p>In a real check, return <code>1</code> from <code>main</code> when the count is above zero, so the CI job fails. <code>Undocumented</code> is a softer check: it lists operations that exist but have neither a summary, a description nor a response.</p>

<h2 id="guide-serve">Serve the docs with the API</h2>
<p>For an existing router, <code>Scan</code> adds an empty operation for every route, so nothing is forgotten. <code>At</code> then picks one of them to describe. <code>AcceptsRaw</code> and <code>ReturnsRaw</code> take a content type and a JSON Schema as text, for bodies that are not a struct.</p>
{{example.net-http-swagger-serve}}
<p>Start it with <code>salam run</code> and open <code>http://localhost:8080/docs</code> in a browser: the page lists both operations, and the <em>Try it</em> box under each one sends real requests to the running server. If you do not have a router at all, <code>Serve</code> runs a small server with only the docs, and <code>ServeSpec</code> does the same for a spec written by hand.</p>
>>
