<h2 id="what">salam serve دقیقاً چیست؟</h2>
<p>سرور وب در خود سلام نوشته شده است: بسته‌ی <a href="/std/net/httpd/">net/httpd</a> یک سرور HTTP با انتخاب سایت از سرآیند <code>Host</code>، قاعده‌های مسیر، هدایت، صفحه‌ی خطا، حافظه‌ی نهان، گزارش دسترسی و پشتیبان فست‌سی‌جی‌آی است. فرمان <code dir="ltr">salam serve</code> فقط یک پوسته‌ی نازک دور همین بسته است؛ برای همین هر چیزی که در این درس می‌بینید از داخل یک برنامه‌ی سلام هم قابل استفاده است.</p>
<p>دو حالت دارد که نباید با هم اشتباه شوند:</p>
<div class="table-wrap"><table class="serve-table">
<thead><tr><th>حالت</th><th>فرمان</th><th>برای چه</th></tr></thead>
<tbody>
<tr><td>سرو یک پوشه</td><td><code dir="ltr">salam serve [dir]</code></td><td>پیش‌نمایش سریع یک سایت ثابت، آزمایش خروجی <code dir="ltr">salam web</code> و <code dir="ltr">salam page build</code>، توسعه‌ی محلی</td></tr>
<tr><td>چند سایت از پیکربندی</td><td><code dir="ltr">salam serve --config=web.salam</code></td><td>چند دامنه، چند زیردامنه، مسیرها، هدایت، حافظه‌ی نهان، گزارش دسترسی، PHP و FastCGI</td></tr>
<tr><td>فقط بررسی پیکربندی</td><td><code dir="ltr">salam serve --config=web.salam --test</code></td><td>پیش از استقرار یا در CI؛ بدون باز کردن هیچ درگاهی</td></tr>
</tbody></table></div>
<p>حالت اول عمداً ساده است: نه TLS دارد، نه هدر <code>ETag</code>، نه بازه‌ی بایت و نه قاعده‌ی مسیر. حالت دوم همان چیزی است که برای سایت واقعی می‌خواهید. اگر فقط یک پوشه‌ی ثابت دارید و به هیچ قاعده‌ای نیاز ندارید، حالت اول کافی است؛ ولی همان را هم می‌توانید با یک پیکربندی کوچک به حالت دوم ببرید و حافظه‌ی نهان و <code>ETag</code> و بلاک‌شدن پرونده‌های نقطه‌ای را بگیرید.</p>
<div class="note"><p><strong>مرزها را از اول بدانید.</strong> در این نسخه <code dir="ltr">salam serve</code> نه TLS دارد، نه <code dir="ltr">proxy_pass</code>، نه CGI و نه سوکت یونیکس برای FastCGI. HTTPS را یک پایان‌دهنده‌ی TLS مثل Caddy یا nginx انجام می‌دهد و برنامه‌های HTTP پایتون و گو و نود هم پشت همان قرار می‌گیرند. جزئیاتش در بخش‌های <a href="#tls">HTTPS</a> و <a href="#other-langs">پایتون و گو</a> است.</p></div>

<h2 id="static">حالت ساده: سرو کردن یک پوشه</h2>
<p>بدون هیچ پرونده‌ای، همین فرمان پوشه‌ی جاری را روی <code dir="ltr">http://127.0.0.1:8000/</code> سرو می‌کند:</p>
<pre class="code" dir="ltr"><code>salam serve</code></pre>
<p>پوشه را هم می‌توانید بدهید و درگاه و نشانی را عوض کنید:</p>
<pre class="code" dir="ltr"><code>salam serve dist
salam serve dist --port=8080
salam serve dist --host=0.0.0.0 --port=8080</code></pre>
<p>پیش‌فرض <code dir="ltr">127.0.0.1:8000</code> است؛ یعنی فقط از همان رایانه دیده می‌شود. برای دیدن از گوشی یا شبکه‌ی محلی <code dir="ltr">--host=0.0.0.0</code> بدهید، اما بدانید این حالت پرونده‌های نقطه‌ای را هم سرو می‌کند.</p>
<ul>
<li>برای هر پوشه <code dir="ltr">index.html</code> را می‌فرستد. اگر نبود، فهرست پوشه را به شکل HTML نشان می‌دهد.</li>
<li>فقط <code dir="ltr">index.html</code> را می‌شناسد؛ فهرست <code dir="ltr">index</code> دلخواه و صفحه‌ی ۴۰۴ سفارشی ندارد.</li>
<li>فایل‌ها را در حافظه نگه می‌دارد و وقتی فایل عوض شود دوباره می‌خواند؛ برای پیش‌نمایش سریع خوب است.</li>
<li>هدر <code>ETag</code>، <code>Last-Modified</code>، پاسخ ۳۰۴ و بازه‌ی بایت (<code>Range</code>) ندارد. این‌ها را حالت پیکربندی دارد.</li>
<li>پرونده‌های نقطه‌ای مثل <code dir="ltr">.env</code> را سرو می‌کند. مسیرهای <code>..</code> را بیرون از پوشه نمی‌برد، اما پوشه‌ای که راز دارد را با این حالت روی شبکه نگذارید.</li>
<li>گزارش دسترسی به شکل <code dir="ltr">GET /path -&gt; 200</code> در خروجی چاپ می‌شود.</li>
<li>فایل‌ها را دوباره نمی‌سازد و تغییرها را نمی‌بیند؛ بعد از هر تغییر دوباره بسازید و صفحه را تازه کنید.</li>
</ul>

<h2 id="build">ساختن سایت با سلام و سرو کردنش</h2>
<p>صفحه‌های سلام به HTML ساخته می‌شوند. یک پروژه‌ی صفحه با <code dir="ltr">salam web</code> به یک صفحه‌ی کامل، و یک پوشه با <code dir="ltr">salam page build</code> به یک HTML برای هر صفحه تبدیل می‌شود. خروجی را در پوشه‌ای مثل <code dir="ltr">dist</code> بگذارید و همان را سرو کنید:</p>
<pre class="code" dir="ltr"><code>mkdir -p dist
salam web --output=dist/index.html
salam serve dist --port=8080</code></pre>
<p>برای سایت چندصفحه‌ای، <code dir="ltr">salam page build</code> هر صفحه را به فایل HTML خودش می‌نویسد و فایل‌های CSS و JS کنارش می‌آیند. اگر صفحه‌ها را با <code dir="ltr">--split</code> ساخته باشید، خروجی جداگانه‌ی CSS و JS هم دارید که می‌توانید برایشان حافظه‌ی نهان بگذارید. صفحه‌های ثابت همان‌طور که هستند کامل‌اند؛ برای بخش‌های پویا به <a href="#salam">اتصال به خود سلام</a> بروید.</p>

<p>خود سایت سلام هم برای پیش‌نمایش خروجی درست همین کار را می‌کند: <code dir="ltr">salam serve website/dist/fa</code>.</p>

<h2 id="config">پیکربندی: از یک سایت تا چند سایت</h2>
<p>پیکربندی یک پرونده‌ی متنی با همان قالب بلوکی سلام است، اما برنامه‌ی سلام نیست: داده است، نه کد. یک تنظیم <code dir="ltr">name = value</code> است، یک بلوک با <code dir="ltr">name:</code> باز و با <code dir="ltr">end</code> بسته می‌شود، توضیح با <code dir="ltr">//</code> یا <code dir="ltr">/* ... */</code> می‌آید، و هر تنظیم و مقدارش در یک خط می‌ماند. رشته‌ها میان دو نقل‌قول‌اند؛ برای مقداری که بک‌اسلش دارد، مثل عبارت باقاعده، از پشت‌نقل‌قول استفاده کنید: <code dir="ltr">`~ \.php$`</code>.</p>
<pre class="code" dir="ltr"><code>server:
    log: access = "/var/log/salam/access.log" end
    site:
        listen = 80
        names = "example.ir www.example.ir"
        root = "/srv/example/public"
        index = "index.html index.htm"
        error page = 404 "404.html"
        location "/assets/": cache = 30d end
        location "= /health": return = 200 "ok" end
        location "/old/": redirect = "https://www.example.ir$uri" code = 301 end
    end
end</code></pre>
<p>ریشه‌ی همه‌چیز بلوک <code dir="ltr">server:</code> است. داخلش بلوک <code dir="ltr">log:</code> برای گزارش دسترسی و بلوک‌های <code dir="ltr">site:</code> برای هر سایت می‌آید. هر سایت یک <code dir="ltr">root</code> دارد و می‌تواند چند بلوک <code dir="ltr">location</code> داشته باشد. بلوک‌ها را می‌توان یک‌خطی هم نوشت: <code dir="ltr">location "= /health": return = 200 "ok" end</code>.</p>
<p>سایت با سرآیند <code>Host</code> انتخاب می‌شود. نام دقیق بر الگوی ستاره‌دار می‌چربد، الگوی بلندتر بر الگوی کوتاه‌تر، و درخواستی که هیچ سایتی آن را ادعا نکرده به سایتی می‌رسد که <code dir="ltr">default = true</code> دارد، وگرنه به اولین سایت آن درگاه. هر سایت اگر <code dir="ltr">listen</code> نداشته باشد روی درگاه ۸۰ می‌نشیند؛ این نکته را در پیکربندی چندسایتی فراموش نکنید.</p>
<p>پیش از هر استقرار، پرونده را بررسی کنید:</p>
<pre class="code" dir="ltr"><code>salam serve --config=web.salam --test</code></pre>
<p>خروجی موفق یک خط است: <code dir="ltr">configuration is ok: 3 site(s), 2 listener(s)</code> و کد خروج ۰. اگر ایرادی باشد، هر مشکل با <code dir="ltr">file:line:column</code> چاپ می‌شود و کد خروج ۱ است. اجرای واقعی با خطای پیکربندی شروع نمی‌شود و کد خروج ۲ می‌دهد. <code dir="ltr">--test</code> بدون <code dir="ltr">--config</code> هم خطا می‌دهد.</p>

<tr><td><code dir="ltr">code = 302</code></td><td>سایت و مسیر</td><td>کد هدایت را از ۱۰۰ تا ۵۹۹ تعیین می‌کند.</td></tr>

<tr><td><code dir="ltr">fastcgi_timeout = 30s</code></td><td>سایت و مسیر</td><td>سقف زمان یک درخواست تا پشتیبان؛ پیش‌فرض ۳۰ ثانیه. کل تبادل را می‌پوشاند.</td></tr>

<h2 id="locations">قاعده‌های مسیر و ترتیب انتخاب</h2>
<p>داخل هر سایت، مسیر درخواست مثل nginx با بلوک‌های <code dir="ltr">location</code> مقایسه می‌شود. چهار شکل دارید:</p>
<ul>
<li><code dir="ltr">location "= /health"</code>: فقط همین مسیر، بدون آزمایش چیز دیگر. سریع‌ترین و قطعی‌ترین.</li>
<li><code dir="ltr">location "/assets/"</code>: هر مسیری که با این پیشوند شروع شود؛ بلندترین پیشوند برنده است.</li>
<li><code dir="ltr">location "^~ /static/"</code>: پیشوندی که اگر برنده شود، جلوی آزمایش عبارت‌های باقاعده را می‌گیرد.</li>
<li><code dir="ltr">location "~ \.php$"</code> و <code dir="ltr">"~* \.png$"</code>: عبارت باقاعده؛ دومی به بزرگی و کوچکی حروف حساس نیست. به ترتیب پرونده آزمایش می‌شوند و اولین مطابقت برنده است.</li>
</ul>
<p>ترتیب کلی این است: اول تطابق دقیق؛ بعد بلندترین پیشوند؛ اگر آن پیشوند <code>^~</code> بود همین‌جا تمام؛ وگرنه عبارت‌های باقاعده به ترتیب پرونده؛ و اگر هیچ‌کدام نخورد، همان بلندترین پیشوند. مسیر پیش از مقایسه URL-decode و پاک‌سازی می‌شود؛ <code>..</code> نمی‌تواند از <code>root</code> بالا برود و مسیری با <code>%00</code> پاسخ ۴۰۰ می‌گیرد.</p>
<p>چند رفتار که در عمل مهم‌اند:</p>
<ul>
<li>فقط فایل‌های ایستا به <code>GET</code> و <code>HEAD</code> پاسخ می‌دهند؛ روش دیگر ۴۰۵ با هدر <code>Allow</code> می‌گیرد. مسیر FastCGI به همه‌ی روش‌ها پاسخ می‌دهد، چون تصمیمش با برنامه است.</li>
<li>فایل‌ها با <code>ETag</code> و <code>Last-Modified</code> می‌روند؛ درخواست تازه ۳۰۴ بدون بدنه می‌گیرد و <code>Range</code> با ۲۰۶ همان بخش را. بازه‌ی بیرون از فایل ۴۱۶ است. چند بازه در یک درخواست با کل فایل پاسخ داده می‌شود.</li>
<li>پوشه‌ای که با <code>/</code> نیامده باشد با ۳۰۱ به شکل اسلش‌دار هدایت می‌شود.</li>
<li>هر بخشی از مسیر که با نقطه شروع شود، مثل <code dir="ltr">.env</code> یا <code dir="ltr">.git</code>، ۴۰۴ می‌گیرد؛ تنها استثنا <code dir="ltr">.well-known</code> است، برای ACME و تأیید دامنه.</li>
<li>برای فایل، مسیر همیشه نسبت به <code>root</code> مؤثر خوانده می‌شود؛ <code>alias</code> فقط پیشوند مسیر را با یک پوشه عوض می‌کند.</li>
</ul>

<h2 id="domains">چند دامنه و چند سایت مختلف روی یک سرور</h2>
<p>همه‌ی سایت‌ها در یک پرونده می‌آیند و یک فرایند <code dir="ltr">salam serve</code> همه را اجرا می‌کند. هر سایت نام‌ها، ریشه و قاعده‌های خودش را دارد:</p>
<pre class="code" dir="ltr"><code>server:
    log: access = "/var/log/salam/access.log" end

    site:
        listen = 80
        names = "example.ir www.example.ir"
        root = "/srv/example/public"
        location "/assets/": cache = 30d end
        location "= /health": return = 200 "ok" end
    end

    site:
        listen = 80
        names = "shop.example.ir"
        root = "/srv/shop/public"
        location "/media/": cache = 7d end
    end

    site:
        listen = 80
        names = "blog.example.ir"
        root = "/srv/blog"
        default = true
    end
end</code></pre>
<p>نکته‌های این پیکربندی:</p>
<ul>
<li>هر سه سایت روی درگاه ۸۰ هستند، ولی یک شنونده ساخته می‌شود؛ انتخاب با <code>Host</code> است. درگاه‌های متفاوت شنونده‌ی جدا می‌سازند.</li>
<li>دو نام یک سایت را می‌توانید در یک رشته بیاورید: <code dir="ltr">"example.ir www.example.ir"</code>. DNS هر دو باید به همین سرور برسد.</li>
<li>سایت سوم <code>default = true</code> است، پس درخواست با نام ناشناخته به آن می‌رسد. این الگوی خوبی برای صفحه‌ی «سایت پیدا نشد» یا سایت اصلی است. بیش از یک default روی یک درگاه نگذارید.</li>
<li>یک نام تکراری روی یک درگاه خطای پیکربندی است: <code dir="ltr">name 'x' is used by two sites on port 80</code>. اگر همان نام را روی درگاه دیگر بخواهید، اشکالی ندارد.</li>
</ul>
<p>اگر چند دامنه‌ی کاملاً متفاوت باید یک پروژه و یک ریشه‌ی یکسان را نشان دهند، همه را در <code>names</code> یک سایت بیاورید: <code dir="ltr">names = "a.ir www.a.ir b.ir c.ir"</code>. DNS همه باید به همین سرور برسد و محتوا یکی است. اگر هر دامنه محتوای خودش را می‌خواهد، برای هر کدام سایت جدا بسازید.</p>
<h3>هدایت دامنه‌ی بدون www به www</h3>
<p>سطح سایت، <code>redirect</code> روی همه‌ی درخواست‌های آن سایت اجرا می‌شود؛ پس دامنه‌ی بدون www را یک سایت جدا بدهید و سایت اصلی را جدا:</p>
<pre class="code" dir="ltr"><code>    site:
        listen = 80
        names = "example.ir"
        redirect = "https://www.example.ir$request_uri"
    end

    site:
        listen = 80
        names = "www.example.ir"
        root = "/srv/example/public"
    end</code></pre>
<p>سایت هدایتگر به <code>root</code> نیاز ندارد، چون سطح سایت پیش از هر مسیری هدایت می‌کند. چون TLS را یک پراکسی جلوتر انجام می‌دهد، مقصد را صریح <code>https://</code> نوشته‌ایم؛ <code>$scheme</code> در سلام همیشه <code>http</code> است. برای آزمایش محلی، <code>Host</code> را دستی بدهید:</p>
<pre class="code" dir="ltr"><code>curl -H "Host: shop.example.ir" http://127.0.0.1:8080/</code></pre>
<p>روی رایانه‌ی خودتان می‌توانید این نام‌ها را در <code>/etc/hosts</code> (یا فایل hosts ویندوز) به <code>127.0.0.1</code> بدهید و مرورگر را باز کنید.</p>

<h2 id="subdomains">چند زیردامنه به یک پروژه‌ی یکسان</h2>
<p>اگر همه‌ی زیردامنه‌ها همان کد و همان ریشه را دارند، یک سایت با همه‌ی نام‌ها بسازید:</p>
<pre class="code" dir="ltr"><code>    site:
        listen = 80
        names = "app.example.ir *.app.example.ir"
        root = "/srv/app/public"
    end</code></pre>
<p>الگوی <code dir="ltr">*.app.example.ir</code> به هر میزبانی می‌خورد که به <code dir="ltr">.app.example.ir</code> ختم شود؛ حتی <code dir="ltr">a.b.app.example.ir</code>. اگر فقط یک سطح زیردامنه می‌خواهید، نام‌ها را یکی‌یکی بنویسید یا در برنامه بررسی کنید. DNS هم باید <code dir="ltr">*.app.example.ir</code> را به سرور بدهد.</p>
<p>حالا برنامه با سرآیند <code>Host</code> می‌فهمد کاربر کدام زیردامنه را باز کرده است. برای سایت ثابت، همان محتوا در همه می‌آید؛ اگر محتوای هر زیردامنه فرق دارد، دو راه دارید:</p>
<ul>
<li><strong>یک ریشه، محتوای پویا:</strong> برنامه‌ی سلام (یا PHP) از <code>Host</code> استفاده می‌کند و محتوای همان زیردامنه را می‌سازد. برای این کار یک سایت با نام‌های ستاره‌دار کافی است.</li>
<li><strong>ریشه‌ی جدا برای هر کدام:</strong> برای هر زیردامنه یک بلوک <code>site:</code> جدا با <code>root</code> خودش بسازید. نام دقیق بر ستاره می‌چربد، پس می‌توانید یک سایت ستاره‌دار برای بقیه داشته باشید و یکی دو زیردامنه‌ی خاص را جدا کنید:</li>
</ul>
<pre class="code" dir="ltr"><code>    site:
        listen = 80
        names = "admin.app.example.ir"
        root = "/srv/admin/public"
    end

    site:
        listen = 80
        names = "*.app.example.ir"
        root = "/srv/app/public"
        default = true
    end</code></pre>
<p>در این مثال <code>admin</code> ریشه‌ی خودش را دارد و بقیه‌ی زیردامنه‌ها از پروژه‌ی اصلی می‌آیند. برای گواهی TLS این چند نام، یا گواهی wildcard بگیرید یا در Caddy هر نام را جدا تعریف کنید؛ salam serve خودش گواهی نمی‌گیرد.</p>

<h2 id="php">اتصال به PHP با php-fpm</h2>
<p>PHP از طریق FastCGI به سلام وصل می‌شود. اول php-fpm را روی یک درگاه TCP بشنوید، چون سوکت یونیکس پشتیبانی نمی‌شود. در فایل pool، مثلاً <code dir="ltr">/etc/php/8.3/fpm/pool.d/www.conf</code>:</p>
<pre class="code" dir="ltr"><code>متغیر_listen = 127.0.0.1:9000
; اگر فقط از همین سرور وصل می‌شوید:
متغیر_listen.allowed_clients = 127.0.0.1</code></pre>
<p>بعد php-fpm را دوباره راه بیندازید. حالا یک سایت PHP با فایل‌های واقعی:</p>
<pre class="code" dir="ltr"><code>server:
    site:
        listen = 80
        names = "php.example.ir www.php.example.ir"
        root = "/srv/php/public"
        index = "index.html"

        location "= /":
            fastcgi_pass = "127.0.0.1:9000"
            fastcgi_index = "index.php"
            fastcgi_timeout = 30s
            fastcgi_param = "APP_ENV" "production"
        end

        location "~ \.php(/|$)":
            fastcgi_pass = "127.0.0.1:9000"
            fastcgi_timeout = 30s
            fastcgi_param = "APP_ENV" "production"
        end

        location "/assets/":
            cache = 30d
        end
    end
end</code></pre>
<p>مسیر <code>/</code> با تطابق دقیق به php-fpm می‌رود و فایل <code dir="ltr">index.php</code> را اجرا می‌کند. عبارت <code dir="ltr">~ \.php(/|$)</code> هر مسیری را که به <code dir="ltr">.php</code> ختم شود یا بعد از آن بخش اضافه داشته باشد می‌گیرد، پس <code dir="ltr">/index.php/a/b</code> هم با <code>PATH_INFO=/a/b</code> اجرا می‌شود و هم فایل PHP به‌صورت متن خام بیرون نمی‌رود. بقیه‌ی فایل‌های ایستا از <code>root</code> خوانده می‌شوند.</p>
<div class="note"><p><strong>هرگز فایل PHP را در فهرست <code>index</code> نگذارید.</strong> اگر <code>index = "index.php"</code> بدهید و مسیری به FastCGI نرود، سلام همان فایل را به‌عنوان فایل ایستا می‌فرستد و کد PHP لو می‌رود. فهرست <code>index</code> را روی <code>index.html</code> بگذارید، مسیر <code>/</code> را با تطابق دقیق به FastCGI بدهید و فقط فایل‌های ورودی PHP را زیر <code>root</code> نگه دارید.</p></div>
<p>سلام این متغیرهای CGI را خودش پر می‌کند: <code>GATEWAY_INTERFACE</code>، <code>SERVER_SOFTWARE</code>، <code>SERVER_PROTOCOL</code>، <code>REQUEST_METHOD</code>، <code>REQUEST_URI</code>، <code>SCRIPT_NAME</code>، <code>SCRIPT_FILENAME</code>، <code>PATH_INFO</code>، <code>DOCUMENT_ROOT</code>، <code>DOCUMENT_URI</code>، <code>QUERY_STRING</code>، <code>CONTENT_TYPE</code>، <code>CONTENT_LENGTH</code>، <code>SERVER_NAME</code>، <code>SERVER_PORT</code>، <code>REMOTE_ADDR</code>، <code>REDIRECT_STATUS</code> و <code>HTTP_*</code> برای هدرهای رایج. <code>fastcgi_param</code> یکی دیگر را اضافه یا عوض می‌کند و <code>$uri</code>، <code>$request_uri</code>، <code>$args</code>، <code>$document_root</code>، <code>$script_name</code>، <code>$server_port</code>، <code>$remote_addr</code> و <code>$header:Name</code> را می‌فهمد.</p>
<div class="note"><p><strong>محدودیت مهم برای فریم‌ورک‌ها.</strong> سلام برای FastCGI دنبال یک فایل واقعی زیر <code>root</code> می‌گردد؛ مسیری که به هیچ فایلی نرسد، پیش از رسیدن به PHP پاسخ ۴۰۴ می‌گیرد. یعنی <code>/index.php</code>، <code>/index.php/a/b</code> و فایل‌های واقعی کار می‌کنند، اما آدرس زیبای <code>/login</code> در Laravel یا وردپرس با پیوند یکتا بدون یک پراکسی جلوتر کار نمی‌کند. اگر پیوند یکتای بدون <code>index.php</code> می‌خواهید، Caddy یا nginx را جلو بگذارید و بازنویسی را آن‌جا انجام دهید؛ یا فعلاً آدرس‌ها را با <code>index.php</code> بدهید. گزینه‌ی سوم، نگه‌داشتن پیوند ساده‌ی <code dir="ltr">?p=123</code> در وردپرس است.</p></div>
<p>پاسخ همان چیزی است که PHP می‌فرستد: خط <code>Status:</code> وضعیت را تعیین می‌کند، بقیه‌ی هدرها همان‌طور بیرون می‌روند (چند <code>Set-Cookie</code> هم) و بدنه بایت‌به‌بایت رد می‌شود. اگر پشتیبان در دسترس نباشد یا نیمه‌کار بمیرد، پاسخ ۵۰۲ است. هر درخواست اتصال خودش را باز می‌کند و <code>REMOTE_ADDR</code> به‌طور پیش‌فرض <code>127.0.0.1</code> است؛ پشت پراکسی آن را با <code dir="ltr">fastcgi_param = "REMOTE_ADDR" "$header:X-Real-IP"</code> عوض کنید و به برنامه بگویید TLS در جلو تمام شده است.</p>

<h2 id="other-langs">پایتون، گو، نود و بقیه‌ی زبان‌ها</h2>
<p>اینجا باید صریح باشم: <code dir="ltr">salam serve</code> <strong>پراکسی معکوس HTTP ندارد</strong> و فقط فایل ایستا و FastCGI می‌فهمد. پس برای پایتون و گو و نود دو راه واقعی دارید.</p>
<h3>راه اول و پیشنهادی: یک پراکسی معکوس جلوتر</h3>
<p>برنامه‌ی پایتون یا گو را روی یک پورت محلی اجرا کنید و Caddy را جلو بگذارید. این‌گونه TLS و WebSocket و بازنویسی مسیر هم یک‌جا حل می‌شود. نمونه‌ی Caddyfile وقتی سلام هم بخشی از سایت را سرو می‌کند:</p>
<pre class="code" dir="ltr"><code>example.ir {
    encode gzip

    handle /api/* {
        reverse_proxy 127.0.0.1:8001
    }

    handle {
        reverse_proxy 127.0.0.1:8080
    }
}</code></pre>
<p>اینجا <code dir="ltr">8001</code> برنامه‌ی پایتون یا گو و <code dir="ltr">8080</code> همان <code dir="ltr">salam serve</code> است. اگر بخش سلام را ندارید، فقط همان <code>reverse_proxy</code> به برنامه را نگه دارید. Caddy گواهی Let's Encrypt را خودش می‌گیرد و <code>Host</code> را دست‌نخورده رد می‌کند.</p>
<h3>راه دوم: FastCGI با یک فایل ورودی</h3>
<p>اگر برنامه‌تان FastCGI حرف می‌زند، می‌توانید مستقیم وصلش کنید. ترفند کار این است که یک فایل خالی به نام نقطه‌ی اتصال زیر <code>root</code> بگذارید تا سلام آن را «اسکریپت» ببیند و بقیه‌ی مسیر را به <code>PATH_INFO</code> بدهد. مثلاً فایل خالی <code dir="ltr">/srv/app/api</code> و این مسیر:</p>
<pre class="code" dir="ltr"><code>        location "/api":
            fastcgi_pass = "127.0.0.1:9100"
            fastcgi_timeout = 60s
        end</code></pre>
<p>حالا <code dir="ltr">/api/users</code> به پشتیبان می‌رسد: <code>SCRIPT_NAME=/api</code>، <code>PATH_INFO=/users</code>. یک استثنای ریز: چون <code>fastcgi_index</code> برای PHP طراحی شده، درخواست دقیقاً <code dir="ltr">/api/</code> به <code dir="ltr">/api/index.php</code> تبدیل می‌شود؛ از <code dir="ltr">/api</code> یا <code dir="ltr">/api/...</code> استفاده کنید. برای پایتون، uWSGI می‌تواند همین پروتکل را روی TCP حرف بزند:</p>
<pre class="code" dir="ltr"><code>pip install uwsgi
uwsgi --fastcgi-socket 127.0.0.1:9100 \
      --wsgi-file /srv/app/app.py \
      --callable app \
      --processes 4</code></pre>
<p>و کوچک‌ترین برنامه‌ی WSGI که مسیر را برمی‌گرداند:</p>
<pre class="code" dir="ltr"><code>def app(environ, start_response):
    path = environ.get("PATH_INFO", "/")
    body = ("hello from python: " + path + "\n").encode()
    start_response("200 OK", [
        ("Content-Type", "text/plain; charset=utf-8"),
        ("Content-Length", str(len(body))),
    ])
    return [body]</code></pre>
<p>برای گو، بسته‌ی <code dir="ltr">net/http/fcgi</code> یک سرور FastCGI می‌دهد. توجه کنید که این بسته در نسخه‌های تازه‌ی گو «منسوخ» علامت خورده اما هنوز کار می‌کند:</p>
<pre class="code" dir="ltr"><code>package main

import (
    "fmt"
    "net"
    "net/http"
    "net/http/fcgi"
)

func main() {
    ln, err := net.Listen("tcp", "127.0.0.1:9100")
    if err != nil {
        panic(err)
    }
    h := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintf(w, "hello from go: %s\n", r.URL.Path)
    })
    if err := fcgi.Serve(ln, h); err != nil {
        panic(err)
    }
}</code></pre>
<p>برای نود هم اگر بسته‌ای مثل <code dir="ltr">node-fastcgi</code> دارید همین الگو جواب می‌دهد؛ وگرنه راه اول را بردارید. محدودیت‌ها را جدی بگیرید: سلام مسیر را با فایل ورودی تطبیق می‌دهد، هر درخواست یک اتصال تازه باز می‌کند، سوکت یونیکس ندارد و همه‌ی درخواست‌های آن مسیر به یک پشتیبان می‌روند. برای نرمال‌ترین استقرار، پراکسی جلوتر بهتر است.</p>

<h2 id="salam">اتصال به خود سلام و سازگاری</h2>
<p>سازگاری سلام با salam serve از دو جهت است. اول این‌که پیکربندی همان قالب بلوکی سلام است و با تجزیه‌گر <code>net/httpd/conf</code> خوانده می‌شود: بلوک‌ها با <code>end</code> (یا <code>پایان</code>) بسته می‌شوند، توضیح‌ها همان <code>//</code> هستند و خطاها با شماره‌ی خط و ستون گزارش می‌شوند. دوم این‌که خود سرور یک بسته‌ی کتابخانه‌ی استاندارد است، پس می‌توانید آن را داخل برنامه‌ی سلام راه بیندازید:</p>
{{example.serve-embed}}
<p>این برنامه دقیقاً کاری را می‌کند که <code dir="ltr">salam serve --config=web.salam</code> می‌کند: پرونده را بررسی و بار می‌کند و اجرا را شروع می‌کند. برای تست پیکربندی بدون اجرا، <code>httpd.Check</code> (یا <code>سرور وب.بررسی</code>) همان <code dir="ltr">--test</code> است؛ برای پرسیدن این‌که یک میزبان یا مسیر به کدام سایت می‌رسد، <code>SiteFor</code>، <code>LocationFor</code>، <code>SiteCount</code> و <code>SiteNames</code> را دارید و هیچ درگاهی باز نمی‌شود.</p>
<p>سه الگوی رایج:</p>
<ul>
<li><strong>سایت ثابت ساخته‌شده با سلام:</strong> <code dir="ltr">salam web</code> یا <code dir="ltr">salam page build</code>، بعد <code dir="ltr">salam serve dist</code>. این ساده‌ترین و سریع‌ترین حالت است.</li>
<li><strong>برنامه‌ی پویا با <code>net/http</code>:</strong> برنامه‌ی سلام خودش سرور را روی یک پورت راه می‌اندازد و می‌تواند فایل‌های ایستا را هم با <code>router.Static</code> بدهد. این برنامه را مستقیم اجرا کنید یا پشت Caddy بگذارید؛ salam serve آن را در خودش mount نمی‌کند چون پراکسی معکوس ندارد.</li>
<li><strong>ترکیب ثابت و PHP:</strong> salam serve هم فایل ایستا می‌دهد هم PHP را به php-fpm می‌سپارد؛ اگر برنامه‌ی پایتون یا گو هم دارید، Caddy بخش <code>/api</code> را به آن و بقیه را به salam می‌دهد.</li>
</ul>
<p>یک تفاوت ظریف: کلیدهای پیکربندی انگلیسی می‌مانند، مثل کلیدهای JSON، حتی اگر API فارسی باشد. نام تابع‌ها و نوع‌های <code>net.httpd</code> نام فارسی هم دارند (<code>بررسی</code>، <code>بارگذاری پرونده</code>، <code>اجرا</code>، <code>توقف</code>)، ولی پیکربندی داده است و با کلید ثابت خوانده می‌شود.</p>

<h2 id="tls">HTTPS و قرار گرفتن پشت Caddy یا nginx</h2>
<p>در این نسخه <code dir="ltr">listen = 443 tls</code> خوانده می‌شود اما با پیام <code dir="ltr">tls is not available yet</code> رد می‌شود. پس TLS را به یک پایان‌دهنده بسپارید. کوتاه‌ترین راه Caddy است:</p>
<pre class="code" dir="ltr"><code>example.ir, www.example.ir {
    reverse_proxy 127.0.0.1:8080
}</code></pre>
<p>این سه کار را با هم می‌کند: گواهی را می‌گیرد و تمدید می‌کند، HTTP را به HTTPS هدایت می‌کند و درخواست را با <code>Host</code> درست به سلام می‌دهد. اگر nginx را ترجیح می‌دهید، همان <code>proxy_pass http://127.0.0.1:8080;</code> و <code>proxy_set_header Host $host;</code> کافی است.</p>
<p>پشت پراکسی دو نکته را تنظیم کنید. برای PHP، <code>REMOTE_ADDR</code> را از هدر پراکسی بگیرید و به برنامه بگویید TLS تمام شده است:</p>
<pre class="code" dir="ltr"><code>            fastcgi_param = "REMOTE_ADDR" "$header:X-Real-IP"
            fastcgi_param = "HTTPS" "on"
            fastcgi_param = "HTTP_X_FORWARDED_PROTO" "https"</code></pre>
<p>برای فایل‌های ایستا، salam گزارش دسترسی را با میزبان و مسیر می‌نویسد اما نشانی طرف مقابل را ندارد؛ اگر به آن نیاز دارید، لاگ Caddy یا nginx را نگه دارید. و یادتان باشد هدایت سطح سایت با <code>$scheme</code> همیشه <code>http</code> می‌سازد، پس مقصد https را صریح بنویسید.</p>

<h2 id="errors">خطاها، عیب‌یابی و بررسی پیش از استقرار</h2>
<p>هر چیزی که ممکن است در پرونده غلط باشد هنگام بارکردن پیدا می‌شود، نه در اولین درخواست. نمونه‌ی خروجی <code dir="ltr">--test</code> برای یک پرونده‌ی خراب:</p>
<pre class="code" dir="ltr"><code>web.salam:3:18: port must be a number from 1 to 65535
web.salam:6:9: header needs two strings: the name and the value
web.salam:7:9: '[' is not a valid regular expression
web.salam:8:13: unknown setting 'returx' in a location (did you mean 'return'?)
web.salam:2:5: root '/srv/does-not-exist' is not a directory
configuration is not valid</code></pre>
<div class="table-wrap"><table class="serve-table">
<thead><tr><th>پیام یا نشانه</th><th>معنا و راه‌حل</th></tr></thead>
<tbody>
<tr><td><code dir="ltr">root '...' is not a directory</code></td><td>پوشه هنگام بارکردن باید وجود داشته باشد. مسیر را درست کنید یا اول بسازید.</td></tr>
<tr><td><code dir="ltr">name '...' is used by two sites on port ...</code></td><td>دو سایت یک نام روی یک درگاه دارند. یکی را عوض کنید یا درگاه را جدا کنید.</td></tr>
<tr><td><code dir="ltr">site number N has no names and is not the default site</code></td><td>هر سایت یا باید <code>names</code> داشته باشد یا <code>default = true</code> باشد.</td></tr>
<tr><td><code dir="ltr">a location path must start with '/'</code></td><td>مسیر پیشوندی باید با اسلش شروع شود. برای عبارت باقاعده از <code>~</code> استفاده کنید.</td></tr>
<tr><td><code dir="ltr">fastcgi_pass cannot read a unix socket yet</code></td><td>php-fpm را روی TCP بگذارید: <code dir="ltr">listen = 127.0.0.1:9000</code>.</td></tr>
<tr><td><code dir="ltr">tls is not available yet</code></td><td>در سلام TLS نگذارید؛ Caddy یا nginx را جلو بگذارید.</td></tr>
<tr><td>پاسخ ۵۰۲</td><td>پشتیبان FastCGI در دسترس نیست، نشانی اشتباه است یا پشتیبان نیمه‌کار مرده است. اتصال TCP و لاگ php-fpm را ببینید.</td></tr>
<tr><td>پاسخ ۴۰۴ برای مسیر PHP بدون پسوند</td><td>سلام فایل اسکریپت را پیدا نکرده است. آدرس را با <code>index.php</code> بدهید یا پراکسی جلوتر با بازنویسی بگذارید.</td></tr>
<tr><td>پاسخ ۴۰۵</td><td>روش غیر از GET و HEAD روی فایل ایستا. <code>Allow</code> را ببینید؛ برای API از FastCGI یا برنامه‌ی سلام استفاده کنید.</td></tr>
<tr><td>پاسخ ۴۰۴ برای <code dir="ltr">.env</code> و پرونده‌های نقطه‌ای</td><td>حالت پیکربندی آن‌ها را می‌بندد؛ تنها استثنا <code dir="ltr">.well-known</code> است. رازها را بیرون از <code>root</code> بگذارید.</td></tr>
</tbody></table></div>
<p>چند نکته‌ی عیب‌یابی که وقت زیاد می‌گیرند:</p>
<ul>
<li><code dir="ltr">--test</code> فقط پیکربندی و وجود <code>root</code> و <code>alias</code> را بررسی می‌کند؛ سالم بودن php-fpm، وجود اسکریپت برای هر درخواست و باز بودن درگاه را نمی‌سنجد.</li>
<li>اگر سرور بالا نمی‌آید و پیام <code dir="ltr">cannot listen on ...</code> است، درگاه اشغال است. با <code dir="ltr">lsof -i :80</code> یا <code dir="ltr">ss -ltnp</code> ببینید چه چیزی آن را گرفته است.</li>
<li>اگر پیکربندی را عوض کردید، سرور در حال اجرا سایت‌های قبلی را نگه می‌دارد؛ دوباره راه بیندازید.</li>
<li>نام میزبان به حروف کوچک تبدیل می‌شود و درگاه و نقطه‌ی پایانی از آن حذف می‌شوند؛ <code dir="ltr">WWW.Example.IR.</code> همان <code dir="ltr">www.example.ir</code> است.</li>
<li>لاگ دسترسی فقط زمان، میزبان، روش، مسیر و وضعیت را دارد؛ IP و زمان پاسخ در آن نیست. اگر این‌ها را می‌خواهید، لاگ پراکسی جلوتر را نگه دارید.</li>
</ul>

<h2 id="production">استقرار تولیدی و چک‌لیست</h2>
<p>برای یک سرور لینوکسی، سرور را با systemd بالا نگه دارید. یک واحد ساده:</p>
<pre class="code" dir="ltr"><code>[Unit]
Description=Salam web server
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=www-data
Group=www-data
WorkingDirectory=/srv
ExecStart=/usr/local/bin/salam serve --config=/srv/web.salam
Restart=on-failure
RestartSec=2
AmbientCapabilities=CAP_NET_BIND_SERVICE

[Install]
WantedBy=multi-user.target</code></pre>
<pre class="code" dir="ltr"><code>sudo systemctl daemon-reload
sudo systemctl enable --now salam-web
sudo systemctl status salam-web
sudo journalctl -u salam-web -f</code></pre>
<p>اگر درگاه ۸۰ را به کاربر غیرریشه می‌دهید، <code>AmbientCapabilities</code> بالا کافی است؛ یا سرور را روی <code>127.0.0.1:8080</code> بگذارید و Caddy را روی ۸۰ و ۴۴۳. کاربر سرویس باید به <code>root</code>ها و مسیر لاگ دسترسی خواندن (و اگر برنامه می‌نویسد، نوشتن) داشته باشد.</p>
<p>چک‌لیست کوتاه پیش از انتشار:</p>
<ul>
<li><code dir="ltr">salam serve --config=web.salam --test</code> را در CI یا پیش از هر استقرار اجرا کنید؛ کد خروج باید ۰ باشد.</li>
<li>پرونده‌ی راز، <code dir="ltr">.env</code>، <code dir="ltr">.git</code> و نسخه‌های پشتیبان را بیرون از <code>root</code> بگذارید. حالت پیکربندی پرونده‌های نقطه‌ای را می‌بندد، اما بهترین کار این است که اصلاً آن‌جا نباشند.</li>
<li>برای دارایی‌های نسخه‌دار (CSS و JS با هش) <code>cache = 30d</code> یا بیشتر بگذارید؛ برای HTML حافظه‌ی نهان نگذارید.</li>
<li>یک <code dir="ltr">location "= /health": return = 200 "ok" end</code> برای probe بگذارید.</li>
<li>گزارش دسترسی را با <code>logrotate</code> بچرخانید؛ سلام خودش چرخش ندارد.</li>
<li>HTTPS را Caddy یا nginx انجام دهد و <code>X-Forwarded-Proto</code> را به برنامه برساند.</li>
<li>هر سایت یک <code>default</code> معنادار داشته باشد؛ سایت پیش‌فرض بی‌صاحب باعث می‌شود دامنه‌ی اشتباه هم پاسخ ۲۰۰ بگیرد.</li>
<li>اگر FastCGI دارید، سقف <code>fastcgi_timeout</code> را با زمان واقعی پاسخ برنامه تنظیم کنید و به یاد داشته باشید هر درخواست یک اتصال تازه می‌سازد.</li>
</ul>

<p>در پایان، <code dir="ltr">salam serve</code> یک سرور کوچک و خوانا برای سایت‌های ثابت و FastCGI است، نه جایگزین کامل nginx. برای یک سایت ثابت یا چند دامنه‌ی ثابت با PHP، همه‌چیز در یک فرمان و یک پرونده‌ی متنی جمع می‌شود. برای برنامه‌های HTTP دیگر و TLS، یک پراکسی ساده جلوتر بگذارید و بگذارید هر ابزار کار خودش را بکند.</p>
